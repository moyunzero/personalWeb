## 这实验能帮你什么


读完并跟着做，你应该能清楚回答：

1. 六种 mode 各在破坏什么？哪一个是正确对照？
2. 为什么要用 **cache ratio / cached_tokens** 当主信号，而不是只盯 TTFT？
3. `correct` 与错误 mode 在代码里对 **messages 列表**的处理差在哪一行逻辑？
4. 如何不花 API 用 `-report` 看对照表？如何只 live 跑最扎眼的一对？
5. `.env` 加载、Moonshot vs OpenRouter 有哪些常见坑？

一句话结论：

> **缓存认的是前缀字节序列，不是「语义差不多」。**
>
> 系统提示、工具定义等靠前内容一改，改动点之后往往整段重算。
>
>
> 你亲手测到：`correct` 仍有可观 `cached_tokens`；`shuffled_tools` 可以把 Cache% 打到 **0**。
>

书中三条实践结论（可当本实验满分答卷）：

1. **系统提示词和工具定义一旦确定就尽量别改**（越靠前，伤缓存通常越大）
2. **动态信息追加到末尾**（或走工具），不要改写已有前缀
3. **用标准 API 消息格式**，不要自行拼成不稳定的纯文本对话流

## 2. 实验在证明什么


目录：`chapter2/kv-cache/`。


一个带本地文件系统工具（`read_file` / `find` / `grep`）的 ReAct Agent，在六种上下文策略下跑同一类任务，对比：

- **Cache%**（cached / prompt）、cache hits/misses
- TTFT、总时长（辅证；推理模型噪声大）
- 行为（尤其滑动窗口丢工具结果、文本格式导致混乱）

台账：六份 `result_*_20260718_kimi_k2_6.json` 为作者侧冻结证据；幅度如实报告，不硬凑历史百分比。


默认模型：`kimi-k2.6`（会报 `cached_tokens` 的 Kimi 系）。老的 `moonshot-v1-*` **往往不报**该字段，不适合做本实验的缓存演示。


---


## 3. 六种 mode（一张表）


| Mode              | 在干什么                               | 主要伤害                                   |
| ----------------- | ---------------------------------- | -------------------------------------- |
| **`correct`**     | 固定 system、固定工具顺序、标准 messages，列表只追加 | **对照**：前缀稳定，缓存可工作                      |
| `dynamic_system`  | 每次往 system 里塞变化时间戳等                | 从前缀改动点起缓存失效                            |
| `shuffled_tools`  | 每轮打乱 tools 定义顺序                    | 工具 schema 靠前 → **缓存命中常暴跌**             |
| `dynamic_profile` | 每轮改用户积分等画像塞进上下文                    | 同上类「无关动态进前缀」                           |
| `sliding_window`  | 只保留最近约 6 条历史                       | 前缀不连续；**更易丢掉早期工具结果**、反复调用              |
| `text_format`     | 历史打成 `USER:/ASSISTANT:` 纯文本        | 书强调：**更伤的是偏离训练时的角色消息格式**（行为崩）；缓存不是唯一故事 |

> README 英文对 `text_format` 也写了 cache，但正文区分更细：前缀若字节仍稳定，缓存仍可能命中；真正的坑是模型要额外「猜」对话结构。读实验时以书为准。

## 4. 关键代码原理（和 README「Critical detail」一致）


`agent.py` 的 `execute_task` 里：


```plain text
CORRECT:
  第 1 轮 _format_messages 建好 list
  之后同一 list 上不断 append assistant / tool
  → 前缀稳定 → 跨请求前缀缓存有机会命中

错误 modes:
  每一轮迭代开始都 _format_messages 重建整份 messages
  （轮内仍可 append，保证单轮 API 合法）
  → 边界上一重建 + system/tools/窗口/文本化变化
  → 前缀不再字节一致 → cached_tokens 变差或归零
```


各 mode 的「怎么脏」：

- `dynamic_system`：`_get_system_prompt()` 掺时间戳
- `shuffled_tools`：`_get_tools()` 每轮 `random.shuffle`
- `dynamic_profile`：追加会变的 credits 消息
- `sliding_window`：历史只留尾部窗口（并回退对齐 tool 配对）
- `text_format`：把历史压成纯文本块再塞回去

入口：


| 文件              | 角色                                                       |
| --------------- | -------------------------------------------------------- |
| `main.py`       | CLI：交互 / `--mode` / `--compare` / **`--report`** **离线表** |
| `agent.py`      | ReAct + 六 mode + 读 `cached_tokens`                       |
| `result_*.json` | 单次运行收据                                                   |

## 5. 推荐学习顺序


### 第 1 步：读目标


`book/chapter2.md` 实验 2-3 五种错误 + 小结；`README` 的 Implementation modes。


### 第 2 步：先离线看表（零 API）


仓库已有作者收据。在项目目录：


```bash
cd chapter2/kv-cache
source ../../.venv/bin/activate

python main.py --report \
  --input result_correct_20260718_kimi_k2_6.json \
          result_dynamic_system_20260718_kimi_k2_6.json \
          result_dynamic_profile_20260718_kimi_k2_6.json \
          result_shuffled_tools_20260718_kimi_k2_6.json \
          result_sliding_window_20260718_kimi_k2_6.json \
          result_text_format_20260718_kimi_k2_6.json
```


读表口诀：

1. **主看 Cache% / Cached**
2. TTFT 当辅证（推理模型会抖）
3. `sliding_window` 若 Cache% 虚高：常因 **prompt 被截短**，高比例 ≠ 高效
4. `dynamic_*` 有时 Cache% 接近 `correct`：动态若靠后，前缀大段仍命中，但总耗时仍可能变差——**动态别进稳定前缀**

### 第 3 步：配 Key（常见坑）


`main.py` 使用 `load_dotenv()`，默认读**当前目录** **`.env`**。


| 坑                                       | 现象                  | 处理                                                     |
| --------------------------------------- | ------------------- | ------------------------------------------------------ |
| 文件叫 `env` 不叫 `.env`                     | 变量读不到               | `cp env .env`                                          |
| `MOONSHOT_API_KEY` 行被 `#` 注释            | Moonshot missing    | 取消注释或改用 OpenRouter                                     |
| 行首空格 / 奇怪引号                             | `could not parse`   | 保持 `KEY=value`，无 `export`                              |
| 在 `python - <<'PY'` 里无参 `load_dotenv()` | 可能 `AssertionError` | `load_dotenv(Path('.env'))` 显式路径                       |
| 只有 `OPENROUTER_API_KEY`                 | 仍可跑                 | README：回退 OpenRouter，`kimi-*` 会映射；与官方 Moonshot 分布可能略有差 |


优先级：`MOONSHOT_API_KEY` / `KIMI_API_KEY` > `OPENROUTER_API_KEY`。


需要会报 `cached_tokens` 的模型（如 `kimi-k2.6`）。


### 第 4 步：live 最小对照（省钱）


不必一次跑满六模式。最能说明「前缀前部被改」的是：


```bash
python main.py --no-interactive --mode correct --model kimi-k2.6 \
  --output result_correct_mine.json

python main.py --no-interactive --mode shuffled_tools --model kimi-k2.6 \
  --output result_shuffled_tools_mine.json

python main.py --report \
  --input result_correct_mine.json result_shuffled_tools_mine.json
```


### 第 5 步：解读——主信号 vs 噪声


以一次本机实测（OpenRouter 回退）为例：


| Mode             | Cache%    | Cached | Hit%  | Total(s) | 1st TTFT |
| ---------------- | --------- | ------ | ----- | -------- | -------- |
| `correct`        | **24.4%** | 20,928 | 33.3% | 263.2    | 17.5s    |
| `shuffled_tools` | **0.0%**  | 0      | 0.0%  | 189.7    | 6.8s     |


**成立的结论**：打乱工具顺序 → 缓存统计归零。


**不要写成的结论**：shuffled「一定更慢」。本轮 shuffled 总时长与首包 TTFT 反而更短，因为：

1. 推理模型 TTFT 方差大（README 明确优先 Cache%）
2. 工具调用次数不同（例如 22 vs 16），墙钟含「干了多少活」
3. OpenRouter 路由 / 缓存计量与官方 Moonshot 收据不必同分布

报告脚注也提醒：不同文件若非同一 `--compare` 任务，绝对墙钟仅供参考。

## 7. 常见问题


**Q: 为什么正确模式后面几轮 TTFT 还会变差？**


A: 对话变长、工具结果堆积、推理模型隐藏思考、网络抖动都会推高 TTFT。看**跨 mode 的 Cache% 对比**，不要单看一轮墙钟。


**Q: 必须 live 跑满六种吗？**


A: 学习上：离线六份 + live 一对（correct / shuffled）通常够。台账完整证据是作者侧六份收据。


**Q:** **`Save%`** **/** **`Bill.Tok`** **是真实账单吗？**


A: 否。`--cache-price-ratio`（默认 0.1）只是**成本示意**。


**Q: 和 Prompt Cache / KV Cache 两个词怎么并存？**


A: 书里：单次生成内的 KV Cache vs 跨请求的 Prompt/前缀缓存，原理都吃「前缀不变」。本实验读的 API `cached_tokens` 更贴近**跨请求前缀缓存**计量；工程上仍用「别乱动前缀」同一条纪律。

## 8. 复习卡片

1. **六 mode**：1 正确 + 5 反模式
2. **correct** = 同一 messages 只追加；错误 = 每轮重建（再叠加各自脏法）
3. **主信号 = Cache% / cached_tokens**；TTFT 辅证
4. **shuffled_tools** 最能演示「前缀前部被改」
5. **sliding_window**：缓存比例可能虚高 + 丢工具记忆
6. **text_format**：优先理解成「格式/行为」问题
7. **动态信息放末尾或走工具**，不要改 system/tools 前缀
