### AI Agent 的五个核心属性


一个 AI Agent 由五个具体属性定义。理解这些属性，能让你区分简单的聊天机器人或自动补全功能，与真正能推理、行动并追求目标的系统。


**1. 自主性（Autonomy）**


系统自己决定下一步做什么，而不是走硬编码的路径。


一个按脚本决策树运行的聊天机器人不算自主。


而一个根据对话实时决定“是查订单、查退款政策，还是升级给人工”的 Agent，才是自主的——它在实时做决策。


**2. 工具使用（Tool Use）**


Agent 会调用外部函数和 API，真正影响外部世界。


一个只生成文字建议用户去访问某个 URL 的 LLM，并不是在使用工具，它只是在产出文字。


而一个真正调用订单查询 API，并把返回数据用到回复里的 AI Agent，才是在使用工具。


区别在于：描述一个动作，还是真正执行这个动作。


**3. 推理（Reasoning）**


Agent 使用 LLM 评估观察结果并规划下一步。


这与基于关键词匹配的规则系统（if-else 逻辑）完全不同。


Agent 会读取规则结果，推理出“订单是 6 天前下的，落在 30 天退货窗口内”，然后决定“我需要处理退款”。


这个评估步骤，就是这里所说的推理。


**4. 记忆（Memory）**


Agent 会在任务步骤之间、以及跨会话之间保持上下文。


无状态 API 把每次请求都当独立事件处理。


而 Agent 会记住客户之前的工单、偏好，以及当前对话中发生的一切。


**5. 目标追求（Goal Pursuit）**


Agent 会跨多个步骤朝着一个结果努力，而不是回答完一个提示就停止。


它会调用多个工具、评估中间结果，并持续推进，直到客户问题被解决，或者必须升级给人工。


具备全部五个属性的系统是**完全 Agent 化**的；只具备部分属性的则是**部分 Agent 化**的。这就是 **Agentic Spectrum（Agent 化光谱）** 成为有用设计工具的原因。


光谱一端是完全确定性流水线（没有 LLM 参与）。


在固定流水线的某些步骤加入 LLM 决策，就变成 LLM 辅助工作流。


再加入工具使用和记忆，就进入部分 Agent 化状态。


如果再加入完全自主（没有预定义步骤），就成了完全自主系统。


目前大多数生产环境的 Agent 系统都处于**部分 Agent 化**区间。


完全自主系统能力很强，但会带来不可预测行为、更高成本和更难调试的问题。


选择部分自主并不是妥协，而是刻意的设计决策，用来平衡 Agent 的能力与人类可控性。

> 当需要你设计一个 AI Agent 时，你的第一步应该是明确系统实际需要多少自主性。  
> 不要直接说“我需要一个完全自主的 Agent”，而应该说类似这样的话：“这个问题需要一个部分 Agent 化的系统。LLM 决定调用哪个工具，但流水线结构和授权边界由我们定义。”  
> 这显示你做的是深思熟虑的架构选择，而不是一上来就追求最先进的选项。

这个光谱给了我们统一的语言。

### Agent 循环（Agent Loop）：感知-推理-行动


无论使用什么框架或复杂程度，每个 AI Agent 都运行着这个五步循环的变体。这个循环是整个课程的核心心智模型。

1. **观察（Observe）**：Agent 接收输入。这可以是用户消息、上一次工具调用的结果，或系统事件。
2. **决策（Decide）**：LLM 处理当前上下文（系统提示、对话历史、可用工具定义），决定下一步做什么。
3. **行动（Act）**：Agent 执行这个决策——可能是调用工具、生成对用户的回复、请求更多信息，或升级给人工。
4. **更新（Update）**：Agent 把结果写入记忆或状态。把工具结果追加到对话历史、更新用户画像，或记录已采取的行动。
5. **停止（Stop）**：Agent 检查任务是否完成。如果满足终止条件，就退出并返回最终输出；否则回到第一步继续观察。

**停止步骤非常关键**。很多 Agent 在生产环境中失败就出在这里。


如果没有明确的终止条件，一个无法解决任务的 Agent 会进入无限循环，疯狂消耗算力和 API 费用。


**循环预算（loop budget）**——最大迭代次数——就是用来防止这个问题的。 


循环运行的次数取决于任务复杂度，而不是 Agent 质量。


简单问题（比如“营业时间是什么？”）通常只跑一轮：观察问题 → 决定可以直接从知识回答 → 生成回复 → 更新历史 → 停止。


退款请求则可能跑多轮：先查订单 → 再查退货政策 → 处理退款 → 生成确认。每一轮都是一次完整循环迭代。

### Agent 系统的五个构建块（Components）


每个 Agent 系统都由五个构建块组成。不同 Agent 的组合方式不同，但生产级 Agent 都会用到全部五个。理解这些组件及其交互方式，才能从零设计一个 Agent。

1. **模型（Model）**

    推理引擎。它评估上下文、选择工具、生成回复。关键设计决策是成本 vs 能力 vs 延迟。很多生产 Agent 会使用多个模型：用更小更便宜的模型做意图分类等简单任务，用更强的模型做复杂推理（比如判断退款资格）。

2. **工具（Tools）**

    Agent 可以调用的外部函数、API 和服务。工具是 Agent 与聊天机器人的本质区别。设计决策包括：暴露多少工具、如何定义 schema、以及工具超时或返回错误时如何处理。工具设计是大多数 Agent 可靠性问题的来源。

3. **记忆（Memory）**

    Agent 如何获取信息。有三种记忆：

    - 短期记忆：会话内的对话历史
    - 长期记忆：跨会话的持久存储（客户偏好、历史工单等）
    - 知识记忆：通过 RAG 检索的内容（产品 FAQ、退货政策文档等）
4. **状态（State）**

    跟踪 Agent 当前执行位置（在哪一步、已完成什么、在等待什么）。


    状态常被与记忆混淆，但区别很重要：

    - **记忆**是 Agent 知道什么
    - **状态**是 Agent 处于什么位置
    例如：记忆记录“这个客户最近三次工单都与物流延误有关”；状态记录“Agent 目前在四步流程中的第二步，正在等待订单查询结果返回”。
    记忆在观察到新信息时变化；状态在 Agent 进入下一步或收到工具结果时变化。
5. **护栏（Guardrails）**

    防止 Agent 采取有害、未授权或成本过高行动的约束。例如：哪些操作需要人工审批、货币限额是多少、哪些输入模式应该被拦截。


    没有护栏的 Agent 可能处理未授权退款、泄露客户数据，或被操纵性提示诱导。

### 贯穿全课的案例：客户支持 AI Agent


本课程会逐步构建一个完整系统——为一家叫 Tech Store 的电子商店设计客户支持 AI Agent。


这个 Agent 需要：

- 处理客户查询
- 查询订单
- 处理退款
- 从知识库回答产品相关问题
- 必要时升级给人工客服
- 跨会话维护对话历史

这个案例之所以好用，是因为它完整包含了刚才讲的五个组件：

- 需要模型路由做成本优化
- 需要四个不同 schema 和失败模式的工具
- 需要短期 + 长期记忆
- 需要多步解决流程的状态跟踪
- 需要护栏（例如退款自动审批 50 美元阈值 + 提示注入防护）

每一节都会给这个系统增加一层：

- 第 2 节：选择模型 + 上下文窗口管理
- 第 3 节：选择执行模式
- 第 4 节：设计工具 schema + 错误处理
- 第 5 节：构建对话与客户历史管理
- 第 6 节：连接知识库与检索流水线
- 第 7 节：在单 Agent 提示过载时拆分为专门的 Worker Agent
- 第 8 节：加入重试逻辑与优雅降级
- 第 9 节：加入安全边界
- 第 10 节：定义质量指标与监控
- 第 11 节：优化成本并扩展到 1 万并发会话
