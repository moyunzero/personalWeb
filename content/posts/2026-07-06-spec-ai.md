### 什么是 Spec？


**Spec** 就是在让 AI 动手之前，先把你想清楚的事情写下来。它可以是一段话、Markdown 文档，甚至是一个 GitHub Issue。形式不重要，核心是回答三个问题：

1. **你到底要做什么？**（意图）
2. **什么能动，什么不能动？**（约束）
3. **怎么算做完了？**（验收标准）

三者缺一不可。AI 替你做决定时，十有八九不是你真正想要的结果。


### 真实案例：待办事项筛选功能


**模糊指令**：“帮我做一个待办事项的筛选功能”


AI 可能添加搜索框、下拉菜单、复杂过滤语法……技术上能跑，但完全不符合你的预期，导致多次返工。


**清晰 Spec**：

> 基于现有待办列表组件，增加筛选功能。
>
> 支持按状态筛选：全部、进行中、已完成。
>
>
> 支持关键词搜索，300ms 防抖。
>
>
> 筛选状态同步到 URL，刷新不丢失。
>
>
> 不改后端接口，前端处理。
>
>
> 无匹配结果时显示空状态。
>
>

这样，AI 自由发挥的空间被大幅压缩，输出质量显著提升。你没有写一行代码，却把 Agent 的注意力精准框定。


### 好 Spec 的三个共同点


1. 意图清晰


不是“做一个功能”，而是“基于什么模块，用什么方式做什么事”。越具体，AI 越容易对齐你的想法。


就像带新人一样：模糊指令会引发多次追问，清晰指令能让对方直接上手。


2. 约束明确


很多人忽略这一点，但**不做什么”往往比“做什么”更重要**。


AI 默认会尝试各种可能：引入新依赖、修改不该动的文件、改变函数签名等。一定要明确写出约束，例如：

- 不引入新依赖
- 不改后端接口
- 不动某个目录下的文件
- 保持现有函数签名兼容

3. 验收标准可测


定义“做完了”的客观标准。每一条都应该是可验证的（看到或没看到），避免“差不多就行”的模糊空间。


示例：

- 筛选栏显示在列表上方
- 点击状态标签切换筛选，列表即时更新
- 刷新页面后筛选状态保留
- 无匹配结果时显示空状态提示

### 轻量版 vs 重量版


**轻量版**（适合小改动）：
直接写在对话中，三五行即可。例如给 UserService 加注销方法：

> 在 UserService 加一个 deleteAccount 方法，软删除（设 deleted_at）而不是物理删除。同时撤销该用户所有的 session。写一个单元测试覆盖正常流程和用户不存在的情况。

**重量版**（适合复杂功能）：
存成独立文档（如 `specs/feature-xxx.md`），结构示例：


```markdown
# 待办事项筛选功能

## 背景
用户待办列表变长后，需要按状态和关键词快速找到目标项。

## 目标
在列表上方增加筛选栏，支持按状态和关键词筛选。

## 非目标
不做日期筛选。不做多选批量操作。不做服务端筛选。

## 约束
- 不改现有 API
- 不引入新依赖
- 筛选状态需要 URL 可同步

## 验收标准
- [ ] 筛选栏显示在列表上方
- [ ] 点击状态标签切换筛选，列表即时更新
- [ ] 输入关键词后 300ms 防抖过滤
- [ ] 刷新页面后筛选状态保留
- [ ] 无匹配结果时显示空状态提示
```


重量版适合跨会话使用，每次新会话可直接引用。


**选择建议**：一个会话能搞定的用轻量版；跨天、多模块的用重量版。


### Spec 是活的


Spec 不是一次性文档，而是一份动态合约。开发过程中发现新约束或边界 case 时，及时更新。否则 AI 会按旧版执行，导致浪费。


### 可直接使用的模板


```markdown
# [功能名称]

## 背景
为什么要做这个？解决什么问题？

## 目标
具体要实现什么。

## 非目标
明确不做什么。

## 约束
- 不改什么
- 不引入什么
- 兼容什么

## 验收标准
- [ ] 标准 1
- [ ] 标准 2
- [ ] 标准 3
```


小改动可能只需“目标 + 约束 + 验收标准”；大功能再用完整结构。
