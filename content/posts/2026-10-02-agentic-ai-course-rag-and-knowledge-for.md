### **第 6 节：**面向智能体的 RAG 与知识


RAG（检索增强生成）是智能体访问其训练数据之外知识的方式。智能体不再依赖大语言模型在训练期间记住的内容，而是在查询时检索相关文档并将其包含在提示中。这将响应基于事实，减少幻觉，并使智能体能够处理模型从未见过的私有、当前或领域特定数据。


在第 2 节中，我们将幻觉和过时知识确定为两个核心大语言模型局限性。RAG 是两者的主要架构解决方案。在第 5 节中，我们覆盖了上下文工程和词元预算。RAG 是该上下文预算的最大消费者。本节覆盖机制：如何将文档转化为可搜索的向量、如何检索正确的块，以及如何判断 RAG 是否适合你的用例。


**我们将覆盖的内容：**

- 嵌入和向量表示如何工作
- 针对不同文档类型的分块策略
- 向量数据库与相似度搜索
- 检索模式：相似度、混合和重排序
- 少样本示例作为上下文知识
- 何时使用 RAG vs 微调 vs 长上下文
- 完整示例：构建支持智能体的知识库

**这在客户支持智能体中的位置：**


我们的支持智能体需要回答关于退货政策、产品详情、配送时间线和 FAQ 主题的问题。这些信息存在于公司文档中，而不是大语言模型的训练数据中。没有 RAG，智能体要么拒绝回答（“我没有那个信息”），要么幻觉出一个不存在的政策。有了 RAG，智能体检索实际政策文档，并生成基于真实、当前公司数据的响应。

### 嵌入和向量如何工作


**嵌入：文本转数字**


嵌入将一段文本转换为数值向量，即一组捕捉文本含义的数字。关键属性：含义相似的文本产生在数学空间中彼此接近的向量。含义不同的文本产生彼此远离的向量。


嵌入模型与大语言模型是分开的。你不使用 GPT-4o 或 Claude 来生成嵌入。你使用专门的嵌入模型（OpenAI 的 text-embedding-3-small、Cohere 的 embed-v3，或 all-MiniLM-L6-v2 等开源模型），它专门训练用于产生有意义的向量表示。


**相似度如何工作**


```plain text
文本 A：“How do I return a product?”
文本 B：“What is your refund and return policy?”
文本 C：“What time does the store open?”

嵌入 A：[0.12, -0.34, 0.78, 0.56, ...]   （1536 维）
嵌入 B：[0.11, -0.31, 0.75, 0.54, ...]   （1536 维）
嵌入 C：[0.89, 0.23, -0.45, 0.12, ...]   （1536 维）

相似度(A, B) = 0.94  → 非常相似（都是关于退货）
相似度(A, C) = 0.23  → 不相似（完全不同主题）
```


余弦相似度测量两个向量之间的角度。得分 1.0 表示含义相同。得分 0.0 表示完全不相关。在实践中，高于 0.75 的得分表示强相关，低于 0.40 的得分表示弱相关或无相关。


**RAG 流水线**


步骤 1：用户提出问题。步骤 2：问题使用嵌入模型转换为向量。步骤 3：向量数据库找到存储的文档块中向量最接近问题向量的块。步骤 4：最匹配的块被注入大语言模型提示，大语言模型生成基于这些块的响应。


**Python 实现**


```python
import openai

def embed_text(text):
    response = openai.embeddings.create(
        model="text-embedding-3-small",
        input=text
    )
    return response.data[0].embedding

def rag_query(user_question, vector_db, llm_client):
    question_embedding = embed_text(user_question)

    results = vector_db.query(
        vector=question_embedding,
        top_k=3
    )

    context_chunks = "\n\n".join([r.text for r in results])

    response = llm_client.chat(
        system="Answer the customer's question using ONLY the provided context. "
               "If the context does not contain the answer, say so honestly.",
        messages=[{
            "role": "user",
            "content": f"Context:\n{context_chunks}\n\nQuestion:{user_question}"
        }]
    )

    return response
```


**嵌入模型对比**


| 模型                             | 维度   | 成本（每 1M 词元） | 质量          | 速度  |
| ------------------------------ | ---- | ----------- | ----------- | --- |
| text-embedding-3-small（OpenAI） | 1536 | 约 $0.02     | 适合大多数用例     | 快   |
| text-embedding-3-large（OpenAI） | 3072 | 约 $0.13     | 在细微查询上准确率更高 | 中等  |
| embed-v3（Cohere）               | 1024 | 约 $0.10     | 强多语言支持      | 快   |
| all-MiniLM-L6-v2（开源）           | 384  | 免费（自托管）     | 适合英语，边缘情况较低 | 非常快 |
| BGE-large-en（开源）               | 1024 | 免费（自托管）     | 与商业模型有竞争力   | 中等  |


知道嵌入是什么、为什么有效（相似含义映射到相似向量），以及它们由独立于大语言模型的模型生成。知道余弦相似度是标准度量。你不需要解释嵌入训练背后的线性代数或余弦相似度的数学定义。

### 分块策略


**为什么分块重要**


在嵌入和存储文档之前，你需要将它们拆分成块。块是检索的单位。当用户提问时，向量数据库返回块，而不是整个文档。分块决策直接影响检索质量：块太小会丢失上下文，块太大会在无关内容上浪费词元。


**四种主要策略**


**固定大小分块**


将文档拆分为固定词元数的块（例如每块 512 词元）。实现简单，作为合理默认值有效，但拆分可能落在句子或段落中间，破坏含义。


```python
def fixed_size_chunk(text, chunk_size=512, overlap=50):
    tokens = tokenizer.encode(text)
    chunks = []
    for i in range(0, len(tokens), chunk_size - overlap):
        chunk_tokens = tokens[i:i + chunk_size]
        chunks.append(tokenizer.decode(chunk_tokens))
    return chunks
```


**基于句子的分块**


在句子边界拆分，将句子分组直到块达到目标大小。保留完整句子，当块被注入提示时提高理解。


**语义分块**


在主题边界拆分。使用嵌入模型检测连续句子之间含义显著变化的位置。计算成本更高，但产生内部连贯的块。


**递归分块**


先在最大的结构边界拆分（章节标题、双换行），然后递归地将仍然过大的块在段落边界拆分，然后在句子边界拆分。这是 LangChain 中的默认策略，对结构化文档效果良好。


**块大小权衡**


| 块大小           | 优势           | 劣势                    |
| ------------- | ------------ | --------------------- |
| 小（128-256 词元） | 精确检索，每块噪声更少  | 丢失周围上下文，可能将完整答案分散到多个块 |
| 中（512 词元）     | 精度和上下文平衡     | 大多数文档类型的良好默认值         |
| 大（1024+ 词元）   | 保留答案周围的完整上下文 | 在无关内容上浪费词元预算，检索精度更低   |


**重叠**


在连续块之间包含 50-100 词元的重叠。没有重叠，块边界处的信息对检索实际上不可见。一个答案跨越块 7 和块 8 之间边界的问题，除非块重叠，否则无法检索到完整答案。


```plain text
文档：[... 句子 A。句子 B。句子 C。句子 D。句子 E ...]

没有重叠：
  块 1：[句子 A。句子 B。句子 C。]
  块 2：[句子 D。句子 E。]
  → 关于 B-C-D 的问题？两个块都没有完整答案。

有 50 词元重叠：
  块 1：[句子 A。句子 B。句子 C。]
  块 2：[句子 C。句子 D。句子 E。]
  → 关于 B-C-D 的问题？块 1 或块 2 可能覆盖足够。
```


**按文档类型的分块策略**


| 文档类型   | 推荐策略          | 块大小               | 原因              |
| ------ | ------------- | ----------------- | --------------- |
| FAQ 文章 | 保持完整（每篇文章一块）  | 不定（通常 100-500 词元） | 每个 FAQ 是自包含的问答对 |
| 政策文档   | 递归（在章节标题拆分）   | 512 词元            | 政策有清晰的章节结构      |
| 产品目录   | 每个条目一块        | 因产品而异             | 每个产品是独立单元       |
| 长手册    | 递归带重叠         | 512 词元，100 重叠     | 大型文档需要结构拆分      |
| 邮件线程   | 每条消息          | 不定                | 每条消息是不同上下文单元    |
| 代码文档   | 递归（在函数/类标题拆分） | 256-512 词元        | 保留函数级上下文        |


**关键洞察**


分块不是一刀切的决策。正确的策略取决于文档类型、预期查询模式和上下文预算。对于我们的客户支持智能体，FAQ 和产品目录使用与政策文档不同的策略。设计分块策略与选择嵌入模型同样重要。

### 向量数据库与检索


**向量数据库做什么**


向量数据库存储嵌入并支持大规模快速相似度搜索。你插入文档块（作为向量），稍后用问题向量查询。数据库在毫秒内返回最相似的存储向量，即使跨越数百万块。


传统数据库按精确匹配搜索（WHERE product_id = 123）。向量数据库按相似度搜索（找到含义最接近此问题的 5 个块）。这是一种根本不同的查询类型，需要专门的索引算法（HNSW、IVF），它们用完美准确率换取速度。


**向量数据库选项**


| 数据库      | 托管            | 规模      | 成本模型             | 最适合                     |
| -------- | ------------- | ------- | ---------------- | ----------------------- |
| Pinecone | 托管云           | 数十亿向量   | 按存储向量 + 查询付费     | 生产，无需基础设施管理             |
| Weaviate | 自托管或云         | 数百万到数十亿 | 免费（自托管），付费（云）    | 希望控制基础设施的团队             |
| pgvector | PostgreSQL 扩展 | 数百万向量   | 现有 PostgreSQL 成本 | 已使用 PostgreSQL 的团队，中等规模 |
| Chroma   | 本地或嵌入式        | 数千到数百万  | 免费（开源）           | 原型设计，小型知识库              |
| Qdrant   | 自托管或云         | 数十亿向量   | 免费（自托管），付费（云）    | 性能关键应用                  |


**选择向量数据库**


决策取决于你的规模和基础设施。对于用几千份文档构建第一个智能体的初创公司，Chroma 或 pgvector 足够，并避免在技术栈中添加新服务。对于处理数百万文档且要求亚 100ms 检索的生产系统，Pinecone 或 Qdrant 更合适。


pgvector 值得特别提及。如果你的应用已经使用 PostgreSQL（大多数应用都使用），pgvector 让你在同一数据库中与关系数据一起存储嵌入。无需操作额外服务。权衡：pgvector 在大规模（1000 万+ 向量）时比专用向量数据库慢，但对大多数应用来说，永远达不到那个规模。


**索引和摄取流水线**


在查询之前，你需要构建索引。这是一个批处理过程，在首次设置知识库时运行一次，并在文档更新时增量运行。


```python
def build_knowledge_base(documents, vector_db):
    for doc in documents:
        chunks = chunk_document(doc)
        for chunk in chunks:
            embedding = embed_text(chunk.text)
            vector_db.upsert(
                id=chunk.id,
                vector=embedding,
                metadata={
                    "source": doc.filename,
                    "section": chunk.section_title,
                    "doc_type": doc.type
                }
            )
```


注意元数据。每个块都存储了关于其来源、章节和文档类型的元数据。这支持过滤检索：“仅在政策文档中搜索”或“仅在 FAQ 文章中搜索”。元数据过滤在相似度匹配之前缩小搜索空间，这同时提高相关性和速度。


**检索流程**


```python
def retrieve_relevant_chunks(question, vector_db, top_k=3, doc_type=None):
    question_embedding = embed_text(question)

    filter_params = {}
    if doc_type:
        filter_params["doc_type"] = doc_type

    results = vector_db.query(
        vector=question_embedding,
        top_k=top_k,
        filter=filter_params
    )

    return [
        {"text": r.text, "source": r.metadata["source"], "score": r.score}
        for r in results
    ]
```


**相关性得分阈值**


并非每个检索结果都有用。相似度得分 0.45 意味着该块最多只是模糊相关。将低相关性块注入提示会浪费词元，并可能混淆大语言模型。


| 得分范围        | 解释            | 行动        |
| ----------- | ------------- | --------- |
| 0.85 - 1.00 | 高度相关，接近精确匹配   | 始终包含      |
| 0.70 - 0.85 | 相关，良好上下文匹配    | 包含        |
| 0.50 - 0.70 | 部分相关，可能包含有用信息 | 谨慎包含，考虑过滤 |
| 低于 0.50     | 弱相关或不相关       | 丢弃，不注入提示  |


设置最低相关性阈值（例如 0.55）防止智能体在其上下文中接收噪声。如果没有块通过阈值，智能体应承认它没有该信息，而不是用无关内容工作。

### 检索模式：相似度、混合与重排序


**三种检索方式**


基本向量相似度搜索是起点，但并不总是足够。不同的检索模式在精度、召回率和延迟之间做出不同权衡。


**1. 相似度搜索（仅向量）**


默认模式。嵌入问题，找到数据库中最接近的向量，返回 top-k 结果。


优势：捕捉语义含义。“How do I send back a product?” 匹配 “Return Policy”，即使词语不同。


劣势：错过精确关键词匹配。如果客户询问“model XR-7200”，而产品目录条目使用那个精确字符串，关键词匹配对此查询比语义相似度更可靠。


**2. 混合搜索（向量 + 关键词）**


结合向量相似度与传统关键词匹配（BM25 或全文搜索）。最终排名使用权重参数混合两种得分。


优势：同时捕捉语义匹配和精确关键词匹配。“model XR-7200 return policy” 既找到产品目录条目（型号关键词匹配）又找到退货政策（“return”语义匹配）。


劣势：需要维护两个索引（向量 + 文本）并调整它们之间的权重。


```python
def hybrid_search(question, vector_db, text_index, top_k=5, alpha=0.7):
    question_embedding = embed_text(question)
    vector_results = vector_db.query(vector=question_embedding, top_k=top_k * 2)

    keyword_results = text_index.search(question, top_k=top_k * 2)

    combined = merge_and_reweight(
        vector_results, keyword_results, alpha=alpha
    )

    return combined[:top_k]
```


alpha 参数控制混合。alpha=1.0 表示纯向量搜索。alpha=0.0 表示纯关键词搜索。0.6-0.7 的值对大多数应用效果良好，偏向语义理解同时保留关键词精度。


**3. 重排序（两阶段检索）**


检索更大的初始集（使用快速相似度搜索取 top 20-50 结果），然后应用更准确但更慢的交叉编码器模型对它们重排序。重排序后返回 top 3-5。


交叉编码器比余弦相似度更准确，因为它一起处理查询和每个候选块，而不是独立比较预计算向量。权衡：每次比较慢 10-50 倍，这就是为什么你将其应用于小型候选集而不是整个数据库。


优势：最高检索准确率。捕捉相似度搜索将某块排在第 12 位但它实际上最相关的情况。


劣势：增加 200-500ms 延迟。交叉编码器模型对每个候选对运行推理。


**何时使用每种模式**


| 模式   | 延迟            | 准确率     | 实现复杂度           | 最适合              |
| ---- | ------------- | ------- | --------------- | ---------------- |
| 仅相似度 | 低（50-100ms）   | 适合语义查询  | 低（单次向量查询）       | 通用问答、文档搜索        |
| 混合   | 中（100-200ms）  | 对混合查询强  | 中（两个索引，得分合并）    | 产品搜索、带代码/名称的技术文档 |
| 重排序  | 较高（300-600ms） | 整体准确率最高 | 较高（额外模型，两阶段流水线） | 高风险检索、法律、合规      |


**支持智能体的决策指南**


对于我们的客户支持智能体，混合搜索是正确的默认值。客户提到产品名称（“XR-7200”）、订单号和政策特定术语，这些受益于关键词匹配。他们也问模糊问题（“how do I send this back?”），需要语义理解。纯相似度搜索会错过关键词匹配。纯关键词搜索会错过语义匹配。混合两者兼得。


对于合规敏感查询（政策解释、退款资格），值得添加重排序，因为检索准确率直接影响智能体决策的正确性。对于简单 FAQ 查询，重排序的额外延迟不合理。

### 少样本示例作为上下文知识


**少样本：通过示例教学**


少样本提示在提示中提供示例输入-输出对，让大语言模型学习预期模式。你不是用抽象指令描述智能体应该如何响应，而是向它展示正确行为的具体示例。


**RAG vs 少样本：不同目的**


RAG 和少样本示例扮演根本不同的角色。RAG 提供事实：智能体回答问题所需的具体政策、产品详情、订单信息。少样本示例提供行为：智能体在应用那些事实时应遵循的格式、语气、推理方法。


| 维度     | RAG            | 少样本示例             |
| ------ | -------------- | ----------------- |
| 目的     | 提供模型没有的事实知识    | 教授行为模式（语气、格式、推理）  |
| 内容     | 文档、政策、产品数据     | 带理想响应的示例对话        |
| 随查询变化？ | 是（每个问题检索不同块）   | 否（跨查询使用相同示例）      |
| 提示中的位置 | 动态，每次查询注入      | 静态，系统提示或前缀的一部分    |
| 词元成本   | 可变（取决于块大小和数量）  | 固定（每次调用相同示例）      |
| 减少幻觉？  | 是（将响应基于检索到的事实） | 间接（向模型展示正确响应长什么样） |


**支持智能体的少样本**


```python
SUPPORT_AGENT_EXAMPLES = """
Example 1:
Customer: "I ordered shoes last week and they haven't arrived."
Agent thinking: Customer is asking about order status. I need to look up their order.
Agent action: order_lookup(customer_id)
Agent response: "I found your order. It shipped on [date] via [carrier] and is
expected to arrive by [date]. Here is your tracking number: [number]."

Example 2:
Customer: "I want to return the headphones I bought."
Agent thinking: Customer wants a return. I need to check the order date against
the return policy before processing.
Agent action: order_lookup(customer_id), then knowledge_search("return policy electronics")
Agent response: "I checked your order and our return policy. Your headphones were
purchased [X] days ago. [If within policy: I can process that return for you.]
[If outside policy: Unfortunately, our return window for electronics is 30 days,
and your purchase was [X] days ago. I can connect you with a specialist to discuss options.]"
"""
```


这些示例教智能体三件事：（1）始终在响应前查询数据，绝不猜测，（2）在采取行动前检查政策，（3）向客户清晰沟通发现了什么以及下一步是什么。示例是行为模板，不是事实内容。


**何时结合 RAG 和少样本**


最强的智能体两者都用。RAG 检索相关政策文档（“Electronics returns accepted within 30 days”）。少样本示例展示如何在客户交互中应用该政策（“检查订单日期，与政策窗口比较，清晰沟通结果”）。大语言模型同时拥有事实和行为模式，以产生正确、格式良好的响应。


```python
def build_agent_prompt(retrieved_chunks, few_shot_examples):
    return f"""You are a customer support agent.

{few_shot_examples}

Use the following context to answer the customer's question:
{retrieved_chunks}

Follow the same pattern shown in the examples above: look up relevant data,
reason through the applicable policy, then respond clearly to the customer.
"""
```


**词元预算考虑**


少样本示例是固定成本：无论查询如何，它们都包含在每个提示中。三个详细示例每个 300 词元，每次调用消耗 900 词元。对于每天进行 10,000 次调用的智能体，每天仅示例就花费 900 万词元。保持示例简洁。两到三个精心选择的示例比六个冗长的示例更有效。如果你的示例总计超过 1,000 词元，请精简它们。

> **提示：** 在讨论如何构建智能体知识系统时，同时提到 RAG 和少样本并解释区别。“我会使用 RAG 在查询时检索相关政策文档，并在系统提示中包含两到三个少样本示例，以教授智能体预期的响应格式和推理方法。”

### 何时使用 RAG vs 微调 vs 长上下文


**给大语言模型提供其没有的知识的三种方式**


当大语言模型需要其训练数据之外的信息时，你有三种架构选择。每种在成本、灵活性、准确率和维护方面做出不同权衡。


**选项 1：RAG（检索增强生成）**


在查询时检索相关文档并将其注入提示。模型本身不变。知识是外部的。


**选项 2：微调**


在你的特定数据上训练模型。知识被烘焙到模型权重中。模型本身被修改。


**选项 3：长上下文**


将所有内容放入提示。无检索，无训练。只需在每次调用中包含整个知识库。仅适用于小型知识库。


**对比**


| 维度      | RAG                 | 微调                | 长上下文             |
| ------- | ------------------- | ----------------- | ---------------- |
| 知识库大小   | 大（无限，外部存储）          | 中（受训练数据量限制）       | 小（必须适合上下文窗口）     |
| 更新速度    | 即时（更新文档，重新嵌入）       | 慢（重新训练模型，数小时到数天）  | 即时（更新提示内容）       |
| 每次查询成本  | 中等（嵌入 + 检索 + 大语言模型） | 每次查询低（模型已训练）      | 高（提示中每个词元都计费）    |
| 前期成本    | 低（嵌入文档一次）           | 高（训练计算、数据准备）      | 无                |
| 特定事实准确率 | 高（检索并引用精确文本）        | 可变（模型可能泛化或幻觉训练事实） | 高（精确文本在上下文中）     |
| 处理新信息   | 是（随时添加新文档）          | 否（需要重新训练）         | 是（添加到提示）         |
| 最适合     | 大型、变化的知识库           | 行为模式、领域特定语言、专门推理  | 小型、稳定参考资料（<50 页） |


**决策框架**


| 场景                  | 推荐方法      | 原因                |
| ------------------- | --------- | ----------------- |
| 5,000 篇 FAQ 文章，每月更新 | RAG       | 对上下文太大，更新太频繁不适合微调 |
| 教智能体用公司口吻写作         | 微调        | 行为模式，不是事实知识       |
| 10 页产品对比表           | 长上下文      | 足够小，可包含在每次提示中     |
| 法律合规政策（50+ 页，每季度更新） | RAG       | 大，需要准确检索，定期更新     |
| 领域特定医学术语            | 微调        | 基础模型不知道的语言模式      |
| 客户自己的订单历史           | RAG（从数据库） | 动态，每个客户唯一，不断变化    |


**为什么 RAG 通常是起点**


对大多数智能体系统，RAG 是正确的第一选择，原因有三：

- 无需修改模型。你使用相同基础模型，在外部添加知识。
- 更新即时。添加、修改或删除文档无需任何重新训练。
- 可扩展。知识库可以从 100 增长到 100,000 份文档而无需改变架构。

微调适用于问题是行为性的（模型需要以不同方式写作、以不同方式推理，或使用领域特定术语），而不是事实性的（模型需要知道具体事物）。区别很重要：你微调的是模型如何行为，你使用 RAG 的是模型知道什么。


**混合方法**


生产系统通常结合多种方法。RAG 用于事实知识检索。微调用于领域特定语气和术语。长上下文用于小型、关键参考资料（系统提示本身就是长上下文）。


示例：医疗支持智能体可能微调临床沟通模式（如何向患者解释病情），使用 RAG 检索特定药物信息和治疗指南，并在长上下文系统提示中包含一小组安全规则。

> 
>
> “会从 RAG 开始，因为它处理更新无需重新训练、可扩展到大型知识库，并保持模型通用。如果发现模型即使在良好提示和少样本示例后仍在领域特定语言或行为模式上挣扎，我会评估微调来填补那个特定差距。我会避免将微调作为第一步，因为它昂贵、训练后静态，并使模型对其他任务不那么灵活。”
>
>

### 完整示例，构建支持智能体的知识库


**知识来源**


我们的客户支持智能体需要访问四类知识：


| 来源      | 大小          | 更新频率         | 文档数量        |
| ------- | ----------- | ------------ | ----------- |
| FAQ 文章  | 总计约 100K 词元 | 每周           | 200 篇文章     |
| 退货和退款政策 | 总计约 30K 词元  | 每季度          | 4 份文档共 15 页 |
| 产品目录    | 总计约 500K 词元 | 每日（新产品、价格变化） | 5,000 个产品条目 |
| 配送文档    | 总计约 20K 词元  | 每月           | 8 页         |


总计：约 650K 词元的原始内容。这超过任何模型的上下文窗口（GPT-4o：128K，Claude：200K），所以长上下文不可行。RAG 是必要的。


**分块决策**


每种文档类型根据其结构获得不同的分块策略：


| 来源     | 策略        | 块大小            | 重叠     | 理由                    |
| ------ | --------- | -------------- | ------ | --------------------- |
| FAQ 文章 | 整篇文章 = 一块 | 100-500 词元（不定） | 无      | 每个 FAQ 是自包含的问答对       |
| 政策文档   | 在章节标题递归   | 512 词元         | 100 词元 | 政策有清晰章节结构（资格、时间范围、例外） |
| 产品目录   | 一个产品 = 一块 | 50-200 词元（不定）  | 无      | 每个产品是独立条目，包含名称、规格、价格  |
| 配送文档   | 在章节标题递归   | 512 词元         | 100 词元 | 与政策文档结构相似             |


**总块数估算**

- FAQ：200 块（每篇文章一块）
- 政策：约 80 块（30K 词元 / 512 带重叠）
- 产品：5,000 块（每个产品一块）
- 配送：约 50 块（20K 词元 / 512 带重叠）

总计：约 5,330 块需要嵌入和存储


按 text-embedding-3-small 每百万词元 $0.02 计算，嵌入 650K 词元成本约 $0.013。基本免费。每天重新嵌入整个知识库每年成本不到 $5。


**检索设计**


```plain text
检索配置：
  方法：混合搜索（向量相似度 + BM25 关键词匹配）
  Alpha：0.65（略微偏向语义，保留产品名称和订单术语的关键词精度）
  Top-k：3 块（平衡上下文质量与词元预算）
  最低相关性阈值：0.55（丢弃低相关性结果）
  元数据过滤：意图明确时将 FAQ 查询路由到 FAQ 块，产品查询路由到目录块
```


**检索的词元预算**


来自第 5 节，智能体在 128K 窗口中的上下文预算：


```plain text
系统提示：                   2,000 词元（固定）
少样本示例：                   900 词元（固定，3 个示例）
检索块（top 3）：            1,500 词元（可变，每块约 500）
对话历史：                   5,000 词元（增长，每轮约 500）
工具调用结果：               1,000 词元（可变）
大语言模型响应：               500 词元（输出）

每次交互总计：              ~10,900 词元
剩余上下文预算：            ~117,000 词元（充足余量）
```


在此使用水平下，智能体可以维持 200+ 轮对话，上下文压力才会成为问题。在实践中，支持对话平均 5-8 轮。


**完整查询演练**


客户：“Can I return the headphones I bought 2 weeks ago?”


```plain text
步骤 1：意图分类 → "return_request"
步骤 2：元数据过滤 → 搜索政策文档 + FAQ

步骤 3：混合搜索
  查询嵌入：embed("Can I return the headphones I bought 2 weeks ago?")
  BM25 关键词："return"、"headphones"、"2 weeks"

  结果：
    块 A（得分 0.91）："Electronics Return Policy: Electronics including
    headphones, speakers, and audio equipment may be returned within 30 days
    of purchase. Items must be in original packaging with all accessories."
    来源：return_policy_electronics.md，第 2 节

    块 B（得分 0.84）："Return Timeframes: Standard items: 60 days.
    Electronics: 30 days. Perishables: non-returnable. Custom orders:
    non-returnable. All returns require proof of purchase."
    来源：return_policy_general.md，第 1 节

    块 C（得分 0.72）："FAQ: How do I start a return? Contact our support
    team or visit any store location with your receipt. Online orders can
    initiate returns through your account dashboard."
    来源：faq_returns.md

步骤 4：将块 A、B、C 注入智能体提示
步骤 5：智能体推理（来自第 3 节的 CoT）：
  - 客户 2 周前买了耳机（14 天）
  - 电子产品退货窗口是 30 天
  - 14 天 < 30 天，所以退货符合条件
  - 商品类别：耳机 = 电子产品
  - 要求：原包装带配件

步骤 6：智能体响应：
  "您的耳机符合退货条件。我们的电子产品退货政策
  允许购买后 30 天内退货，您的订单在该
  窗口内。耳机需要保持原包装并包含
  所有配件。我现在可以为您开始退货流程，
  或者您可以通过账户仪表板发起退货。"
```


响应中的每个事实声明都基于检索到的块。智能体没有幻觉 30 天窗口或包装要求。如果政策下季度变为 14 天，更新文档并重新嵌入会即时更新智能体行为，无需任何代码更改或重新训练。

**覆盖的概念**


| 概念        | 一句话总结                              |
| --------- | ---------------------------------- |
| 嵌入        | 文本转换为数值向量；相似含义产生相似向量               |
| 分块        | 将文档拆分为检索单元；策略因文档类型而异               |
| 向量数据库     | 存储嵌入，支持大规模快速相似度搜索                  |
| 相似度搜索     | 找到向量最接近查询向量的块                      |
| 混合搜索      | 结合向量相似度与关键词匹配以获得更好覆盖               |
| 重排序       | 两阶段检索：快速初始搜索，用交叉编码器准确重排序           |
| 少样本示例     | 教授行为模式而非事实的示例输入-输出对                |
| RAG vs 微调 | RAG 用于事实知识（外部、可更新）。微调用于行为模式（模型修改）。 |


**常见错误**


| 错误                   | 为什么错                                                | 更好的回答                                        |
| -------------------- | --------------------------------------------------- | -------------------------------------------- |
| “我会在 FAQ 数据上微调模型”    | FAQ 数据变化频繁，微调是静态且昂贵的                                | “我会对 FAQ 数据使用 RAG，因为文章变化时即时更新，无需重新训练”        |
| “我会检索 top 20 块并全部包含” | 20 块在大部分无关内容上浪费约 10K 词元上下文                          | “我会检索 top 3-5 块并设置相关性阈值，丢弃低于 0.55 相似度的内容”    |

| 没有分块策略，嵌入整个文档        | 完整文档产生差检索，因为嵌入在太多内容上平均                              | “我会根据文档类型分块：FAQ 作为整篇文章，政策在章节标题拆分，目录作为独立产品条目” |
