> **Personal GPT Phase 2 · 系列第 7 篇** 

## 0. 背景


### 为什么要「预检索」


多专科图跑起来之前，服务端可以**先自己调用一次**与 `kb_search` 相同的 `invokeKbSearch`，把结果塞进一条 **`SystemMessage`****（系统侧消息，通常不直接展示给用户）**，标签类似「【知识库预检索·工具结果·可信】」。这里的「可信」指 **envelope（外壳：谁写的、状态行）** 来自服务端；snippet 正文仍是文档数据，不可当指令。


这样 Retriever 进场时，上下文里往往已经有 HIT 或 NO_HIT，不必完全赌「模型一定会先调工具」。


好处：减少「专科空转规划」、把 L0 压缩后的检索尽早做完、citation 卡片可以更早从预检索结果灌进 bag。


代价：多一次（有**等待**上限的）检索；闲聊或不涉 KB 的任务不应付这笔账——所以有开关条件。


**`Promise.race`** **≠ 取消任务（白话）**：8 秒超时只表示「服务端不等了、先带着空预取继续跑图」；底层 `invokeKbSearch` 可能仍在跑、仍耗资源。真正的 AbortSignal 取消是另一回事（本路径并未把 abort 一直传到向量库客户端）。


### 什么是 thread_id / run_id


LangGraph / 会话侧常用 **thread_id** 标识一条对话线程（**checkpointer** 会话存档、多轮记忆按它隔离——见第 11 篇）。


工具回调时，运行时会带一份 `configurable`（可含 `thread_id`、`workspaceId`、`userText` 等）。


坑在于：嵌套专科子图里，tool 经常**拿不到完整的** **`configurable.userText`**，但 `thread_id` / 请求级 id 往往还能传到。Phase 2 因此维护一张进程内 Map：按 id 存 `{ userText, workspaceId }`，供 `kb_search` 回退读取。


实现上，写入键用的是**每次请求的** **`runId`****（UUID）**，并放进 `configurable.run_id`；工具查找时**优先** **`run_id`****，再退回** **`thread_id`**。这样同一会话线程上两个并发请求，不会互相覆盖 KB 上下文或 web 配额计数。


**ANN**：向量库的近似最近邻搜索（见第 3 篇）；对每个请求都预检索 = 每次多付一次 embedding + ANN 账单。

## 1. 开场矛盾


只靠 Retriever「必须先调 kb_search」仍会遇到：

1. 模型先写一长段计划，迟迟不调工具；或调了但 query 乱改，丢掉用户原话里的专有名词。
2. 嵌套 Agent 的 tool 看不到 `userText`，L0 的「userText / condensed 回退」缺种子，长句 miss 更容易复发。
3. 若对每个请求都预检索，寒暄与纯联网题也付 embedding + ANN——和 Chat 路由要省的账单同类。

矛盾收束成两块工程：**按需预检索 + 按 run 注入上下文 Map（上限 256，结束清理）**。


## 2. 本篇目标


讲清服务端 KB 预检索触发条件、**8s 等待竞速**（`Promise.race` 只限制等待，**不 cancel** 底层检索）、`SystemMessage` 注入形态，以及按 `runId` 的上下文 Map（插入序淘汰上限 256，结束应 clear）。

## 3. 预检索与上下文


### 3.1 总览


| 层/部件                        | 做什么                            | 代价               | 代码入口           |
| --------------------------- | ------------------------------ | ---------------- | -------------- |
| `shouldPrefetchKb`          | 清单含 retriever 或话术像 KB          | 误触发时多一次检索        | §6.2           |
| `invokeKbSearch` + 8s race  | 进图前出 HIT/NO_HIT                | 超时则跳过预取          | §6.2           |
| `SystemMessage` 注入          | 强制专科采信预取结果                     | 多一段 system token | §6.2           |
| `kb-search-context` Map     | 按 runId 存 userText/workspaceId | 内存；漏清有上限         | §6.1           |
| tool 内 `userTextFromConfig` | configurable 优先，否则 Map         | 嵌套场景兜底           | kb-search.tool |


### 3.2 为什么要这么做


漏斗思维：能在服务端用**确定代码**完成的检索，就不要只靠模型「想起来调用」。


预取结果写成带硬标记的工具同款文本，与第 6 篇协议对齐——Retriever 看见预取 HIT 应直接复述 citation，而不是改口称未命中。


上下文 Map 解决的是框架传递缺口，不是业务新功能：没有它，workspace 过滤与 userText 回退在嵌套 tool 里会静默退化成「空 / default」。


### 3.3 优势


| 对比对象                       | 本方案优势                      |
| -------------------------- | -------------------------- |
| 完全信任 Retriever 自行检索        | 更早有可信 HIT/NO_HIT；轨迹可见「预检索」 |
| 每个请求都预取                    | 按意图/清单门控，省闲聊成本             |
| 只靠 configurable.userText   | 嵌套 tool 仍能拿到原话与 workspace  |
| 无上限 Map                    | 漏清时内存可被 256 顶住             |
| 用 thread_id 兼作配额键且无 run_id | 同线程并发会互相踩                  |


### 3.4 不做会怎么样


| 若取消…             | 会发生什么                                   |
| ---------------- | --------------------------------------- |
| 取消预检索            | 更依赖模型先调工具；citation 入袋更晚                 |
| 取消超时 race        | 向量慢时整请求卡死在进图前                           |
| 预取失败仍伪装 HIT      | 直接违反诚实协议                                |
| 取消上下文 Map        | 嵌套 kb_search 缺 userText/workspace 回退    |
| 不在 finally clear | Map 按唯一 runId 堆积（键不会自然碰撞成「串味」）；仍应清以免内存涨 |
| Map 无上限          | 异常路径漏清 → 内存涨                            |


### 3.5 原理小结（数据流）


```plain text
HTTP Agent 请求
  → runId = randomUUID()
  → setKbSearchContextForThread(runId, { userText, workspaceId })
  → configurable.run_id = runId（兼 workspaceId / userText）
  → 若 shouldPrefetchKb：
        extractKbSearchQuery(userText) → invokeKbSearch（≤8s）
        → SystemMessage(【知识库预检索·工具结果·可信】+ 报文)
        → 解析 citation / 置 kbNoRelevantHit
  → graph.stream({ messages: seededMessages })
  → 嵌套 kb_search：config 缺 userText 时 getKbSearchContextForThread(run_id)
  → finally：clearKbSearchContextForThread(runId)
```


一句话原理：**服务端先查一次并注入；用 run 级 Map 补上工具看不见的上下文。**

## 4. 方案取舍


| 方案                              | 优点     | 缺点 / 为何不选                     |
| ------------------------------- | ------ | ----------------------------- |
| 不做预取，只加强 Retriever prompt       | 实现少    | 空转与漏调用仍常见                     |
| 预取结果写进 HumanMessage             | 简单     | 易与用户话混淆；采信语义弱                 |
| Redis 存上下文                      | 多实例共享  | v2 单进程演示过重                    |
| **按需预取 + 进程内 Map + run_id（采用）** | 改动小、可测 | 多实例不共享 Map；靠 finally + 256 护栏 |


超时选 **8_000 ms**：超时返回 `undefined`，跳过注入，图仍继续——宁可少一次预取，也不阻塞整次演示。

## 5. 调用链


```plain text
agent.service execute
  → setKbSearchContextForThread(runId, …)
  → inferRequiredSpecialists → shouldPrefetchKb?
        yes → invokeKbSearch → SystemMessage 前缀 + lcMessages
        no  → 仅 lcMessages
  → supervisorGraph.stream(seededMessages, { configurable.run_id })
  → kbSearchTool → workspaceFromConfig / userTextFromConfig
        → 可回落 getKbSearchContextForThread(threadIdFromConfig)
  → finally clear*
```

## 6. 关键实现（完整核心）


### 6.1 按 thread/run 的上下文 Map


```typescript
/**
 * kb_search 按 thread_id 注入用户原话 / workspace。
 * 嵌套 Agent 的 tool 常拿不到完整 configurable.userText，但 thread_id 一般会传到。
 */
export type KbSearchContext = {
  userText?: string;    // L0 回退检索用的用户原话种子
  workspaceId?: string; // 向量检索的工作区过滤
};

/** 防漏清时无界增长；Map 保持插入序，超限淘汰最旧条目 */
export const MAX_KB_SEARCH_THREAD_CONTEXTS = 256;

const byThread = new Map<string, KbSearchContext>();

// 写入上下文；键实际是 runId（见 agent.service），同 thread 并发请求互不覆盖
export function setKbSearchContextForThread(threadId: string, ctx: KbSearchContext): void {
  if (!threadId?.trim()) return;
  const key = threadId.trim();
  if (byThread.has(key)) {
    byThread.delete(key); // 先删再写：刷新插入序（读不会刷新；不是严格 LRU）
  } else if (byThread.size >= MAX_KB_SEARCH_THREAD_CONTEXTS) {
    const oldest = byThread.keys().next().value;
    if (oldest !== undefined) byThread.delete(oldest); // 超 256 淘汰最旧
  }
  byThread.set(key, ctx);
}

// 请求结束 finally 里调用，防 Map 泄漏
export function clearKbSearchContextForThread(threadId: string): void {
  if (!threadId?.trim()) return;
  byThread.delete(threadId.trim());
}

export function getKbSearchContextForThread(threadId?: string): KbSearchContext {
  if (!threadId?.trim()) return {};
  return byThread.get(threadId.trim()) ?? {};
}
```


工具侧读取（概念对齐实现）：


```typescript
// 工具回调里解析「当前请求」的键：优先 run_id（并发隔离），再退回 thread_id
function threadIdFromConfig(config?: { configurable?: Record<string, unknown> }): string | undefined {
  const runId = config?.configurable?.run_id;
  if (typeof runId === "string" && runId.trim()) return runId.trim();
  const raw = config?.configurable?.thread_id;
  return typeof raw === "string" && raw.trim() ? raw.trim() : undefined;
}

// configurable 缺 userText 时，从进程内 Map 兜底（嵌套专科 tool 常见场景）
function userTextFromConfig(config?: { configurable?: Record<string, unknown> }): string | undefined {
  const fromCfg = config?.configurable?.userText;
  if (typeof fromCfg === "string" && fromCfg.trim()) return fromCfg.trim();
  return getKbSearchContextForThread(threadIdFromConfig(config)).userText;
}
```


### 6.2 按需预检索并注入 SystemMessage


```typescript
const runId = randomUUID(); // 每次 HTTP 请求独立 id，兼作 Map 键与 web 配额键

// 进图前先写入上下文，供嵌套 kb_search 回退读取
setKbSearchContextForThread(runId, {
  userText,
  workspaceId: parsed.workspaceId,
});

try {
  const required = inferRequiredSpecialists(userText); // 推断任务需要哪些专科

  // 按需预检索：清单含 retriever，或用户话术涉及知识库
  const shouldPrefetchKb =
    required.includes("retriever") ||
    /知识库|企业.?库|内部.?文档|\bkb\b|引用/.test(userText);

  let seededMessages = [...lcMessages];

  if (shouldPrefetchKb) {
    const KB_PREFETCH_TIMEOUT_MS = 8_000;
    // Promise.race 只限制「服务端等待」；超时后底层检索可能仍在跑
    const kbPrefetch = await Promise.race([
      invokeKbSearch({
        query: extractKbSearchQuery(userText),
        userText,
        workspaceId: parsed.workspaceId,
      }),
      new Promise<undefined>((resolve) => {
        const timer = setTimeout(() => resolve(undefined), KB_PREFETCH_TIMEOUT_MS);
        timer.unref?.(); // 不阻止 Node 进程退出
      }),
      // 另与 abortSignal 竞速：客户端断开则放弃预取
    ]);

    if (kbPrefetch) {
      trace.recordTool({
        name: "kb_search",
        agent: "system", // 预取由服务端发起，非专科节点
        summary: `预检索 ·${summarizeKbToolOutput(kbPrefetch)}`,
        detail: kbPrefetch,
      });
      // parseKbCitationsFromToolText → citationBag
      // NO_RELEVANT_HIT → tracker.kbNoRelevantHit = true

      // SystemMessage 插在用户消息前：专科进场时上下文已有 HIT/NO_HIT
      seededMessages = [
        new SystemMessage(
          [
            "【知识库预检索·工具结果·可信】",
            "以下由服务端直接调用 kb_search 得到；子 Agent 必须采信，禁止编造相反的命中/未命中结论。",
            kbPrefetch,
          ].join("\n"),
        ),
        ...lcMessages,
      ];
    }
    // kbPrefetch 为 undefined（超时/中断）→ 不注入，不假装命中
  }

  await supervisorGraph.stream(
    { messages: seededMessages },
    {
      configurable: {
        ...runConfig.configurable,
        run_id: runId, // 传给嵌套 tool，与 Map 键一致
        workspaceId: parsed.workspaceId,
        userText,
      },
    },
  );
} finally {
  clearKbSearchContextForThread(runId);
  clearWebSearchCallCount(runId); // 同 run 的 web 计数一并清理
}
```


要点：

- 预取 query 先走 `extractKbSearchQuery`；`invokeKbSearch` 内部仍可用 `userText` / condensed 回退（第 3 篇）。
- 超时或中断 → 不注入，不假装命中。
- 注入文案明确「可信 / 禁止编造相反结论」，与 Retriever prompt 的「已有预检索 HIT 则复述」对齐。

## 8. 如何验证


| 输入 / 条件                         | 期望                                |
| ------------------------------- | --------------------------------- |
| 多步清单含 retriever（如先查库再写报告）       | 轨迹有「预检索 · HIT/NO_HIT」；消息含【知识库预检索】 |
| 用户文案含「知识库」「引用」等                 | 即使清单推断不全，仍可能触发预取                  |
| 纯闲聊短路                           | 不进预取路径（route=short）               |
| 预取 >8s                          | 无注入；图仍继续                          |
| `set` 超过 256 个不同 key            | 最旧条目被淘汰（单测覆盖）                     |
| 请求结束                            | Map 中该 runId 被 clear；并发两请求互不覆盖配额  |
| 嵌套 tool 无 configurable.userText | 仍能经 run_id 读到原话做回退检索              |

## 9. 诚实边界

- 预取与专科再调 `kb_search` **可能重复付费**——换的是稳定性；未做「HIT 则禁止二次检索」的硬锁。
- 正则意图（`知识库|引用|…`）会误触发或漏触发；不是学习型路由。
- 进程内 Map **不跨多实例**；水平扩展要另设计（v2 不做）。
- `run_id` 优先解决并发；若调用链丢失 configurable，仍可能退回空上下文。
- 下一篇的待办/轨迹会展示预取与专科步骤，但 UI 不保证解释「为何跳过预取」。

---


## 10. 收束

1. 预检索把「第一次 KB 真相」提前到进图前，并用 SystemMessage 固定采信。
2. 按需门控避免寒暄也打向量库。
3. run 级上下文 Map 补上嵌套 tool 的配置缺口，256 + finally 防止泄漏。
4. 与第 3、6 篇合起来：压缩检索 → 硬标记协议 → 预取注入，才是 Agent 侧诚实 KB 的闭环。
