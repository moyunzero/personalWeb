## 1. 矛盾


产品早期常把两样东西塞进**同一个**向量 collection：

1. 用户刚上传的少量文档
2. 成千上万条心理学 QA / 提示词 seed（用来「空库也能聊两句」）

用 metadata（`source`、`documentId`）区分，实现成本最低。但 ANN 只认「谁离 query 向量近」——seed 数量级更大、句式更标准时，**泛化问法的 Top-K 经常被 seed 占满**。


表现很像玄学：入库日志显示 `ready`、chunk 也在，用户贴标题能问到，换种说法就只引用心理学问答。这是**召回层挤占**，不是「没切块」「没 embedding」。


本篇解决：路由已经决定 `retrieve` 之后，**怎么捞，才不让海量 seed 吞掉用户语料的席位。**


## 2. 本篇目标


给出可落地的双路策略：

- Path A：用户上传 / `prompt-suggestion`，门槛 **0.55**
- Path B：`psychology-qa` seed，门槛 **0.72**（更高，更难进最终列表）
- `mergeHits` 按 `(documentId, chunkIndex)` 去重，按相似度排序
- 最终 Top-N（默认 5）；合并后再做一次 top1 ≥ 0.55 的有效性检查

并说明 Multi-Query / HyDE / Reranker：**默认关闭**，与「要不要检」、「怎么展示引用」职责切开。


## 3. 双路是什么


### 3.1 总览：不是两次无关搜索，是一次合并席位分配


| 部件     | 做什么                                  | 代码入口                     |
| ------ | ------------------------------------ | ------------------------ |
| Path A | 只在用户语料里搜，threshold=0.55              | `USER_CORPUS_FILTER`     |
| Path B | 只在 psychology seed 里搜，threshold=0.72 | `SEED_PSYCHOLOGY_FILTER` |
| merge  | 去重 + 按 similarity 降序                 | `mergeHits`              |
| 可选增强   | 多查询 / HyDE / LLM 重排                  | `ENABLE_*`，默认 false      |
| 出门检查   | 合并后 top1 仍须 ≥ 0.55，否则 `no-docs`      | `passesTop1PreCheck`     |


对外仍是一个 `getRelevantContext` → `ok | no-docs | timeout | api-error`；citations 给第 3 篇的流末卡片。


### 3.2 为什么要分路，而不是「同一个 Top-K + 事后降权」？


单路全局 ANN 的数学事实是：**K 个名额是零和的。**


seed 向量更密、问法更「标准问答」时，用户文档就算相关，也可能排在第 6、第 7——而你只取 Top-5，它等于不存在。


事后在应用层「若 source=psychology 则 score×0.8」也行，但：

- 仍先浪费了 ANN 名额在 seed 上
- 系数难标，和门槛一样是经验活
- 无法表达「用户路允许 0.55，seed 路必须 0.72」这种**不对称资格**

分路的本质是：**先用 filter 把名额池拆开，再用不同门槛决定谁有资格进池，最后再合并竞争。**


```typescript
// Path A：用户文档（有 documentId）或 prompt-suggestion
const USER_CORPUS_FILTER = {
  $or: [
    { documentId: { $exists: true } },
    { source: { $eq: "prompt-suggestion" } },
  ],
} as const;

// Path B：仅心理学 seed
const SEED_PSYCHOLOGY_FILTER = { source: { $eq: "psychology-qa" } } as const;
```


注意：路由预检用的 `ROUTE_CORPUS_FILTER` 会把三类语料合在一起探测「库里有没有东西」；**真正检索**才拆成 A/B。预检负责「要不要检」，双路负责「检的时候别挤占」——两层阈值（0.68/0.42 vs 0.55/0.72）不要混谈。


### 3.3 为什么 seed 门槛更高（0.72 > 0.55）？


产品立场：

- 用户上传是「我显式交给系统的私有知识」→ 召回应更宽容（0.55）
- seed 是「兜底闲聊/示范」→ 只有**非常像**才允许进最终上下文（0.72），否则泛化情绪/心理问法会淹没用户文档

0.72 与 0.55 一样是**经验起点**，可用 env `SEED_CORPUS_SIMILARITY_THRESHOLD` 调；不是离线最优解。标定时应看 citation 的 `source` 分布，而不是只看平均相似度。


### 3.4 为什么还要 merge，而不是「用户路优先截断」？


有时问题确实该答 seed（用户库无关的心理常识）。粗暴「有用户命中就丢掉全部 seed」会误伤。


`mergeHits` 规则：

1. 键：`documentId:chunkIndex`
2. 同键保留更高 similarity
3. 全局按 similarity 降序，再 `slice(0, limit)`

这样 seed 仍可进前排，但必须先跨过更高门槛；用户路与 seed 路在最终列表里按分数说话，而不是按身份一刀切。


### 3.5 优势


| 对比对象                 | 双路方案的优势                                         |
| -------------------- | ----------------------------------------------- |
| **单路全局 Top-K**       | 用户语料有独立名额池；seed 不能靠数量霸榜                         |
| **物理分两个 collection** | 同库 metadata 即可；运维与 embedding 管线更简单（Phase 1 约束下） |
| **只靠 Reranker 纠偏**   | 不打开 LLM 也能止血；Rerank 仍可叠加，默认关省延迟                 |
| **永远禁用 seed**        | 空库/示范体验还在；只是进最终上下文更严                            |


### 3.6 不做会怎么样


| 若取消…                           | 会发生什么                                            |
| ------------------------------ | ------------------------------------------------ |
| **双路，退回单路 ANN**                | 泛化问法 citation 几乎全是 `psychology-qa`；用户文档「有时灵有时不灵」 |
| **两路同门槛 0.55**                 | seed 再次大量进最终 Top-N，分路名存实亡                        |
| **物理分库但检索忘加 filter**           | 等于没隔离；或漏查一路                                      |
| **只开 Reranker、不分路**            | 候选里若已无用户 chunk，重排无法「变出」未召回的文档                    |
| **query/passage embedding 混用** | 相似度刻度漂移，0.55/0.72 全部失真                           |
| **source 字符串与 filter 不一致**     | Path B 永远空；或用户文档进不了 Path A                       |


### 3.7 原理小结（数据流）


```plain text
getRelevantContext(query, workspaceId)
  → buildSearchQueries          // 默认 [query]；ENABLE_MULTI_QUERY 时 + 变体
  → for each q:
       buildEmbeddingInput      // 默认原句；ENABLE_HYDE 时换成假设段落
       embedQuery（input_type=query）
       searchWorkspace:
         Path A filter + thr=0.55
         Path B filter + thr=0.72
         mergeHits → slice(limit)
       merge 进总 hits
  → applyReranker               // 默认只截断到 5；开启则 LLM 重排
  → top1 < 0.55 ? no-docs : ok(context + citations)
```


一句话原理：**名额先按语料类型拆池，再用不同门槛发「入场券」，最后才在合并列表里按相似度排序——避免海量 seed 与少量用户文档抢同一张 Top-K 选票。**


## 4. 方案取舍


| 方案                          | 优点        | 缺点 / 为何不选（本期）            |
| --------------------------- | --------- | ------------------------ |
| 单路全局 ANN                    | 实现最短      | 易被大 seed 淹没              |
| 物理分库 / 分 collection         | 隔离强       | 双写、双配、迁移重                |
| **双路 filter + 分阈值 + merge** | 同库纠偏，改动面小 | 多一次 search；靠 metadata 约定 |
| BM25 / 混合检索                 | 关键词友好     | 引入 ES 等，留给 ISSUE / 后续里程碑 |
| 仅 Reranker                  | 语义重排      | 救不了「候选里没有用户文档」           |


可选增强默认全关：先让双路止血可观测，再按需打开成本更高的 LLM 路径。


## 5. 调用链


```plain text
路由已决定 retrieve
  →（可选）Multi-Query 变体
  →（可选）HyDE 假设段落
  → embedQuery
  → Path A / Path B 并行语义上的两次 search（代码顺序 await）
  → mergeHits
  →（可选）Reranker
  → passesTop1PreCheck
  → formatContextBlocks + mapDocsToCitations
  → 超时则 grace，再失败 → timeout / api-error
```


与第 2 篇关系：路由说 `retrieve` 只表示「值得检」；本篇仍可能返回 `no-docs`（合并后 top1 不够）。与第 3 篇关系：`citations` 的 `source` 字段，正是验证「有没有被 seed 挤占」的最好探针。


## 6. 关键实现（完整核心）


### 6.1 阈值与开关


```typescript
function readFloatEnv(name: string, fallback: number): number {
  const raw = process.env[name];
  if (!raw) return fallback;
  const value = Number.parseFloat(raw);
  return Number.isFinite(value) ? value : fallback;
}

/** 用户路门槛 + 最终 top1 有效性门槛 */
export const TOP1_SIMILARITY_THRESHOLD = 0.55;

/** seed 路更高门槛；可 env 覆盖 */
export const SEED_CORPUS_SIMILARITY_THRESHOLD = readFloatEnv(
  "SEED_CORPUS_SIMILARITY_THRESHOLD",
  0.72,
);

export const RETRIEVAL_LIMIT = 5;
export const RERANKER_CANDIDATE_LIMIT = 10;
export const RETRIEVAL_GRACE_MS = 10_000;

/** 显式 true 才开 —— 与双路止血解耦 */
export const ENABLE_HYDE = process.env.ENABLE_HYDE === "true";
export const ENABLE_MULTI_QUERY = process.env.ENABLE_MULTI_QUERY === "true";
export const ENABLE_RERANKER = process.env.ENABLE_RERANKER === "true";
```


### 6.2 Embedding：query / passage 必须分开


NIM embedqa 要求 `input_type`。在线检索与路由预检用 `query`；入库用 `passage`。混用会导致相似度刻度整体漂移，双路门槛失效。


```typescript
import { createOpenAICompatible } from "@ai-sdk/openai-compatible";
import { embed, embedMany } from "ai";

type NimInputType = "query" | "passage";

function createNimFetch(inputType: NimInputType) {
  return async (input: RequestInfo | URL, init?: RequestInit) => {
    if (init?.body && typeof init.body === "string") {
      const body = JSON.parse(init.body) as Record<string, unknown>;
      body.input_type = inputType;
      init = { ...init, body: JSON.stringify(body) };
    }
    return fetch(input, init);
  };
}

function createNimEmbeddingModel(inputType: NimInputType) {
  return createOpenAICompatible({
    name: "nim",
    baseURL: "<https://integrate.api.nvidia.com/v1>",
    apiKey: process.env.NIM_API_KEY!,
    fetch: createNimFetch(inputType),
  }).embeddingModel("nvidia/llama-nemotron-embed-1b-v2");
}

export async function embedText(text: string): Promise<number[]> {
  const { embedding } = await embed({
    model: createNimEmbeddingModel("query"),
    value: text,
  });
  return embedding;
}

export async function embedTexts(texts: string[]): Promise<number[][]> {
  if (texts.length === 0) return [];
  const { embeddings } = await embedMany({
    model: createNimEmbeddingModel("passage"),
    values: texts,
  });
  return embeddings;
}
```


### 6.3 双路搜索 + 合并


```typescript
interface RetrievedChunk {
  text: string;
  similarity: number;
  title?: string;
  source?: string;
  category?: string;
  documentId?: string;
  chunkIndex?: number;
  keywords?: string[];
}

interface VectorStore {
  search(params: {
    workspaceId: string;
    vector: number[];
    limit: number;
    similarityThreshold: number;
    filter?: Record<string, unknown>;
  }): Promise<RetrievedChunk[]>;
}

const USER_CORPUS_FILTER = {
  $or: [
    { documentId: { $exists: true } },
    { source: { $eq: "prompt-suggestion" } },
  ],
} as const;

const SEED_PSYCHOLOGY_FILTER = { source: { $eq: "psychology-qa" } } as const;

function hitKey(hit: RetrievedChunk) {
  return `${hit.documentId ?? "unknown"}:${hit.chunkIndex ?? 0}`;
}

function mergeHits(existing: RetrievedChunk[], incoming: RetrievedChunk[]) {
  const byKey = new Map<string, RetrievedChunk>();
  for (const hit of [...existing, ...incoming]) {
    const key = hitKey(hit);
    const prev = byKey.get(key);
    if (!prev || hit.similarity > prev.similarity) byKey.set(key, hit);
  }
  return [...byKey.values()].sort((a, b) => b.similarity - a.similarity);
}

async function searchWorkspace(
  store: VectorStore,
  workspaceId: string,
  vector: number[],
): Promise<RetrievedChunk[]> {
  const limit = ENABLE_RERANKER ? RERANKER_CANDIDATE_LIMIT : RETRIEVAL_LIMIT;

  const userHits = await store.search({
    workspaceId,
    vector,
    limit,
    similarityThreshold: TOP1_SIMILARITY_THRESHOLD,
    filter: USER_CORPUS_FILTER,
  });

  const seedHits = await store.search({
    workspaceId,
    vector,
    limit,
    similarityThreshold: SEED_CORPUS_SIMILARITY_THRESHOLD,
    filter: SEED_PSYCHOLOGY_FILTER,
  });

  return mergeHits(userHits, seedHits).slice(0, limit);
}
```


开启 Reranker 时先扩候选到 10，再压回 5，避免重排没有材料。


### 6.4 可选增强（默认关）与出门检查


```typescript
async function buildSearchQueries(query: string): Promise<string[]> {
  if (!ENABLE_MULTI_QUERY) return [query];
  const raw = await generateRagHelperText(
    "为用户问题生成 3 个简短的检索查询变体，每行一个，不要编号，不要解释。",
    query,
    0.2,
  );
  const variants = raw
    .split("\n")
    .map((line) => line.trim())
    .filter(Boolean)
    .slice(0, 3);
  return variants.length > 0 ? [query, ...variants] : [query];
}

async function buildEmbeddingInput(query: string): Promise<string> {
  if (!ENABLE_HYDE) return query;
  const hypothetical = await generateRagHelperText(
    "写一段能回答用户问题的简短假设性段落，只输出段落正文。",
    query,
    0.3,
  );
  return hypothetical || query;
}

function passesTop1PreCheck(hits: RetrievedChunk[]): boolean {
  return hits.length > 0 && hits[0]!.similarity >= TOP1_SIMILARITY_THRESHOLD;
}

async function applyReranker(query: string, hits: RetrievedChunk[]): Promise<RetrievedChunk[]> {
  const candidates = hits.slice(0, RERANKER_CANDIDATE_LIMIT);
  if (!ENABLE_RERANKER) return candidates.slice(0, RETRIEVAL_LIMIT);
  return rerankHitsWithLlm(query, candidates, RETRIEVAL_LIMIT);
}

declare function generateRagHelperText(
  system: string,
  user: string,
  temperature?: number,
): Promise<string>;

declare function rerankHitsWithLlm(
  query: string,
  hits: RetrievedChunk[],
  limit: number,
): Promise<RetrievedChunk[]>;
```


Reranker 失败时回退向量序（实现里 JSON 解析失败即 sort by similarity）——增强路径不能变成单点故障。


### 6.5 `getRelevantContext` 主流程（自洽版）


```typescript
export async function getRelevantContext(
  store: VectorStore,
  query: string,
  workspaceId: string,
): Promise<
  | { kind: "ok"; citations: Citation[]; blocks: string }
  | { kind: "no-docs" }
  | { kind: "timeout" }
  | { kind: "api-error"; error: unknown }
> {
  if (!workspaceId?.trim()) {
    throw new Error("getRelevantContext requires workspaceId");
  }
  if (!query) return { kind: "no-docs" };

  try {
    const searchQueries = await buildSearchQueries(query);
    let mergedHits: RetrievedChunk[] = [];

    for (const searchQuery of searchQueries) {
      const embeddingInput = await buildEmbeddingInput(searchQuery);
      const vector = await embedText(embeddingInput);
      const hits = await searchWorkspace(store, workspaceId, vector);
      mergedHits = mergeHits(mergedHits, hits);
    }

    mergedHits = await applyReranker(query, mergedHits);

    if (!passesTop1PreCheck(mergedHits)) {
      return { kind: "no-docs" };
    }

    return {
      kind: "ok",
      blocks: mergedHits.map((h) => h.text).join("\n\n"),
      citations: mergedHits.map((h) => ({
        documentId: h.documentId ?? "",
        title: h.title ?? "untitled",
        similarity: h.similarity,
        snippet: h.text.slice(0, 280),
        source: h.source,
        chunkIndex: h.chunkIndex,
      })),
    };
  } catch (error) {
    if (error instanceof Error && /timeout/i.test(error.message)) {
      return { kind: "timeout" };
    }
    return { kind: "api-error", error };
  }
}

interface Citation {
  documentId: string;
  title: string;
  similarity: number;
  snippet: string;
  source?: string;
  chunkIndex?: number;
}
```


生产实现里还有 `awaitSearchWithGrace`：主超时后宽限 `RETRIEVAL_GRACE_MS`，迟到结果仍可采用——检索抖动时少直接打脸。


## 7. 日志与可观测


最小字段（每次 retrieve）：


```typescript
type RetrieveLog = {
  requestId: string;
  workspaceId: string;
  hyde: boolean;
  multiQuery: boolean;
  reranker: boolean;
  hitCount: number;
  hits: { similarity: number; title?: string; source?: string }[];
};
```


调双路时重点看：

1. **citation** **`source`** **占比**：泛化问法下 `psychology-qa` 是否仍接近 100%
2. **用户文档问法**：Path A 是否经常进 top1
3. **把 seed 门槛从 0.72 降到 0.55**：seed 占比是否明显上升（用于证明门槛在干活）
4. **`no-docs`** **率**：过高可能是门槛过严，或 query/passage 混用导致刻度坏了

指标：`vector.search.ok` / `no_docs` / `timeout` / `api_error`（与聊天入口 telemetry 对齐）。


## 8. 如何验证


| 条件                                      | 期望                                           |
| --------------------------------------- | -------------------------------------------- |
| 同库：大量 psychology seed + 少量用户文档；泛化心理问法   | citation 不应**只**被 seed 占满到完全看不到用户路可能（对比单路基线） |
| 问用户文档标题/独特专有名词                          | 用户文档更容易进前排，`source` 非 psychology             |
| `SEED_CORPUS_SIMILARITY_THRESHOLD=0.55` | seed 进入最终 Top-N 变容易                          |
| `ENABLE_RERANKER=true`                  | 更准、更慢；候选先扩到 10                               |
| 入库 passage / 在线 query                   | 刻度稳定；乱混后门槛失效                                 |
| seed 的 `source` 写成别的字符串                 | Path B 空，行为异常                                |


## 9. 边界

- 这是**混库挤占的止血**，不是 BM25 / 多向量混合检索；极泛问法仍可能偏。
- 0.55 / 0.72 是经验值，换 embedding 模型必须重标。
- Path A 依赖 `documentId` 存在或 `prompt-suggestion`；元数据写错等于用户路消失。
- 两次 search 增加延迟与 Astra QPS；流量大时要盯。
- Multi-Query / HyDE 打开后会放大检索次数与费用，且可能把噪声问法一并放大。
- 双路不解决租户串数（那是第 5 篇 `workspaceId`）；也不解决向量半截写入（第 6 篇）。
- 路由预检仍可能因 seed 很像而判 `retrieve`，再在本层 `no-docs`——「该检」≠「检得到优质用户文档」。

## 10. 收束

1. **矛盾**：同库 seed 与用户文档抢 Top-K。
2. **做法**：分 filter、分门槛、再 merge。
3. **优势**：不动物理分库也能纠偏；Rerank 可叠加但非前提。
4. **不做**：单路淹没、同门槛假分路、只靠重排救召回。
5. **原理**：先拆名额池，再发入场券，最后按分排序。

复盘时把「现象 → 分路 → 门槛 → 合并 → 看 citation.source」串顺，比堆 HyDE/Rerank 名词更有用。
