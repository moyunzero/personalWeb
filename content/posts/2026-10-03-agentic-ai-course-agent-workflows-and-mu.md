### **第 7 节：智能体工作流与多智能体系统**


单个智能体会遇到极限。随着智能体处理范围的扩大，系统提示变得更长，工具集变得更大，大语言模型开始做出更差的决策，因为它试图同时做太多事情。多智能体系统通过将职责拆分给专门化的智能体来解决这个问题，这些智能体协作处理复杂任务。


本节覆盖何时将单个智能体拆分为多个智能体、主要的协调模式（监督者-工作者、编排者、点对点）、如何设计具有清晰边界的智能体角色，以及使多智能体系统比它们所替代的单个智能体更糟的常见错误。


**我们将覆盖的内容**

1. 什么时候单个智能体不够用
2. 监督者-工作者模式
3. 编排者与顺序流水线
4. 点对点智能体通信
5. 角色专门化与智能体设计
6. 错误 vs 正确：多智能体设计错误

**与前面章节的连接**


在第 3 节中，我们覆盖了单个智能体的执行模式：ReAct、提示链、路由器、反思。本节将这些模式扩展到多个智能体。监督者-工作者模式是一个路由器（第 3 节），其中每条路由是一个独立的智能体而不是一个独立的提示。编排者模式是提示链（第 3 节），其中每一步是一个独立的智能体而不是一次独立的大语言模型调用。如果第 3 节教会你一个智能体如何思考，本节教会你多个智能体如何协作。

### 什么时候单个智能体不够用


**你的单个智能体已经超出其设计的迹象**


当单个智能体有聚焦的范围、可管理的工具集和一致的行为期望时，它工作得很好。当其中任何一项扩展到单个系统提示和单个上下文窗口无法可靠处理的程度时，它就会崩溃。


| 信号               | 正在发生什么                   | 示例                                  |
| ---------------- | ------------------------ | ----------------------------------- |
| 系统提示超过 3,000+ 词元 | 智能体试图在一个提示中处理太多角色和规则     | 支持智能体提示覆盖订单查询、账单争议、技术故障排查、账户安全和产品推荐 |
| 行为要求冲突           | 不同任务需要不同语气、格式或决策风格       | 投诉需要正式谨慎，一般查询需要随意快速，故障排查需要技术精确      |
| 工具集超过 10-15 个工具  | 随着选项增多，大语言模型工具选择准确率下降    | 智能体拥有订单、退款、配送、账单、账户管理、产品搜索、库存、分析等工具 |
| 上下文窗口填满          | 一个智能体处理长对话和许多工具结果时工作记忆耗尽 | 故障排查会话有 8 次工具调用，每次返回大型 JSON 负载      |
| 错误隔离不可能          | 一个能力的失败拖垮整个智能体           | 账单 API 故障导致整个支持智能体失败，包括与账单无关的订单查询   |


**解决方案：专门化智能体**


将超载的智能体拆分为多个智能体，每个都有聚焦的系统提示、有限的工具集和清晰的范围边界。然后协调它们。


关键洞察：不要从多智能体开始。从单个智能体开始。只有当单个智能体因上述信号之一明显失败时才拆分。过早分解会增加协调开销，而没有解决真正的问题。

> **提示：** 如果要求你设计一个支持系统，从单个智能体开始，并解释何时以及为什么会拆分为多个智能体。

### 监督者-工作者模式


**如何工作**


监督者智能体接收每个传入请求，分类意图，并将其路由到适当的专门化工作者智能体。监督者不执行实际工作。它决定谁应该处理请求、委派、接收结果并将其返回给用户。


每个工作者有自己的系统提示、自己的工具和自己的行为规则。工作者彼此独立。


![%E6%88%AA%E5%B1%8F2026-10-05_20.06.01.png](images/blog/2026-10-03-agentic-ai-course-agent-workflows-and-mu/img-ddcfb98975.png)


**Python 实现**


```python
async def supervisor(user_message, customer_id):
    intent = await classify_intent(user_message)

    workers = {
        "order_status": OrderWorker(tools=[order_lookup]),
        "refund": RefundWorker(tools=[order_lookup, refund_process, knowledge_search]),
        "complaint": ComplaintWorker(tools=[escalate_to_human]),
        "general": GeneralWorker(tools=[knowledge_search])
    }

    worker = workers.get(intent, workers["general"])
    response = await worker.handle(user_message, customer_id)
    return response

async def classify_intent(message):
    response = await llm.chat(
        model="gpt-4o-mini",
        messages=[{
            "role": "system",
            "content": "Classify the customer message into one of: order_status, refund, complaint, general. Respond with only the category."
        }, {
            "role": "user",
            "content": message
        }],
        temperature=0
    )
    return response.content.strip()
```


注意两个设计决策。第一，监督者使用便宜、快速的模型（GPT-4o-mini）进行分类，因为意图分类是简单任务，不需要强大模型。第二，每个工作者只拥有与其角色相关的工具。投诉工作者无法访问 `refund_process`。订单工作者无法访问 `escalate_to_human`。这在工具层面强制了范围边界。


**何时使用监督者-工作者**


当请求属于清晰可分的类别，且每个类别需要不同工具、不同提示指令或不同行为规则时使用。监督者模式在路由决策直接（单个分类步骤）且每个任务完全由一个工作者处理时效果良好。


当单个任务需要多个工作者在同一请求上协作时，它效果不好。对于那种情况，使用编排者模式。

### 编排者与顺序流水线


**如何工作**


编排者定义一个多步骤工作流，其中多个工作者按顺序执行。每个工作者完成一步并将其输出传递给下一个工作者。编排者管理流水线：它知道步骤顺序，处理每个阶段的失败，并聚合最终结果。


与监督者的关键区别：监督者路由到一个工作者。编排者在同一请求上按顺序串联多个工作者。


![%E6%88%AA%E5%B1%8F2026-10-05_20.06.20.png](images/blog/2026-10-03-agentic-ai-course-agent-workflows-and-mu/img-babcb4b938.png)


**案例研究：客户投诉流水线**


客户发送一条关于缺陷产品的愤怒消息。这需要多个处理步骤，必须按顺序执行，因为每一步都依赖前一步的输出。


| 步骤 | 工作者    | 输入           | 输出            | 为什么顺序          |
| -- | ------ | ------------ | ------------- | -------------- |
| 1  | 严重性分类器 | 原始客户消息       | 严重性：高，类别：缺陷产品 | 必须先分类才能路由到正确政策 |
| 2  | 政策检索器  | 严重性 + 类别     | 相关退货/退款政策文本   | 必须知道类别才能检索正确政策 |
| 3  | 响应起草器  | 客户消息 + 政策文本  | 带退款提议的草稿响应    | 必须有政策才能起草准确响应  |
| 4  | 语气审查器  | 草稿响应 + 严重性级别 | 审查后的响应，调整同理心  | 必须有草稿才能审查      |


**Python 实现**


```python
async def complaint_pipeline(customer_message, customer_id):
    classification = await severity_worker.handle(customer_message)

    policy_context = await policy_worker.handle(
        category=classification["category"],
        severity=classification["severity"]
    )

    draft_response = await drafting_worker.handle(
        customer_message=customer_message,
        policy=policy_context,
        severity=classification["severity"]
    )

    final_response = await tone_worker.handle(
        draft=draft_response,
        severity=classification["severity"],
        target_tone="empathetic and professional"
    )

    return final_response
```


**何时使用编排者 vs 监督者**


| 维度   | 监督者-工作者          | 编排者                   |
| ---- | ---------------- | --------------------- |
| 路由   | 一个请求去一个工作者       | 一个请求流经多个工作者           |
| 依赖   | 工作者独立            | 每一步依赖前一步输出            |
| 用例   | 分类并分发            | 多步处理流水线               |
| 失败处理 | 如果选中的工作者失败，重试或升级 | 如果任何步骤失败，流水线停止（或跳过该步） |
| 延迟   | 一个工作者的处理时间       | 所有工作者处理时间之和           |
| 示例   | “这是退款还是订单查询？”    | “分类、检索、起草、审查”         |

> **提示：** 提出两种模式都可以工作的场景。强回答会说出两者并解释为什么选择其一。“我会在这里使用监督者模式，因为任务是独立的。如果随后添加一个要求，比如发送前进行质量审查，我会为那个后处理步骤加入编排者。”

### 点对点与智能体通信


**如何工作**


在点对点多智能体系统中，智能体直接相互通信，没有中央监督者或编排者。每个智能体可以向任何其他智能体发送消息、请求信息或委派子任务。


![%E6%88%AA%E5%B1%8F2026-10-05_20.06.40.png](images/blog/2026-10-03-agentic-ai-course-agent-workflows-and-mu/img-c8d1102e04.png)


**点对点在何时出现在生产中**


点对点在研发环境中常见，但在生产面向客户的系统中罕见。原因是可控性：当智能体在没有中央协调的情况下相互交谈时，调试失败很难，保证终止很难，确保一致行为很难。


| 方面   | 监督者/编排者                       | 点对点                                |
| ---- | ----------------------------- | ---------------------------------- |
| 控制流  | 中央协调者决定谁行动以及何时行动              | 智能体之间协商和委派                         |
| 可调试性 | 清晰轨迹：监督者路由到工作者 X，工作者 X 调用工具 Y | 复杂轨迹：智能体 A 问智能体 B，B 问智能体 C，C 循环回 A |
| 终止保证 | 协调者强制步骤限制                     | 循环委派风险（A 问 B，B 问 C，C 问 A）          |
| 灵活性  | 限于预定义路由或流水线步骤                 | 智能体可以动态决定涉及谁                       |
| 最适合  | 具有可预测任务流的生产系统                 | 探索性任务、研究、创意协作                      |


**真实世界示例**


编码助手是点对点类架构最常见的生产使用。一个规划智能体决定写什么代码，一个编码智能体写代码，一个测试智能体运行测试，如果测试失败，测试智能体将失败发送回编码智能体修复。智能体迭代直到测试通过或预算耗尽。


研究系统有时使用点对点：一个搜索智能体找到来源，一个阅读智能体提取关键信息，一个综合智能体合并发现，如果发现缺口则再次调用搜索智能体。


**实用建议**


对于设计问题，默认使用监督者-工作者或编排者。提到点对点作为探索性任务的选项，并解释为什么你不会将其用于生产支持系统：缺乏中央控制使得更难保证响应质量、强制时间预算和调试失败。

### 角色专门化与智能体设计


**什么构成设计良好的智能体角色**


多智能体系统中的每个智能体应满足三个标准：覆盖一个角色的聚焦系统提示、只包含与该角色相关工具的有限工具集，以及定义智能体接收什么和返回什么的清晰输入/输出契约。


**三个组成部分**


| 组件      | 它定义什么            | 示例（退款工作者）                                                                                               |
| ------- | ---------------- | ------------------------------------------------------------------------------------------------------- |
| 聚焦系统提示  | 一个角色、一个范围、一个行为画像 | “你是退款处理智能体。你验证退货资格并为符合条件的订单处理退款。”                                                                       |
| 有限工具集   | 智能体工作所需的工具       | `order_lookup`、`refund_process`、`knowledge_search`。无权访问 `escalate_to_human`（那是监督者的工作）。                  |
| 输入/输出契约 | 智能体接收什么，必须返回什么   | 输入：customer_id、user_message、intent_classification。输出：action_taken、response_text、escalation_needed（布尔值）。 |


**Python 示例：定义专门化工作者**


```python
class RefundWorker:
    def __init__(self):
        self.system_prompt = """
        You are a refund processing agent for TechStore.

        SCOPE: You handle refund requests ONLY. Do not answer general questions,
        order status inquiries, or complaints. If the request is outside your scope,
        return escalation_needed=True.

        PROCESS:
        1. Look up the order using order_lookup
        2. Check return eligibility using knowledge_search
        3. If eligible AND amount <= $50: process refund using refund_process
        4. If eligible AND amount > $50: return escalation_needed=True
        5. If not eligible: explain why and offer alternatives

        TOOLS AVAILABLE: order_lookup, refund_process, knowledge_search
        """

        self.tools = [order_lookup_schema, refund_process_schema, knowledge_search_schema]

    async def handle(self, user_message, customer_id):
        messages = [
            {"role": "system", "content": self.system_prompt},
            {"role": "user", "content": f"Customer{customer_id}:{user_message}"}
        ]
        return await run_agent_loop(messages, self.tools, max_steps=5)
```


**反模式：共享一切**


多智能体设计中最常见的错误是给每个智能体访问每个工具，并使用几乎相同的系统提示。这完全违背了拆分为多个智能体的目的。如果每个工作者都能做一切，你没有专门化。你只是复制了。


```plain text
坏的：三个“专门化”工作者都有 12 个工具，系统提示只在第一句不同。

好的：订单工作者有 2 个工具（order_lookup、knowledge_search）。
      退款工作者有 3 个工具（order_lookup、refund_process、knowledge_search）。
      投诉工作者有 1 个工具（escalate_to_human）。
      每个系统提示定义一个工作及其边界。
```


测试：如果你移除一个工作者，将其系统提示和工具分发给另一个工作者，会有什么变化吗？如果没有，那两个工作者应该是一个智能体。

### 错误 vs 正确，多智能体设计错误


**错误 1：过早拆分**


错误：为一个处理 3 种请求类型的系统从 5 个智能体开始。协调开销（监督者分类、智能体间通信、共享状态管理）增加延迟和复杂度，没有任何好处。


正确：从单个智能体开始。监控它在哪里失败。只有当系统提示变得过载、工具冲突或达到上下文限制时才拆分。第一次拆分通常是 2-3 个智能体，而不是 10 个。


**错误 2：没有真正的专门化**


错误：三个工作者共享相同工具和几乎相同的提示。每个工作者“可以”处理任何事情，所以监督者的路由决策无关紧要。


正确：每个工作者有聚焦的范围、不同的工具，以及只覆盖其职责的系统提示。从一个工作者移除一个工具并专门给另一个，是专门化的具体测试。


**错误 3：没有协调者**


错误：存在多个智能体但没有一个协调。应用代码有硬编码的 if/else 路由。添加新智能体类型需要代码变更。


正确：监督者或编排者智能体动态处理路由。添加新工作者意味着添加新意图类别和新工作者，而不是重写路由逻辑。


**错误 4：单个智能体能工作时使用多智能体**


错误：为一个只处理简单 FAQ 查询的系统构建带 3 个工作者的监督者。分类、路由和协调的开销远超收益。


正确：一个带有干净系统提示和 3-4 个工具的单个智能体高效处理简单、定义良好的任务。多智能体是扩展解决方案，不是默认架构。


**决策框架**


| 你的情况                      | 推荐架构         | 原因                       |
| ------------------------- | ------------ | ------------------------ |
| 1-3 种任务类型，共享工具，一致行为       | 单个智能体        | 无需专门化。协调开销不合理。           |
| 3-6 种任务类型，每种类型不同工具，不同行为需求 | 带专门化工作者的监督者  | 清晰路由、聚焦智能体、隔离失败。         |
| 具有顺序依赖的多步任务               | 编排者流水线       | 每一步有不同工作，输出流向下一步。        |
| 动态、探索性任务，需要迭代协作           | 点对点（带循环预算）   | 智能体需要协商和迭代。添加严格终止条件。     |
| 发送前需要质量审查的简单任务            | 单个智能体 + 反思步骤 | 不要为自我纠正循环能处理的事情构建多智能体系统。 |

### 本节速查表


**覆盖的概念**


| 概念      | 一句话总结                           |
| ------- | ------------------------------- |
| 何时拆分    | 系统提示过载、行为冲突、工具冲突、上下文限制。只在被迫时拆分。 |
| 监督者-工作者 | 监督者分类意图并路由到一个专门化工作者。工作者独立。      |
| 编排者     | 按顺序串联多个工作者。每一步依赖前一步输出。          |
| 点对点     | 智能体直接通信，无中央协调。灵活但难控制。生产中罕见。     |
| 角色专门化   | 每个智能体：聚焦提示、有限工具、清晰输入/输出契约。      |
| 决策框架    | 单个智能体优先。路由用监督者。流水线用编排者。探索用点对点。  |


**常见错误**


| 错误                 | 为什么错                             | 更好的回答                                                 |
| ------------------ | -------------------------------- | ----------------------------------------------------- |
| “我会构建多智能体系统”（作为默认） | 多智能体增加协调开销。除非单个智能体失败，否则不合理。      | “我会从单个智能体开始，如果系统提示超过 3,000 词元或工具选择准确率下降，再拆分为监督者-工作者。” |
| 给每个工作者所有工具         | 违背专门化。工具越多，大语言模型选择准确率越低。         | “每个工作者只有它需要的工具。退款工作者有 3 个工具。投诉工作者有 1 个。”              |
| 没有监督者或编排者          | 没有协调，智能体无法管理、监控或调试。              | “监督者处理路由并强制终止。每个请求有一个入口点。”                            |
| 混淆监督者与编排者          | 它们解决不同问题。监督者路由到一个工作者。编排者串联多个工作者。 | “监督者用于分发到独立处理器。编排者用于步骤相互依赖的顺序流水线。”                    |


**需要记住的关键术语**


```plain text
监督者：       根据意图分类路由到一个工作者
```
