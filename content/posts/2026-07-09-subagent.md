### Subagent 解决什么问题？


复杂任务往往包含多种子工作：写新功能、审查代码、搜索历史实现、补测试等。


全塞进一个窗口 → 上下文快速膨胀，AI 容易忘记约束、绕圈修改、输出质量下降。


**Subagent 的核心价值**：**隔离上下文**。


主 Agent 负责决策和核心实现；需要搜索、审查、测试时，派 Subagent 出去独立完成，只把结论带回。这样主 Agent 的上下文保持干净。


比喻：主 Agent 是项目经理，Subagent 是各工种工人。经理只需知道结果，不用全程关注细节过程。


### 实战案例：重构列表组件


任务：将列表组件拆分成多个小组件。

- **主 Agent**：负责写新组件、调整数据流、保证整体功能。
- **Search Agent**：在 codebase 中搜索类似拆分案例和数据传递方式，只返回清单（不污染主上下文）。
- **Review Agent**：独立审查 diff，检查 props 传递、性能问题、命名风格（无“自己写自己审”的心理包袱）。
- **Test Agent**：针对改动补充测试，重点覆盖边界情况。

各 Agent 上下文独立，最终只把关键结论汇总到主流程。


### Subagent 适用场景


**适合派出去的**：

- 大范围搜索（找所有使用旧 API 的地方）
- 独立探索（研究第三方库最佳实践）
- 并行子任务（同时为多个模块写测试）
- 重复机械活（全局替换 console.log）
- 验证类工作（跑测试、判断结果）

**不适合派出去的**：

- 需要主会话历史上下文的任务
- 极小的简单任务（开销不值）
- 需要反复交互确认的任务

### 如何写好 Subagent 指令


Subagent 是一次性任务，指令要**明确、结构化**，像写函数调用一样。


示例：

> 在 src/ 下找所有直接调用 process.env 的地方。
>
> 输出格式：每行 path:line + 使用的变量。
>
>
> 不要修改任何文件，不要进入 node_modules。
>
>
> 完成标准：输出列表 + 总数。
>
>

指令越清晰，结果越可直接使用。


### 预配置 Subagent


常用类型可预定义：

- [code-reviewer.md](http://code-reviewer.md/)（专注审查）
- [explore.md](http://explore.md/)（大范围只读探索）
- [test-writer.md](http://test-writer.md/)（专写测试）

在工具对应目录（如 `.claude/agents/` 或 `.cursor/agents/`）定义角色、可用工具和 System Prompt，主 Agent 可按名快速调用。


### 与前文串联


Subagent 是**上下文管理的自然延伸**：把会膨胀的内容赶到子代理去，只带回精炼结论。
