### **第 3 节：智能体架构与执行模式**


在构建工具、RAG 流水线或记忆系统等单个组件之前，你需要先看清智能体如何组织、如何执行的完整图景。本节覆盖智能体执行的主要架构模式。每种模式都在控制力、灵活性和可靠性之间做出不同权衡。


**我们将覆盖的内容：**

- 确定性工作流 vs 自主智能体
- ReAct 模式（推理 + 行动）
- 思维链作为一种推理技术
- 提示链与顺序工作流
- 路由与分发器模式
- 反思与自我纠正
- 为正确的问题选择正确的模式

**这在客户支持智能体中的位置：**


我们正在构建的客户支持智能体需要一个执行模式。智能体应该对每一条客户消息都遵循固定步骤序列吗？它应该自己决定下一步做什么吗？不同类型的消息应该交给不同处理器吗？本节的模式回答这些问题。到最后，你会知道哪种模式适合我们的支持智能体，以及为什么。

### 确定性工作流 vs 自主智能体


**一个光谱的两端**


每个智能体系统都位于从完全确定性到完全自主的光谱上的某个位置。理解你的系统应该位于哪里，是你将做出的最重要的架构决策之一。


**确定性工作流**


开发者提前定义每一步。大语言模型执行每一步，但它不决定下一步做什么。步骤 1 总是通向步骤 2，步骤 2 总是通向步骤 3。序列在开发时固定。

- 可预测：相同输入每次都产生相同流程
- 可测试：每一步都可以独立测试
- 受限：无法适应意外输入或新情况

**自主智能体**


大语言模型根据观察到的内容决定下一步做什么。它可以选择调用哪些工具、以什么顺序调用、以及何时停止。开发者定义能力和边界，而不是序列。

- 灵活：无需修改代码即可适应新情况
- 强大：处理复杂、多步骤、路径可变的任务
- 有风险：可能进入无限循环、做出意外决策，且更难测试

**生产现实**


大多数生产 AI 系统更接近工作流，而不是完全自主智能体。完全自主听起来很厉害，但会引入难以调试、测试和向利益相关者解释的不可预测性。


| 维度     | 确定性工作流       | 自主智能体          |
| ------ | ------------ | -------------- |
| 步骤序列   | 由开发者固定       | 由大语言模型在运行时决定   |
| 可预测性   | 高            | 低              |
| 可测试性   | 每一步可独立测试     | 只能端到端测试        |
| 灵活性    | 低（遇到意外输入会崩溃） | 高（适应新输入）       |
| 调试     | 容易（追踪每个固定步骤） | 困难（大语言模型决策不透明） |
| 无限循环风险 | 无            | 真实存在（需要循环预算）   |
| 生产就绪度  | 高            | 需要大量护栏         |
| 最适合    | 已知、可重复流程     | 探索性、可变任务       |


**光谱**


大多数生产系统位于提示链和路由之间。没有护栏的完全自主智能体几乎从不适合生产。即使是 Google 和 Amazon 这样大规模部署智能体的公司，也使用受控工作流，只在特定决策点拥有自主性，而不是端到端自主。

> 
>
> **提示：** 问“你会为 X 构建自主智能体吗？”，强回答是：“这取决于任务的可变性。对于订单履行这样的固定流程，确定性工作流更可靠。对于开放式故障排查，我会使用带步骤预算和明确终止条件的受控 ReAct 循环。”

### 实践中的 ReAct 模式


**ReAct：推理与行动交错**


ReAct 是研究和生产中最广泛引用的智能体模式。智能体在思考（推理该做什么）和行动（调用工具或生成回复）之间交替。每次行动后，智能体观察结果并再次推理。循环持续，直到智能体有足够信息给出最终答案，或直到触发终止条件。


**循环**


循环持续，直到智能体确定它有足够信息回复，或直到触发终止条件（循环预算、时间限制、词元限制）。


**完整轨迹：客户支持示例**


客户：“我的订单 #4821 在哪里？”


```plain text
思考 1：客户想要订单状态。我需要查询订单 #4821。
行动 1：order_lookup(order_id="4821")
观察 1：{"status": "shipped", "carrier": "FedEx", "tracking": "FX789012", "eta": "Dec 15"}

思考 2：订单已通过 FedEx 发货。我有跟踪号和预计送达时间。
        我可以给客户完整答复，无需进一步查询。
行动 2：回复客户

回复：“您的订单 #4821 已通过 FedEx 发货。您的跟踪号是
      FX789012，预计送达日期是 12 月 15 日。”
```


这个轨迹花了 2 个推理步骤和 1 次工具调用。更复杂的问题，比如排查损坏商品，可能需要 5-8 步：查询订单、检查保修状态、检索退货政策、验证客户地址，然后处理退货。


**Python 实现**


```python
def react_loop(user_message, tools, max_steps=10):
    context = [{"role": "user", "content": user_message}]

    for step in range(max_steps):
        response = llm.chat(
            system=AGENT_SYSTEM_PROMPT,
            messages=context,
            tools=tools
        )

        if response.has_tool_call:
            tool_name = response.tool_call.name
            tool_args = response.tool_call.arguments
            result = execute_tool(tool_name, tool_args)
            context.append({"role": "assistant", "content": response.reasoning})
            context.append({"role": "tool", "content": result})
        else:
            return response.content

    return "我无法完全解决此问题。让我为您连接专家。"
```


注意 `max_steps=10` 参数。这是循环预算。没有它，困惑的智能体可能永远循环，消耗词元且永不回复。末尾的回退消息是优雅降级，而不是崩溃。


**何时使用 ReAct**

- 步骤数量事先未知
- 下一个行动取决于上一个行动的结果
- 任务需要探索（故障排查、研究、多步调查）

**何时不使用 ReAct**

- 任务有固定、已知的步骤序列（改用提示链）
- 任务是简单分类或路由决策（改用电由器）
- 延迟至关重要，每个推理步骤都会增加 1-2 秒延迟

**真实世界规模**


Anthropic 的 Claude 和 OpenAI 的 GPT 都通过工具调用 API 原生支持 ReAct 模式。当你用工具定义调用 API，模型决定调用工具时，它会生成结构化工具调用，等待结果，然后继续推理。Intercom 和 Zendesk 等公司的客户支持智能体使用 ReAct 的变体来处理需要查询数据、应用政策和生成回复的工单，通常每个工单在 2-4 个推理周期内完成。

### 思维链作为推理模式


**思维链（CoT）：一步一步思考**


思维链提示 instructs 大语言模型在给出最终答案前逐步展示推理。模型不是直接跳到结论，而是明确地解决问题。这不是一种独立架构。它是一种可以在任何架构内部使用的推理技术。


**为什么它对智能体重要**


复杂的智能体决策需要多步推理。智能体应该升级此问题吗？此退款符合条件吗？此客户的请求需要经理批准吗？没有 CoT，模型会跳到答案，可能跳过关键检查。有了 CoT，它会明确地按标准逐步处理，从而产生更准确的决策，并创建可审计轨迹，供出错时审查。


**没有 CoT**


客户：“我想为我 2 个月前买的笔记本电脑退款。”


智能体回复：“退款已批准。”


这是错误的。智能体跳过了所有政策检查，批准了可能违反退货政策的退款。没有推理轨迹解释为什么批准。


**有 CoT**


客户：“我想为我 2 个月前买的笔记本电脑退款。”


智能体推理：

- 订单大约在 60 天前下单。
- 我们的退货政策允许电子产品在 30 天内退货。
- 60 天超过了 30 天退货窗口。
- 该商品属于“电子产品”类别，没有延长退货窗口。
- 决策：根据标准政策，退款不符合条件。
- 我应该告知客户并提供替代方案。

智能体回复：“我根据我们的退货政策检查了您的订单。很遗憾，电子产品购买可在 30 天内退货，而您的购买大约在 60 天前。我可以帮您探索保修选项，或为您连接专家进一步讨论您的情况。”


推理明确、可审计且正确。如果智能体出错，你可以准确追踪推理在哪里出错。


**CoT vs ReAct：区别是什么？**


| 维度     | 思维链（CoT）           | ReAct            |
| ------ | ------------------ | ---------------- |
| 它做什么   | 逐步推理，然后回答          | 推理、行动、观察、重复      |
| 外部行动   | 无（仅推理，无工具调用）       | 有（在推理步骤之间调用工具）   |
| 推理发生时机 | 在答案前一次性完成          | 与行动和观察交错         |
| 用例     | 基于已在上下文中的信息做复杂决策   | 需要外部数据或行动的任务     |
| 示例     | “此退款符合条件吗？”（政策已检索） | “查询订单、检查政策、处理退款” |
| 延迟     | 一次大语言模型调用          | 多次大语言模型调用 + 工具调用 |


**关键洞察**


CoT 和 ReAct 不是替代关系。它们是互补的。ReAct 智能体在每个推理步骤内部使用 CoT。当智能体在工具调用之间暂停思考时，那种思考就是思维链推理。最强的智能体结合两者：CoT 用于每个单独决策，ReAct 用于整体任务执行流。把它们看作工具箱中的两个独立工具，而不是两个竞争选项，才是正确的心智模型。

> **提示：** 在讨论推理时，区分“我会在单个步骤内使用思维链做退款资格决策”和“我会为涉及查询、政策检查和行动的整体客户交互使用 ReAct”。

### 提示链与顺序工作流


**提示链：将复杂任务拆成简单步骤**


提示链将复杂任务拆成一系列更简单、更聚焦的大语言模型调用。步骤 1 的输出成为步骤 2 的输入。每一步做好一件事，并使用针对该单一任务优化的特定系统提示。


**为什么用链而不是一个大提示？**


一个提示说“阅读此客户投诉、分类其严重性、查询相关政策、起草回复并检查语气”，是在要求大语言模型同时做五件事。随着同时目标数量增加，大语言模型表现会下降。提示链让每一步成为聚焦、可测试的大语言模型调用，只有一个指令和明确成功标准。


**示例：客户投诉流水线**


步骤 1：分类投诉严重性（低、中、高、严重）
步骤 2：起草与严重性级别相称的回复
步骤 3：根据语气指南检查起草的回复，必要时修订


每一步都是独立的大语言模型调用，带有聚焦提示。如果步骤 2 生成差草稿，步骤 3 会抓住它。如果你需要调试为什么客户收到错误语气，可以独立检查每一步的输入和输出。


**Python 实现**


```python
def complaint_pipeline(customer_message):
    severity = llm.chat(
        system="Classify the severity of this customer complaint. "
               "Return exactly one of: low, medium, high, critical. "
               "No explanation, just the classification.",
        messages=[{"role": "user", "content": customer_message}]
    )

    draft = llm.chat(
        system=f"Draft a customer support response for a{severity} severity "
               f"complaint. Be empathetic and solution-oriented. Keep the "
               f"response under 150 words.",
        messages=[{"role": "user", "content": customer_message}]
    )

    final = llm.chat(
        system="Review this draft customer support response. Check that the "
               "tone is professional and empathetic. Check that it does not "
               "promise anything outside policy. If it needs adjustment, "
               "return the revised version. If it is acceptable, return it "
               "unchanged.",
        messages=[{"role": "user", "content": draft}]
    )

    return final
```


**提示链的特征**


| 特征   | 细节                              |
| ---- | ------------------------------- |
| 步骤序列 | 固定，由开发者在构建时定义                   |
| 步骤依赖 | 步骤 N 的输出是步骤 N+1 的输入             |
| 故障隔离 | 如果步骤 2 失败，步骤 1 和 3 不受影响         |
| 可测试性 | 每一步可独立单元测试                      |
| 灵活性  | 低：运行时不能跳过步骤或改变顺序                |
| 延迟   | 累加：总延迟 = 所有步骤延迟之和               |
| 成本   | 每一步是独立大语言模型调用（3 步 = 单次调用 3 倍成本） |
| 最适合  | 已知、可重复的多步流程                     |


**何时使用提示链**

- 任务有已知步骤序列，且不根据中间结果改变
- 每一步都受益于聚焦、具体的提示
- 你需要每个阶段的可测试性和可调试性
- 示例：内容审核流水线、文档处理、报告生成、客户投诉处理

**何时不使用**

- 下一步取决于当前步骤中发现的内容（使用 ReAct）
- 任务类型变化，不同输入需要不同处理路径（使用路由器）
- 任务简单到单次大语言模型调用就能处理得很好

**提示链 vs ReAct**


关键区别：在提示链中，开发者在构建时决定序列。在 ReAct 中，大语言模型在运行时决定序列。如果你的流程无论输入内容如何都总是遵循相同步骤，使用链。如果路径根据中间结果改变，使用 ReAct。

### 路由与分发器模式


**路由器：分类一次，分发到正确处理器**


路由器读取传入消息，分类意图，并分发到适当的专用处理器。没有顺序链。路由器做单个决策：哪个处理器应该处理此请求？


**模式**


路由器可以是大语言模型调用（“将意图分类为这些类别之一”）或传统机器学习分类器（更快、更便宜、更确定性）。下游每个处理器本身可以是不同智能体，拥有自己的系统提示、提示链，甚至 ReAct 循环。路由器不关心每个处理器内部发生什么。它只负责分发。


**Python 实现**


```python
INTENT_HANDLERS = {
    "order_status": handle_order_query,
    "refund_request": handle_refund,
    "complaint": handle_complaint,
    "general_question": handle_faq,
}

def route_message(customer_message):
    intent = llm.chat(
        system="Classify the customer's intent into exactly one of: "
               "order_status, refund_request, complaint, general_question. "
               "Return only the classification label, no explanation.",
        messages=[{"role": "user", "content": customer_message}]
    )

    handler = INTENT_HANDLERS.get(intent.strip(), handle_faq)
    return handler(customer_message)
```


注意回退：`INTENT_HANDLERS.get(intent.strip(), handle_faq)`。如果大语言模型返回意外分类（偶尔会发生），请求会落到通用 FAQ 处理器，而不是崩溃。始终为分类产生意外值的情况做设计。


**路由器设计决策**


| 决策    | 选项                              | 权衡                                              |
| ----- | ------------------------------- | ----------------------------------------------- |
| 路由器实现 | 大语言模型（GPT-4o-mini） vs 传统机器学习分类器 | 大语言模型：灵活、处理边缘情况、较慢。分类器：更快（5ms vs 500ms）、更便宜、确定性 |
| 类别数量  | 4-6 个类别 vs 20+                  | 更少：分类准确率更高。更多：路由更细，误分类风险更高                      |
| 回退处理  | 默认类别 vs 升级到人工                   | 默认：总能处理（可能处理不好）。升级：捕捉不确定情况                      |
| 置信度阈值 | 任意分类都路由 vs 要求高置信度               | 低阈值：解决更快。高阈值：路由更准确，一些消息需要重新路由                   |


**路由器 vs 提示链：何时使用哪个**


路由器和提示链解决不同问题。提示链通过多个步骤处理一种请求类型。路由器通过将每种请求发送到正确处理器来处理多种请求类型。它们自然组合：路由器分发到处理器，每个处理器可以是提示链。


```plain text
客户消息 -> 路由器 -> "refund_request" -> 退款处理器（提示链）：
                                            步骤 1：验证订单
                                            步骤 2：检查资格
                                            步骤 3：处理退款
```


**何时使用路由器**

- 任务类型变化，但每种类型都有定义良好的处理路径
- 不同意图需要不同工具、提示或处理逻辑
- 你想隔离关注点（退款逻辑与投诉处理分离）
- 你需要为不同复杂度使用不同模型

**真实世界规模**


大多数生产客户支持系统使用路由器作为入口点。Zendesk 的 AI 将传入工单分类后再路由到专用工作流。Amazon 的客户服务在订单问题、退货、账户问题和一般咨询之间路由。路由器模式可扩展，因为每个处理器可以独立开发、测试和部署。

> **提示：** 在系统设计中，路由器模式通常是面向客户智能体的最强起点。它给你清晰的关注点分离、每个意图的独立可测试性，以及为每个类别使用不同模型或提示的能力。从这里开始，只有当路由器不足时才转向更复杂的模式。

### 反思与自我纠正模式


**反思：智能体评估自己的输出**


反思在生成后添加自评估步骤。智能体产生回复，然后单独评估检查该回复是否满足定义的质量标准。如果不满足，智能体修订。这不是“要求大语言模型更努力”。评估器使用明确、可测试的标准。


**评估器-优化器循环**


该模式有两个角色：

- 生成器：基于任务和上下文产生初始回复
- 评估器：根据定义标准检查回复并提供具体反馈

如果评估器拒绝，生成器将反馈包含在内再次尝试。


评估器的标准必须具体且可检查。“这个回复好吗？”不是有用的评估标准。“这个回复包含 PII 吗？”是。“回复引用了检索到的政策文档吗？”是。“回复少于 200 词吗？”是。


**Python 实现**


```python
def reflect_and_correct(customer_message, context, max_revisions=2):
    draft = llm.chat(
        system=AGENT_SYSTEM_PROMPT,
        messages=[{"role": "user", "content": customer_message}],
        context=context
    )

    for revision in range(max_revisions):
        evaluation = llm.chat(
            system="Evaluate this customer support response. Check:\n"
                   "1. Does it answer the customer's actual question?\n"
                   "2. Is the tone professional and empathetic?\n"
                   "3. Does it avoid sharing internal policies or system details?\n"
                   "4. Is it grounded in the provided context, not hallucinated?\n"
                   "Return PASS if all criteria are met. Otherwise return FAIL "
                   "followed by specific feedback on what needs to change.",
            messages=[{
                "role": "user",
                "content": f"Customer message:{customer_message}\n"
                           f"Agent response:{draft}\n"
                           f"Available context:{context}"
            }]
        )

        if evaluation.strip().startswith("PASS"):
            return draft

        draft = llm.chat(
            system=AGENT_SYSTEM_PROMPT
                   + f"\n\nYour previous response was rejected. "
                   + f"Feedback:{evaluation}",
            messages=[{"role": "user", "content": customer_message}],
            context=context
        )

    return draft
```


`max_revisions=2` 上限至关重要。没有它，边缘回复可能在生成器和评估器之间无限反弹。两次修订尝试通常足够。如果两次修订后仍失败，剩余质量差距不太可能由第三次尝试修复，而延迟成本已经显著。


**何时使用反思**


| 场景                      | 使用反思？ | 原因                        |
| ----------------------- | ----- | ------------------------- |
| 升级的客户投诉                 | 是     | 高风险，质量比速度更重要              |
| 简单 FAQ 答案（“你们营业时间是什么？”） | 否     | 增加延迟和成本，无质量收益             |
| 法律或合规敏感回复               | 是     | 错误有真实监管后果                 |
| 高流量、低风险交互               | 否     | 每条消息 2-3 倍大语言模型成本在规模上不可承受 |
| 起草外部沟通                  | 是     | 值得多花 1-2 秒做质量保证           |
| 内部智能体到智能体交接             | 很少    | 内部消息不如面向客户敏感              |


**反思的成本**


每个反思周期为交互增加 1-2 次额外大语言模型调用。对于每天处理 10,000 次对话的支持智能体，对每条消息应用反思会使大语言模型成本增加三倍。生产方法是选择性的：对升级投诉、高价值客户账户和合规敏感回复应用反思。对简单查询和 FAQ 答案跳过，因为轻微质量问题的成本很低。


在规模上，这意味着按风险级别标记交互（路由器可以做到），只对中高风险回复激活反思循环。这在你需要的地方提供质量，而不会让月度 API 账单爆炸。


**关键洞察**


反思不是让智能体“更聪明”。它是在回复到达用户之前捕捉特定的、定义的失效模式。评估器的标准必须明确且可测试。如果你不能把标准写成清单，反思就不会有帮助。它在你确切知道失败长什么样，并能精确描述到让大语言模型检测时效果最好。

### 错误 vs 正确，智能体架构选择


**常见错误 1：对固定流程使用完全自主**


错误：构建完全自主的 ReAct 智能体来处理订单退货。
退货流程有 4 个固定步骤：验证订单、检查资格、
处理退款、发送确认。智能体不需要“决定”
下一步做什么。步骤总是相同的。


正确：使用提示链。每一步是聚焦的大语言模型调用。序列是
固定、可测试且可预测的。自主性在这里增加风险而无收益。


**常见错误 2：当任务需要动态决策时使用简单链**


错误：为客户故障排查构建固定提示链。
故障排查是探索性的。下一个问题取决于客户的回答。
固定链无法适应意外信息。


正确：使用带步骤预算的 ReAct 循环。智能体提出诊断问题，
观察答案，推理下一步检查什么，并继续，
直到问题被识别或步骤预算耗尽。


**常见错误 3：当单次调用足够时构建多步工作流**


错误：创建一个 4 步流水线来回答“你们营业时间是什么？”
步骤 1：分类意图。步骤 2：检索 FAQ。步骤 3：生成答案。
步骤 4：检查语气。总计：4 次大语言模型调用，3-4 秒延迟。


正确：单次大语言模型调用，将 FAQ 放入上下文。问题很简单。
添加流水线步骤增加延迟和成本，质量零提升。
对简单任务过度工程是常见架构错误。


**常见错误 4：高风险输出没有反思**


错误：合规智能体生成关于数据隐私义务的回复，
没有任何审查步骤就直接发送给客户。
一个幻觉的政策细节可能造成法律责任。


正确：添加反思步骤，在发送前根据合规标准检查回复。
与法律上不正确的陈述到达客户相比，1-2 秒延迟可以忽略。


**常见错误 5：基于复杂度而非适配度选择模式**


错误：“ReAct 是最先进的模式，所以我会用它做所有事情。”
复杂度不是特性。对需要简单路由器的任务使用 ReAct 循环
会增加延迟、成本和失效模式。


正确：将模式与任务匹配。解决问题的最简单模式就是最佳模式。
架构技能体现在选择得当，而不是选择最复杂选项。


**决策框架：哪个任务用哪个模式？**


| 任务特征              | 推荐模式      | 示例              |
| ----------------- | --------- | --------------- |
| 固定序列，步骤总是相同       | 提示链       | 订单退货处理、文档生成     |
| 输入类型可变，每种类型有已知处理器 | 路由器       | 客户支持入口、工单分类     |
| 步骤数量未知，下一步取决于结果   | ReAct     | 技术故障排查、研究任务     |
| 基于可用信息做单个复杂决策     | 思维链       | 退款资格、风险评估、升级决策  |
| 需要质量保证的高风险输出      | 添加反思      | 合规回复、升级投诉       |
| 多个独立子任务           | 并行执行      | 同时获取订单状态和积分     |
| 简单问题，上下文已可用       | 单次大语言模型调用 | FAQ、营业时间、基本产品信息 |


**黄金法则**


从可能起作用的最简单模式开始。固定流程用提示链。可变意图用路由器。只有当任务真正需要动态决策时才添加 ReAct。只有当错误输出的成本证明额外大语言模型调用合理时才添加反思。复杂度不是特性。它是你在延迟、调试难度和失效表面积上付出的成本。

> **提示：** 问“你会如何为 X 构建智能体？”，不要跳到最复杂的模式。先问自己：“任务序列是固定还是可变？下一步是提前已知，还是取决于中间结果？输出是高风险还是常规？”然后选择匹配的模式。

### 本节速查表


**覆盖的概念**


| 概念        | 一句话总结                  |
| --------- | ---------------------- |
| 确定性 vs 自主 | 从开发者定义工作流到大语言模型决定执行的光谱 |
| ReAct     | 推理和行动在循环中交错，直到任务完成     |
| 思维链（CoT）  | 回答前逐步推理，提高复杂决策准确性      |
| 提示链       | 将复杂任务拆成固定序列的聚焦大语言模型调用  |
| 路由器 / 分发器 | 分类意图一次，分发到适当的专用处理器     |
| 反思        | 自评估循环，在输出发送前捕捉定义的失效模式  |
| 模式选择      | 将模式与任务特征匹配，始终从最简单选项开始  |


**常见错误**


| 错误               | 为什么错                   | 更好的回答                               |
| ---------------- | ---------------------- | ----------------------------------- |
| “我会构建完全自主智能体”    | 完全自主不可预测、难测试，且很少生产就绪   | “我会从结构化工作流开始，只在任务需要动态决策时添加自主性”      |
| “我会所有事情都用 ReAct” | ReAct 为不需要它的任务增加延迟和复杂度 | “对于固定流程我会用提示链。ReAct 保留给步骤数未知的探索性任务” |
| “智能体在运行时决定一切”    | 生产系统需要可预测性、可测试性和可审计性   | “我会用路由器做意图分类，并为每种意图使用确定性处理器”        |
| 在尝试单智能体前跳到多智能体   | 协调开销通常超过专业化收益          | “我会从单智能体开始，只有当提示过载或工具集冲突时才拆分”       |
| 对每次交互都应用反思       | 反思使每次交互的大语言模型成本翻倍或三倍   | “我会选择性地对高风险回复应用反思，简单查询跳过”           |


**需要记住的关键数字**


```plain text
ReAct 循环预算：          5-15 步（典型生产范围）
反思修订上限：            2 次尝试（超过后收益递减）
路由器分类：              大语言模型约 500ms，机器学习分类器约 5ms
提示链延迟：              累加（3 步各 1s = 总共 3s）
反思成本乘数：            每次交互 2-3 倍（生成器 + 评估器调用）
生产模式分布：            约 80% 部署智能体使用工作流，约 20% 使用自主模式
```
