### **第 11 节：生产：规模、延迟与成本**


演示智能体在开发者笔记本电脑上一次处理一个用户。生产智能体在分布式基础设施上处理 10,000 个并发用户，受延迟约束，在预算内运行。“它能工作”和“它能在规模上可靠、经济地工作”之间的差距是大多数智能体项目失败的地方。本节覆盖跨越这一差距所需的工程：如何建模和降低


成本、如何最小化延迟、如何智能缓存，以及如何水平扩展基础设施。


前面章节的每一个架构决策都有成本和延迟含义。第 2 节的模型选择、第 3 节的执行模式、第 4 节的工具调用、第 5 节的上下文管理、第 6 节的 RAG 流水线、第 7 节的多智能体协调，以及第 8 节的反思循环，都会影响生产智能体每次交互的成本和延迟。本节通过生产经济学的视角将这些决策串联起来。


**我们将覆盖的内容：**

- 词元经济学与成本建模
- 缓存策略：提示缓存、语义缓存、工具结果缓存
- 延迟优化技术
- 水平扩展智能体基础设施
- 完整示例：将支持智能体扩展到 10,000 个并发对话

**这在客户支持智能体中的位置：**


我们的支持智能体在演示中能工作。现在我们需要部署它，每月处理 300,000 次对话，每次对话成本低于 $0.15，响应延迟目标为 3 秒。这需要缓存、模型路由、基础设施扩展和仔细的成本工程。本节构建生产部署计划。

### 词元经济学与成本建模


**大语言模型定价如何工作**


大语言模型 API 按词元收费，输入词元（你发送的内容：系统提示、上下文、对话历史、检索块）和输出词元（模型生成的内容：响应）有不同费率。输出词元通常比输入词元贵 3-5 倍，因为生成比处理输入需要更多计算。


**词元定价参考（近似值，因提供商而异）**


| 模型               | 输入成本（每 1M 词元） | 输出成本（每 1M 词元） | 相对成本 | 最适合           |
| ---------------- | ------------- | ------------- | ---- | ------------- |
| GPT-4o           | $2.50         | $10.00        | 高    | 复杂推理、细致响应     |
| GPT-4o-mini      | $0.15         | $0.60         | 低    | 分类、抽取、简单问答    |
| Claude Sonnet    | $3.00         | $15.00        | 高    | 长上下文推理、详细分析   |
| Claude Haiku     | $0.25         | $1.25         | 低    | 快速分类、简单生成     |
| Llama 3 70B（自托管） | ~$0.50（计算）    | ~$0.50（计算）    | 中    | 完全控制、无 API 依赖 |


价格经常变化。方法论比具体数字更重要。模式是一致的：每个提供商都提供昂贵但能力强的模型，以及便宜但有限的模型。


**每次交互成本公式**


```plain text
成本 = (输入词元 x 输入费率) + (输出词元 x 输出费率)

输入词元 = 系统提示 + 少样本示例 + 检索块
         + 对话历史 + 工具结果

输出词元 = 智能体响应 + 推理词元（如果使用 CoT）
```


**完整示例：单次支持智能体交互**


```plain text
系统提示：                  2,000 词元
少样本示例：                  900 词元
检索块（3 个）：            1,500 词元
对话历史：                  1,000 词元（2 个先前轮次）
工具结果（订单查询）：        300 词元
─────────────────────────────────────
总输入词元：                5,700 词元

智能体响应：                  400 词元
CoT 推理（隐藏）：            200 词元
─────────────────────────────────────
总输出词元：                  600 词元

使用 GPT-4o：
  输入成本：5,700 / 1,000,000 x $2.50  = $0.01425
  输出成本：  600 / 1,000,000 x $10.00 = $0.00600
  每次交互总计：                         $0.02025

使用 GPT-4o-mini：
  输入成本：5,700 / 1,000,000 x $0.15  = $0.000855
  输出成本：  600 / 1,000,000 x $0.60  = $0.000360
  每次交互总计：                         $0.001215
```


GPT-4o 每次交互成本约为 GPT-4o-mini 的 17 倍。对于简单订单状态查询，mini 模型的质量足够。对于需要细致推理的复杂退款资格决策，GPT-4o 产生明显更好的结果。这种成本差距是模型路由模式的基础。


**月度成本预测**


```plain text
假设：
  每月 300,000 次对话
  每次对话平均 5 轮（5 次大语言模型调用）
  每月 1,500,000 次大语言模型调用

全部 GPT-4o：       1,500,000 x $0.02025 = $30,375/月
全部 GPT-4o-mini：  1,500,000 x $0.001215 = $1,823/月
模型路由（60% mini，40% GPT-4o）：
  900,000 x $0.001215 + 600,000 x $0.02025 = $1,094 + $12,150 = $13,244/月
```


模型路由相比所有事情都用 GPT-4o 节省 56%，同时为真正需要它的 40% 交互保留昂贵模型的质量。


**成本杠杆**


| 杠杆         | 机制                  | 典型节省        | 权衡              |
| ---------- | ------------------- | ----------- | --------------- |
| 模型路由       | 简单任务用便宜模型，复杂任务用昂贵模型 | 40-60%      | 需要可靠的意图分类       |
| 更短系统提示     | 减少每次调用的固定词元开销       | 5-15%       | 智能体行为指导减少的风险    |
| 更少检索块      | RAG 取 3 块而不是 5 块    | 10-20%      | 遗漏相关上下文的风险      |
| 缓存（下一张幻灯片） | 完全避免冗余大语言模型调用       | 30-50%      | 动态数据的响应可能过时     |
| 提示缓存（提供商）  | 重复前缀的输入成本降低         | 输入成本 25-50% | 仅当前缀在调用间完全相同时有效 |
| 批处理        | 以更低费率批量处理非紧急请求      | 50%         | 仅适用于异步、非交互任务    |

> **提示：** 当遇到“如何将成本降低 50%？”时，不要说“使用更便宜的模型”。那会牺牲质量。更强的回答分层多个杠杆：“我会实现模型路由，将简单查询发送到 GPT-4o-mini（节省 40%），为重复问题添加语义缓存（再节省 15-20%），并将检索块从 5 个减少到 3 个，带相关性阈值，以减少词元浪费。结合起来，这些技术可以在没有有意义质量退化的情况下将成本降低 50-60%。”

### 大语言模型调用的缓存策略


**为什么缓存大语言模型调用？**


大语言模型调用昂贵且缓慢。如果 100 个客户在一天内问“你们的退货政策是什么？”，进行 100 次单独的 RAG 检索和 100 次单独的大语言模型调用来产生 100 个几乎相同的响应是浪费的。缓存通过为重复或相似查询提供存储的响应来消除冗余计算。


**三层缓存**


**1. 提示缓存（提供商级）**


一些大语言模型提供商（Anthropic、OpenAI）缓存长提示前缀的计算。如果你的系统提示和少样本示例在调用之间相同（通常如此），提供商会缓存该前缀的键值注意力状态。随后具有相同前缀的调用只处理新内容（对话历史、检索块），而不是从头处理整个提示。


节省：缓存前缀部分的输入词元成本降低 25-50%。除了启用该功能外，无需代码更改。


限制：前缀必须逐字节相同。如果系统提示在调用之间变化，提示缓存不适用。


**2. 语义缓存（应用级）**


为语义相似的查询缓存响应。当新问题到达时，检查相似问题是否已经回答过。如果相似度得分超过阈值，提供缓存响应，而不是进行新的大语言模型调用。


```python
class SemanticCache:
    def __init__(self, vector_db, similarity_threshold=0.92):
        self.vector_db = vector_db
        self.threshold = similarity_threshold

    def get(self, question):
        question_embedding = embed_text(question)
        results = self.vector_db.query(
            vector=question_embedding,
            top_k=1,
            collection="response_cache"
        )

        if results and results[0].score >= self.threshold:
            return results[0].metadata["response"]
        return None

    def set(self, question, response):
        question_embedding = embed_text(question)
        self.vector_db.upsert(
            id=hash(question),
            vector=question_embedding,
            metadata={"question": question, "response": response},
            collection="response_cache"
        )


def handle_query(question, cache, agent):
    cached_response = cache.get(question)
    if cached_response:
        return cached_response

    response = agent.process(question)
    cache.set(question, response)
    return response
```


相似度阈值至关重要。太低（0.80），你会为看起来相似但含义不同的问题提供错误答案（“电子产品的退货政策” vs “食品的退货政策”）。太高（0.98），你很少获得缓存命中。0.90-0.95 的阈值对 FAQ 类查询效果良好。


**3. 工具结果缓存**


缓存频繁调用工具的结果。产品详情、政策文档和 FAQ 内容很少变化，但被不断查询。用适当的 TTL（生存时间）值缓存工具结果。


```python
CACHE_TTL = {
    "product_details": 3600,        # 1 小时（价格可能变化）
    "policy_document": 86400,       # 24 小时（政策很少变化）
    "faq_article": 86400,           # 24 小时
    "order_status": 60,             # 1 分钟（变化频繁）
    "inventory_check": 300,         # 5 分钟
}

def cached_tool_call(tool_name, params, cache):
    cache_key = f"{tool_name}:{hash(str(params))}"
    cached = cache.get(cache_key)

    if cached:
        return cached

    result = execute_tool(tool_name, params)
    ttl = CACHE_TTL.get(tool_name, 300)
    cache.set(cache_key, result, ttl=ttl)
    return result
```


**缓存策略对比**


| 策略     | 缓存什么           | 节省           | 延迟影响         | 新鲜度风险           |
| ------ | -------------- | ------------ | ------------ | --------------- |
| 提示缓存   | 重复提示前缀的大语言模型计算 | 输入成本 25-50%  | 中等（仍运行大语言模型） | 无（相同计算）         |
| 语义缓存   | 相似问题的完整响应      | 每次命中 90-100% | 大（完全跳过大语言模型） | 中等（底层数据变化时可能过时） |
| 工具结果缓存 | API/数据库调用结果    | 可变（取决于命中率）   | 显著（跳过网络调用）   | 取决于 TTL 设置      |


**缓存失效**


缓存最难的部分是知道缓存数据何时过时。关于退货政策的缓存响应在政策变化的那一刻就无效了。缓存的订单状态在订单发货的那一刻就无效了。


规则：

- 静态内容（政策、FAQ）：长 TTL（小时到天），内容更新时失效
- 动态内容（订单状态、库存）：短 TTL（秒到分钟），或不缓存
- 语义缓存：底层知识库文档更新时失效

有疑问时，选择更短 TTL。缓存未命中花费一次额外大语言模型调用。过时响应花费客户信任。

### 延迟优化


**延迟来自哪里**


单次智能体交互涉及多个顺序操作。每个都增加客户体验到的总响应时间。


**典型支持智能体交互的延迟分解**


```plain text
步骤                          延迟          备注
──────────────────────────────────────────────────────────
意图分类                      200-500ms      大语言模型调用（mini 模型）
RAG 检索                      50-200ms       向量数据库查询
工具调用（订单查询）          100-500ms      外部 API，依赖网络
大语言模型推理 + 响应         800-2,000ms    主模型，最大组件
输出过滤/护栏                 50-100ms       分类器或规则检查
──────────────────────────────────────────────────────────
总计（顺序）：                1,200-3,300ms
```


大语言模型推理步骤占主导。它通常占总延迟的 50-70%。优化大语言模型调用影响最大。


**优化技术**


**1. 流式输出**


一旦生成第一个词元就开始向用户显示响应，而不是等待完整响应。实际生成时间不变，但感知延迟大幅下降。用户在 200-500ms 内看到文本出现，而不是等待 2-3 秒获得完整响应。


```python
def stream_response(messages, system_prompt):
    stream = llm.chat(
        system=system_prompt,
        messages=messages,
        stream=True
    )

    for chunk in stream:
        yield chunk.content
```


流式输出实现几乎免费，应成为所有交互式智能体的默认。


**2. 并行工具调用**


当多个工具调用独立时，并行执行它们。来自第 4 节：如果客户问“我的订单状态是什么？我有积分吗？”，订单查询和积分查询是独立的。顺序执行：400ms + 400ms = 800ms。并行执行：max(400ms, 400ms) = 400ms。


```python
import asyncio

async def parallel_tool_calls(tools_to_call):
    tasks = [execute_tool_async(tool.name, tool.args) for tool in tools_to_call]
    results = await asyncio.gather(*tasks)
    return results
```


**3. 为速度选择模型**


更小的模型更快。GPT-4o-mini 生成词元比 GPT-4o 快 2-3 倍。对于意图分类步骤（需要速度，不是深度推理），mini 模型从流水线中减少 200-400ms。


**4. 预计算**


在摄取期间提前嵌入文档，而不是在查询时。计算并缓存常见查询嵌入。在实例启动时预热模型连接。你能从查询时移到构建时的每一毫秒计算，都会减少面向用户的延迟。


**5. 连接池**


保持与外部 API、向量数据库和大语言模型提供商的持久连接。为每个请求创建新的 TCP/TLS 连接增加 50-150ms 开销。连接池为第一个之后的所有请求消除这一点。


**优化权衡表**


| 技术      | 延迟降低              | 质量影响         | 实现工作量         |
| ------- | ----------------- | ------------ | ------------- |
| 流式输出    | 感知：60-80% 降低      | 无            | 低（大多数 SDK 支持） |
| 并行工具调用  | 多工具步骤 30-50%      | 无            | 中（异步代码、依赖分析）  |
| 分类用更小模型 | 每次分类 200-400ms    | 轻微（简单任务推理降低） | 低（模型路由配置）     |
| 预计算（嵌入） | 每次查询 100-300ms    | 无            | 低（摄取期间批处理）    |
| 连接池     | 每次外部调用 50-150ms   | 无            | 低（配置更改）       |
| 更短提示    | 50-200ms（处理更少词元）  | 可能（指令细节减少）   | 低（提示编辑）       |
| 响应长度限制  | 100-500ms（生成更少词元） | 可能（响应截断）     | 低（提示指令）       |


**目标延迟**


| 智能体类型       | 目标 p50 | 目标 p95 | 可接受 p99 |
| ----------- | ------ | ------ | ------- |
| 交互式聊天（面向客户） | 低于 2s  | 低于 4s  | 低于 6s   |
| 语音智能体（实时）   | 低于 1s  | 低于 2s  | 低于 3s   |
| 后台任务（邮件处理）  | 低于 30s | 低于 60s | 低于 120s |
| 批量分析（报告生成）  | 分钟     | N/A    | N/A     |


对于我们的客户支持智能体，目标是 p50 低于 2 秒，p95 低于 4 秒。启用流式输出后，即使用完整响应需要 2.5 秒，用户也能在 500ms 内看到第一个词元。

### 扩展智能体基础设施


**从一个实例到多个**


单个智能体实例一次处理一个对话（或通过异步处理几个）。要服务 10,000 个并发对话，你需要多个智能体实例运行在负载均衡器后面，共享状态并协调访问下游服务。


**无状态 vs 有状态智能体**


第一个设计决策：你的智能体实例是无状态还是有状态？


**无状态**：智能体实例不在内存中保存对话状态。所有状态（对话历史、用户上下文）外部存储在 Redis 或数据库中。任何实例都可以处理任何请求。扩展简单：添加更多实例。


**有状态**：智能体实例在内存中保存对话状态。返回用户必须路由到同一实例（粘性会话）。扩展更难：实例故障丢失进行中的对话。重新平衡复杂。


| 维度     | 无状态           | 有状态       |
| ------ | ------------- | --------- |
| 扩展     | 自由添加实例        | 需要粘性会话    |
| 实例故障   | 无数据丢失（状态在外部）  | 进行中的对话丢失  |
| 每次请求延迟 | 略高（状态检索）      | 略低（状态在内存） |
| 复杂度    | 更简单的运维，外部状态依赖 | 复杂路由、会话管理 |
| 生产建议   | 大多数智能体的默认选择   | 仅当延迟极其关键时 |


无状态智能体加 Redis 作为状态存储是标准生产模式。从 Redis 读取的 1-2ms 开销与运维简单性收益相比可以忽略。


**基础设施架构**


![%E6%88%AA%E5%B1%8F2026-10-07_21.56.30.png](images/blog/2026-10-06-agentic-ai-course-production-scale-laten/img-9b0b8846b5.png)


负载均衡器将传入请求分发到智能体池。每个智能体实例从 Redis 读取对话状态，处理请求（大语言模型调用、工具调用、RAG 检索），更新 Redis 中的状态，并返回响应。智能体实例本身是可丢弃的。任何实例都可以重启或替换而不会丢失数据。


**基于队列的非交互任务架构**


并非所有智能体任务都是交互式的。邮件处理、工单分诊、报告生成和批量分析可以通过消息队列异步处理。


```python
# 生产者：传入请求进入队列
def enqueue_task(task):
    queue.publish(
        topic="agent_tasks",
        message={
            "task_id": task.id,
            "type": task.type,
            "payload": task.data,
            "priority": task.priority
        }
    )

# 消费者：智能体工作者从队列拉取
def agent_worker():
    while True:
        task = queue.consume("agent_tasks")
        result = process_task(task)
        store_result(task.task_id, result)
```


队列好处：处理突发流量（队列吸收尖峰）、启用优先级排序（紧急工单先处理）、将接收与处理解耦（即使智能体忙碌，接收也永不阻塞）。


**速率限制**


规模化的智能体对下游服务产生显著流量。二十个智能体实例，每个在每实例 50 个并发对话中进行 5 次工具调用，每秒对后端 API 产生 5,000 次工具调用。没有速率限制，智能体流量可能压垮它所依赖的服务。


速率限制层：

- 每智能体实例：限制并发大语言模型调用（例如 10 个并发）
- 每工具：限制对每个外部 API 的调用（例如每秒 100 次对订单服务）
- 每客户：限制每分钟每客户交互次数（防止滥用和失控循环）
- 每提供商：遵守大语言模型提供商速率限制（例如 OpenAI 层级限制）

```python
from ratelimit import limits, sleep_and_retry

@sleep_and_retry
@limits(calls=100, period=1)
def call_order_api(order_id):
    return requests.get(f"{ORDER_SERVICE}/orders/{order_id}")
```


**扩展决策框架**


| 场景            | 解决方案                    | 原因            |
| ------------- | ----------------------- | ------------- |
| 100 个并发对话     | 单实例，异步处理                | 负载不足以证明基础设施合理 |
| 1,000 个并发对话   | 3-5 个实例 + 负载均衡器 + Redis | 中等规模，标准部署     |
| 10,000 个并发对话  | 20+ 实例 + Redis 集群 + 队列  | 高规模，需要队列处理突发  |
| 100,000+ 并发对话 | 微服务架构，区域部署              | 企业规模，按区域路由    |

### 完整示例，将支持智能体扩展到 10K 并发对话


**场景**


客户支持智能体现在服务一家每月 300,000 次客户对话的公司，高峰负载为工作时间内 10,000 个并发对话。要求：

- 响应延迟：p50 低于 2 秒，p95 低于 4 秒
- 可用性：99.5% 正常运行时间
- 成本：每次对话平均低于 $0.15
- 质量：保持与单实例演示相同的准确率

**架构**


负载均衡器分发到 20 个无状态智能体实例。Redis 集群存储对话状态，废弃对话 TTL 为 24 小时。向量数据库集群（3 节点）处理 RAG 检索。语义缓存处理重复 FAQ 查询。模型路由器分类意图并选择适当模型。


**模型路由策略**


| 查询类型          | 百分比 | 模型          | 每次交互成本      | 理由           |
| ------------- | --- | ----------- | ----------- | ------------ |
| 简单 FAQ / 订单状态 | 45% | GPT-4o-mini | $0.006      | 简单查询，无复杂推理   |
| 标准退款 / 退货     | 30% | GPT-4o-mini | $0.008      | 结构化流程，低复杂度   |
| 复杂投诉 / 边缘情况   | 15% | GPT-4o      | $0.045      | 需要细致推理和语气    |
| 升级到人工         | 10% | N/A（路由出去）   | $0.002（仅分类） | 智能体无法解决，需要人工 |


加权平均每次交互成本：(0.45 x $0.006) + (0.30 x $0.008) + (0.15 x $0.045) + (0.10 x $0.002) = $0.0027 + $0.0024 + $0.00675 + $0.0002 = 每次大语言模型交互 $0.012


**成本模型**


```plain text
每次对话（平均 5 轮）：
  大语言模型调用：     5 轮 x $0.012 平均          = $0.060
  RAG 检索：           3 次向量搜索 x $0.0001      = $0.0003
  嵌入调用：           5 次查询 x $0.00001          = $0.00005
  工具调用：           2 次 API 调用 x $0.0001      = $0.0002
  ──────────────────────────────────────────────────────────
  每次对话小计（缓存前）：                            $0.061

  语义缓存命中率：35% 的对话
  缓存对话成本：      $0.002（仅分类 + 缓存查找）
  非缓存对话：        $0.061

  每次对话有效成本：
    (0.35 x $0.002) + (0.65 x $0.061) = $0.0007 + $0.0397 = $0.040

月度成本：
  300,000 次对话 x $0.040 = $12,000/月

基础设施成本：
  20 个智能体实例（容器）：      $600/月
  Redis 集群：                   $200/月
  向量数据库集群（3 节点）：     $400/月
  负载均衡器 + 网络：            $150/月
  监控和日志：                   $200/月
  ──────────────────────────────────────────────────
  基础设施总计：                 $1,550/月

总月度成本：                     $13,550/月
每次对话成本：                   $0.045
```


这远低于每次对话 $0.15 的目标。最大的成本杠杆是语义缓存命中率。将其从 35% 提高到 50%（通过扩展 FAQ 覆盖并略微降低相似度阈值），月度大语言模型成本将从 $12,000 降至约 $9,500。


**延迟预算**


```plain text
目标：p50 低于 2,000ms，p95 低于 4,000ms

步骤                           p50        p95       应用的优化
────────────────────────────────────────────────────────────────────────
意图分类                       150ms      300ms     GPT-4o-mini，连接池
缓存检查（语义）               10ms       20ms      内存向量搜索
RAG 检索                       100ms      250ms     向量数据库集群，3 副本
工具调用（订单查询）           200ms      500ms     连接池，重试预算
大语言模型推理 + 响应          800ms    1,800ms    简单用 GPT-4o-mini，流式输出
护栏检查                       40ms       80ms      基于规则，无大语言模型调用
────────────────────────────────────────────────────────────────────────
总计（顺序最坏情况）：         1,300ms   2,950ms
```


p50 为 1,300ms，p95 为 2,950ms，均满足目标。流式输出意味着即使用完整响应需要 1.3 秒，用户也能在约 500ms 时看到第一个词元。


**瓶颈分析**


| 组件           | 当前容量      | 瓶颈在       | 缓解           |
| ------------ | --------- | --------- | ------------ |
| 智能体池（20 实例）  | 10K 并发    | ~15K 并发   | 添加实例（水平）     |
| Redis 集群     | 100K 操作/秒 | ~50K 并发对话 | Redis 集群分片   |
| 向量数据库（3 节点）  | 5K 查询/秒   | ~25K 并发   | 添加只读副本       |
| 订单 API（下游）   | 500 请求/秒  | ~12K 并发   | 速率限制、结果缓存    |
| 大语言模型提供商速率限制 | 因层级而异     | 取决于提供商计划  | 多个提供商密钥，负载分配 |


当前增长下的下一个瓶颈是订单 API，约 12K 并发对话。缓解：用 60 秒 TTL 缓存订单状态结果（大多数客户检查一次状态，且状态在 60 秒内不会变化）。


**所做的权衡**


| 权衡            | 选择                  | 收益                    | 风险                |
| ------------- | ------------------- | --------------------- | ----------------- |
| 语义缓存          | 35% 命中率，阈值 0.92     | 每月节省 $4,200           | 缓存查询的响应略微过时       |
| 模型路由          | 75% 查询用 GPT-4o-mini | 相比全部 GPT-4o 降低 56% 成本 | 误分类复杂查询时质量较低      |
| 无状态智能体        | Redis 状态存储          | 简单扩展，无粘性会话            | 每次请求 1-2ms 状态检索开销 |
| RAG top-k = 3 | 3 块而不是 5 块          | 每次调用节省约 1,000 输入词元    | 边缘情况遗漏相关上下文的风险    |
| 流式输出          | 所有响应默认              | p0 延迟低于 500ms         | 少量实现复杂度           |

**常见错误**

| 忽视下游服务的速率限制  | 规模化的智能体流量压垮后端 API | “我会按工具和按客户进行速率限制，并缓存频繁访问的数据以减少下游负载”                         |
