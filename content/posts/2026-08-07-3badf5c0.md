## 1. 矛盾


有了向量库，最省事的是「每句话都 Top-K」。代价很具体：寒暄被无关片段污染、通识题被带偏、每次闲聊都付 **query embedding + ANN +（可选）重排** 的账单。


反过来路由太「敢判 direct」，用户刚上传的文档又会表现为「库里有、怎么问都没有」。


和「永远检索」比，路由要省下的不是抽象架构分，而是：**闲聊 / 通识不再走全量检索链路**。省一次检索，往往省的是一次 embedding、一次向量查询，以及后续可能打开的 Multi-Query / HyDE / Rerank。


## 2. 本篇目标


给出一套可运行的三层决策：`direct | retrieve`。本篇**只负责「要不要检」**；检什么、怎么检（双路门槛、HyDE、Multi-Query、Rerank）是下一层的事，开关虽在同一配置文件，默认大多关闭


并写清几件容易含糊的事：

- 灰色地带为何不调 LLM
- 0.68 / 0.42 从哪来
- 预检失败或跳过时走哪条路
- 空库 / 新 workspace 预检会怎样
- 线上靠哪些字段调阈值

## 3. 三层分别是什么


### 3.1 总览：输出只有两个字，手段却有三层


路由对外只产出：


```typescript
type QueryRoute = "direct" | "retrieve";

interface QueryRouteDecision {
  route: QueryRoute;
  reason: string;              // 给人看、也给日志用
  fastPath?: boolean;          // 是否没走 LLM
  precheckSimilarity?: number; // 预检 Top-1，便于调阈值
}
```


`direct`：聊天入口**不调用** `getRelevantContext`，回答不带引用卡片。


`retrieve`：才进入检索；检索内部还可能开 HyDE / Multi-Query / Rerank（默认关），那是「怎么检」，不是本层的「要不要检」。


三层是**同一决策的三种代价不同的探测器**，按成本从低到高排，能早停就早停：


| 层 | 名字           | 代价                              | 代码入口                                              | 能定什么                        |
| - | ------------ | ------------------------------- | ------------------------------------------------- | --------------------------- |
| ① | 意图快路径        | 几乎为 0（字符串 / 词表）                 | `tryIntentFastPath`                               | 明显闲聊、算式 → `direct`          |
| ② | Embedding 预检 | 1 次 query embedding + Top-1 ANN | `routeWithEmbeddingPrecheck` → `probeKbRelevance` | 像不像库内内容 → high / low / gray |
| ③ | LLM 路由器      | 1 次小模型 JSON 调用                  | `routeWithLlm`                                    | **仅预检 skip 时**兜底            |


编排在 `decideQueryRoute` 里写死为「短路求值」：


```typescript
export async function decideQueryRoute(query: string, options: { workspaceId: string }) {
  // ① 能定就返回，后面两层完全不跑
  const intentFast = tryIntentFastPath(query);
  if (intentFast) return intentFast;

  // ② decided → 返回；skip → 才进 ③
  const precheckOutcome = await routeWithEmbeddingPrecheck(query, options.workspaceId);
  if (precheckOutcome.kind === "decided") return precheckOutcome.decision;

  // ③ 预检不可用才问 LLM；再挂 → default direct
  if (ENABLE_LLM_QUERY_ROUTER) {
    try {
      return await routeWithLlm(query);
    } catch {
      return { route: "direct", reason: "heuristic_default_direct" };
    }
  }
  return { route: "direct", reason: "heuristic_default_direct" };
}
```


聊天入口据此分支（检索被门控，而不是默认开启）：


```typescript
const routeDecision = await decideQueryRoute(lastContent, { workspaceId, requestId });

let contextResult = { kind: "no-docs" as const };
if (routeDecision.route === "retrieve") {
  contextResult = await getRelevantContext(lastContent, requestId, workspaceId);
}
// direct：上面 if 不进，citations 为空，流式生成仍发生
```


### 3.2 第一层：意图快路径——零模型成本的「一眼能定」


**原理：** 有些问题形态与知识库无关是确定的，不必付 embedding。用可维护词表 / 正则，而不是巨型万能正则。


```typescript
const GREETING_PHRASES = new Set(["你好", "您好", "hi", "hello", "在吗", "谢谢", /* ... */]);

function normalizeForIntent(text: string) {
  return text.trim().replace(/^[\s!！?？。,，~]+|[\s!！?？。,，~]+$/g, "").toLowerCase();
}

function tryIntentFastPath(query: string): QueryRouteDecision | null {
  if (!query.trim()) {
    return { route: "direct", reason: "empty_query", fastPath: true };
  }
  if (/^[\d\s+\-*/()=？?]+$/.test(query.trim())) {
    return { route: "direct", reason: "pure_math", fastPath: true };
  }
  if (GREETING_PHRASES.has(normalizeForIntent(query))) {
    return { route: "direct", reason: "greeting_only", fastPath: true };
  }
  return null; // 定不了 → 交给第 ② 层
}
```


**优势：** `你好` 这类请求零外呼，也不污染上下文。


**局限：** 覆盖面窄——「帮我看看上传的合同里违约金怎么写」必须留给后面两层。


### 3.3 第二层：Embedding 预检——「问题像不像库里已有内容」


**原理：** 私有知识是否相关，最直接的廉价信号是：把问题编成与入库相同空间的向量，看库内最近邻有多近。这不是最终检索（limit=1、threshold=0），只是路由探针。


```typescript
async function probeKbRelevance(query, workspaceId, ...) {
  const vector = await embedQueryText(query); // query 模式，可走进程内 LRU 缓存
  if (!vector) {
    return { topSimilarity: 0, probed: false }; // 失败 → skip，不是 low_sim
  }

  const hits = await vectorStore.search({
    workspaceId,
    vector,
    limit: 1,
    similarityThreshold: 0, // 故意为 0：空库也算「探测成功」
    filter: ROUTE_CORPUS_FILTER, // 用户文档 / seed 等路由语料
  });

  return {
    topSimilarity: hits[0]?.similarity ?? 0,
    title: hits[0]?.title,
    probed: true,
  };
}
```


判定函数把连续相似度切成三段：


```typescript
// ≥ 0.68 → 很像 → retrieve
precheckSuggestsRetrieve = probed && topSimilarity >= ROUTE_RETRIEVE_SIMILARITY

// < 0.42 → 很不像 → direct
precheckSuggestsDirect   = probed && topSimilarity <  ROUTE_DIRECT_SIMILARITY

// [0.42, 0.68) → 灰区 → 代码里直接 retrieve，不再调 LLM
```


对应 `routeWithEmbeddingPrecheck` 的三种 `reason`：`high_sim` / `low_sim` / `gray_retrieve`。


**为什么用向量预检，而不是关键词规则？**


用户问法往往和文档标题不一致（同义、换说法）。规则漏召回高；Top-1 相似度是连续信号，还能靠日志重标阈值。


**空库特例（重要）：**


embedding 成功、库里没有任何命中 → `probed: true, topSimilarity: 0` → 走 `low_sim` → **direct**。


这不是预检失败：系统已经知道「库里没什么可对上的」，不必再 skip 去问 LLM「要不要检」。


### 3.4 第三层：LLM 路由器——只在预检「做不成」时出场


**原理：** 当第 ② 层返回 `skip`（预检关闭，或 `probed: false`），没有可用的相似度信号，才用小模型做二分类。输出被 Zod 收成严格 JSON；解析失败则 `heuristic_default_direct`。


```typescript
async function routeWithLlm(query: string): Promise<QueryRouteDecision> {
  const raw = await generateRagHelperText(ROUTER_SYSTEM, query, /* temperature */ 0);
  const jsonMatch = raw.match(/\{[\s\S]*\}/);
  if (!jsonMatch) return { route: "direct", reason: "heuristic_default_direct" };
  try {
    const parsed = RouteSchema.parse(JSON.parse(jsonMatch[0]));
    return { route: parsed.route, reason: `llm:${parsed.reason}` };
  } catch {
    return { route: "direct", reason: "heuristic_default_direct" };
  }
}
```


**刻意不做的事：** 灰区（`probed: true` 且分数在中间）**不**进这一层。原因见 §4.1——延迟、成本、以及漏检更伤用户。


### 3.5 为什么要这么做（设计动机）


可以把整条链路想成一个漏斗：


```plain text
全部问题
  │  ① 滤掉「确定无关」的闲聊/算式        ← 省 100% 检索成本
  ▼
剩余问题
  │  ② 用 Top-1 相似度三分（高/低/灰）    ← 多数在此定案，仍不调 LLM
  ▼
仅当 ② 做不成
  │  ③ LLM 兜底；再不成 → direct          ← 最贵，调用次数应最少
  ▼
retrieve 才进入 getRelevantContext
```


动机可以收成三句：

1. **成本不对称：** 误一次 `direct`（漏检）会伤害「我上传了文档」的信任；误一次 `retrieve`（多检）主要是多花一次检索。所以灰区偏 retrieve。
2. **信号成本不对称：** 词表 ≈ 免费；embedding 预检 ≈ 半次检索；LLM 路由 ≈ 一次生成。能用便宜信号定案，就别用贵的。
3. **职责分离：** 路由只门控「要不要检」；HyDE / 双路 / Rerank 留在检索层。否则调 0.68 时分不清是路由错了还是检索错了。

### 3.6 优势（相对常见三种极端）


| 对比对象            | 三层路由的优势                                                     |
| --------------- | ----------------------------------------------------------- |
| **永远 Top-K 检索** | 闲聊/通识少付 embedding+ANN（+ 可选重排）；上下文不被无关 chunk 污染；引用卡片不会在寒暄下乱出 |
| **永远 LLM 路由**   | 多数请求零模型或仅预检；首字延迟更稳；少一次「把文档名判成通识」的幻觉面                        |
| **只有规则、无预检**    | 换说法的真实知识问题仍能靠相似度召回；有连续分数可标定，而不是无限加 if                       |
| **灰区再调 LLM**    | 少一轮路由延迟与费用；产品行为可预期（拿不准就检）                                   |


可观测性也是优势：`reason` + `precheckSimilarity` 能直接回答「为什么没检 / 为什么检了」，支撑以后重标阈值。


### 3.7 不做会怎么样（反事实）


| 若取消…                       | 会发生什么                                         |
| -------------------------- | --------------------------------------------- |
| **整层路由，永远 retrieve**       | 每句闲聊都检索；回答被 seed/旧文档带偏；账单和延迟上升；引用区在「你好」下也可能出现 |
| **整层路由，永远 direct**         | 知识库形同虚设；上传文档无法进入回答链路                          |
| **只留 ①，去掉 ②③**             | 非寒暄问题要么全检要么全不检；「合同里违约金」类问法没有廉价判别器             |
| **只留 ③，去掉 ①②**             | 每句多一次 LLM；峰值延迟差；路由器自身也会误判                     |
| **② 的灰区改调 LLM**            | 高频灰区把「省检索」省下的钱花回路由；首字变慢；行为更不可预测               |
| **② 失败不 skip、直接当 low_sim** | embedding 故障会被误判成「库里不像」→ 系统性漏检                |
| **空库当 skip 去问 LLM**        | 无文档时仍烧路由器；正确答案本应是「没什么可检的」→ direct             |


### 3.8 原理小结（对照代码数据流）


```plain text
lastContent
  → decideQueryRoute
       ├─ tryIntentFastPath? ──yes──► { route: direct, reason: greeting_only|... }
       │
       ├─ probeKbRelevance
       │     embed 失败 ──► skip ──► routeWithLlm? ──► direct/retrieve / default direct
       │     embed 成功 + Top-1
       │        ≥ 0.68 ──► retrieve (high_sim)
       │        < 0.42 ──► direct   (low_sim)   ← 含空库 Top-1=0
       │        灰区   ──► retrieve (gray_retrieve)  ← 不进 LLM
       │
  → route === "retrieve" ?
       yes → getRelevantContext → systemPrompt + citations
       no  → 无检索上下文，无引用卡片，仍 streamText
```


一句话原理：**用「问题像不像库内内容」的廉价信号，替代「每句都检」或「每句都问大模型」；信号清楚就当场定，信号模糊就按漏检成本更高来选，信号拿不到才用贵模型兜底。**


## 4. 方案取舍


| 策略                     | 问题                        |
| ---------------------- | ------------------------- |
| 永远 retrieve            | 成本高、闲聊脏                   |
| 永远 LLM 路由              | 额外一轮模型延迟与费用；还可能把私有文档名判成通识 |
| **规则 → 向量预检 → LLM 兜底** | 便宜路径优先；灰区宁可多检             |


### 4.1 为什么灰区不调 LLM？


预检落在 `[0.42, 0.68)` 时，代码直接 `retrieve`，**不再问 LLM**。原因叠在一起：

1. **延迟**：灰区本就是「说不准」，再加一轮路由器，首字更慢。
2. **成本**：路由器也是一次 LLM 调用；高频灰区会把「省检索」省回来的钱花回去。
3. **产品立场**：漏检比误检更伤上传用户——「我刚传的文档怎么问都没有」比「偶尔多检了一次」更难解释。灰区偏向 retrieve，是刻意的。

LLM 只留给 **预检不可用**（关闭、embedding 失败等）时做兜底。


### 4.2 为什么阈值是 0.68 / 0.42？


这是 **NIM embedqa 余弦相似度上的经验起点**，不是离线标定出来的最优解：

- `≥ 0.68`：Top-1 已经很像库内内容 → 直接 retrieve，跳过 LLM。
- `< 0.42`：几乎不像 → 直接 direct。
- 中间灰区 → retrieve。

两个数拉开约 0.26 的带宽，是为了少在边界来回抖。换 embedding 模型、换语料分布后，**必须用真实问答日志重标**（见 §8），否则会系统性偏检或漏检。环境变量可覆盖：`ROUTE_RETRIEVE_SIMILARITY` / `ROUTE_DIRECT_SIMILARITY`。


## 5. 调用链


```plain text
用户问题
  → ① 意图快路径：空 / 寒暄 / 纯算式 → direct
  → ② embedding Top-1 预检（可关）
        embedding 失败 / 预检关闭 → skip → ③
        探测成功且 Top-1 = 0（空库等）→ low_sim → direct
        ≥ 0.68 → retrieve
        < 0.42 → direct
        灰区 → retrieve（不调 LLM）
  → ③ 仅当预检 skip：LLM JSON 路由；失败或关闭 → default direct
  → retrieve → getRelevantContext（此处才可能开 HyDE / Multi-Query / Rerank）
  → direct → 直接生成，不附引用
```


**和后续检索的衔接：**


`decideQueryRoute === "retrieve"` 只表示「值得检」。真正的 `getRelevantContext` 里还有双路阈值、可选 HyDE / Multi-Query / Rerank；那些默认多为关，本篇不展开（见系列第 4 篇）。路由层不要和检索增强搅在同一段逻辑里，否则阈值调优时分不清是「不该检」还是「检坏了」。

### 6.2 意图快路径


```typescript
function isEmptyQuery(q: string) {
  return q.trim().length === 0;
}
function isPureMathExpression(q: string) {
  return /^[\d\s+\-*/().]+$/.test(q.trim());
}
function isGreetingOnly(q: string) {
  // 实际项目用词表；此处示意
  return /^(你好|hi|hello|在吗)[\s!！.。]*$/i.test(q.trim());
}

function tryIntentFastPath(query: string): QueryRouteDecision | null {
  if (isEmptyQuery(query)) return { route: "direct", reason: "empty_query", fastPath: true };
  if (isPureMathExpression(query)) return { route: "direct", reason: "pure_math", fastPath: true };
  if (isGreetingOnly(query)) return { route: "direct", reason: "greeting_only", fastPath: true };
  return null;
}
```


### 6.3 预检：`probeKbRelevance`


```typescript
export interface EmbeddingPrecheckResult {
  topSimilarity: number;
  title?: string;
  /** false = 没能完成探测（应 skip 到 LLM / default） */
  probed: boolean;
}

/**
 * 路由前探测：query embedding + Top-1。
 * similarityThreshold=0：空库也会「探测成功」，只是 Top-1 为 0。
 */
export async function probeKbRelevance(
  query: string,
  workspaceId: string,
  embedQuery: (q: string) => Promise<number[] | null>,
  searchTop1: (workspaceId: string, vector: number[]) => Promise<{ similarity: number; title?: string } | null>,
): Promise<EmbeddingPrecheckResult> {
  const vector = await embedQuery(query);
  if (!vector) {
    // embedding 失败 → 调用方应 skip，不要当成 low_sim
    return { topSimilarity: 0, probed: false };
  }

  const top = await searchTop1(workspaceId, vector);
  return {
    topSimilarity: top?.similarity ?? 0, // 空库 / 无命中 → 0，但 probed=true
    title: top?.title,
    probed: true,
  };
}

export function precheckSuggestsRetrieve(r: EmbeddingPrecheckResult) {
  return r.probed && r.topSimilarity >= ROUTE_RETRIEVE_SIMILARITY;
}
export function precheckSuggestsDirect(r: EmbeddingPrecheckResult) {
  return r.probed && r.topSimilarity < ROUTE_DIRECT_SIMILARITY;
}
```


### 6.4 预检失败 / 跳过 / 空库：分别走哪条路


| 情况                                      | `probed` | 典型 Top-1 | 路径                                              |
| --------------------------------------- | -------- | -------- | ----------------------------------------------- |
| `ENABLE_EMBEDDING_ROUTE_PRECHECK=false` | （不调用）    | —        | **skip** → LLM（若开）否则 `heuristic_default_direct` |
| embedding 失败 / 返回空向量                    | `false`  | —        | **skip** → 同上                                   |
| 新 workspace、向量库无文档、或过滤后无命中              | `true`   | `0`      | **decided direct**（`low_sim`），**不是 skip**       |
| Top-1 ≥ 0.68                            | `true`   | 高        | retrieve（`high_sim`）                            |
| Top-1 < 0.42                            | `true`   | 低        | direct（`low_sim`）                               |
| 灰区                                      | `true`   | 中间       | retrieve（`gray_retrieve`），不调 LLM                |
| LLM 路由抛错 / 解析失败                         | —        | —        | `heuristic_default_direct`                      |


要点：**空库 ≠ 预检失败。**


空库在 embedding 正常时会得到 `probed: true, topSimilarity: 0`，于是走 `low_sim → direct`，避免无意义地去全量检索，也避免误走 LLM「猜要不要检」。


只有「根本没探测成」才 skip 给 LLM；LLM 再挂，就 default **direct**（宁可少检，也不在基础设施抖动时乱检索）。


向量库 API 若直接抛异常（例如鉴权 403），当前实现会冒泡到聊天入口——这是诚实边界：预检层没有吞掉所有基础设施错误。生产上应打 error 日志并视情况降级为 skip。


### 6.5 完整 `decideQueryRoute`


```typescript
import { z } from "zod";

export type QueryRoute = "direct" | "retrieve";

export interface QueryRouteDecision {
  route: QueryRoute;
  reason: string;
  fastPath?: boolean;
  precheckSimilarity?: number;
}

const RouteSchema = z.object({
  route: z.enum(["direct", "retrieve"]),
  reason: z.string(),
});

declare function probeKbRelevance(
  query: string,
  workspaceId: string,
): Promise<{ probed: boolean; topSimilarity: number }>;

declare function generateRagHelperText(
  system: string,
  user: string,
  temperature?: number,
): Promise<string>;

const ROUTER_SYSTEM = `你是企业知识库问答路由器。判断是否需要检索私有知识库。
输出严格 JSON：{"route":"direct"|"retrieve","reason":"一句话中文"}
retrieve：需要用户上传/内部资料才能答准。
direct：通识、闲聊、算式、无需私有文档。`;

function routeQueryHeuristic(): QueryRouteDecision {
  return { route: "direct", reason: "heuristic_default_direct" };
}

async function routeWithLlm(query: string): Promise<QueryRouteDecision> {
  const raw = await generateRagHelperText(ROUTER_SYSTEM, query, 0);
  const jsonMatch = raw.match(/\{[\s\S]*\}/);
  if (!jsonMatch) return routeQueryHeuristic();
  try {
    const parsed = RouteSchema.parse(JSON.parse(jsonMatch[0]));
    return { route: parsed.route, reason: `llm:${parsed.reason}` };
  } catch {
    return routeQueryHeuristic();
  }
}

async function routeWithEmbeddingPrecheck(
  query: string,
  workspaceId: string,
): Promise<{ kind: "decided"; decision: QueryRouteDecision } | { kind: "skip" }> {
  if (!ENABLE_EMBEDDING_ROUTE_PRECHECK) return { kind: "skip" };

  const precheck = await probeKbRelevance(query, workspaceId);
  if (!precheck.probed) return { kind: "skip" };

  const sim = precheck.topSimilarity;
  const meta = { precheckSimilarity: sim };

  if (sim >= ROUTE_RETRIEVE_SIMILARITY) {
    return {
      kind: "decided",
      decision: {
        route: "retrieve",
        reason: `embedding_precheck:high_sim:${sim.toFixed(3)}`,
        fastPath: true,
        ...meta,
      },
    };
  }
  if (sim < ROUTE_DIRECT_SIMILARITY) {
    return {
      kind: "decided",
      decision: {
        route: "direct",
        reason: `embedding_precheck:low_sim:${sim.toFixed(3)}`,
        fastPath: true,
        ...meta,
      },
    };
  }

  // 灰色地带：宁可多检，这里不调用 LLM
  return {
    kind: "decided",
    decision: {
      route: "retrieve",
      reason: `embedding_precheck:gray_retrieve:${sim.toFixed(3)}`,
      fastPath: true,
      ...meta,
    },
  };
}

export async function decideQueryRoute(
  query: string,
  options: { workspaceId: string },
): Promise<QueryRouteDecision> {
  const intentFast = tryIntentFastPath(query);
  if (intentFast) return intentFast;

  const precheckOutcome = await routeWithEmbeddingPrecheck(query, options.workspaceId);
  if (precheckOutcome.kind === "decided") return precheckOutcome.decision;

  // 预检 skip：才轮到 LLM；再失败 → default direct
  if (ENABLE_LLM_QUERY_ROUTER) {
    try {
      return await routeWithLlm(query);
    } catch {
      return routeQueryHeuristic();
    }
  }
  return routeQueryHeuristic();
}
```

## 7. 日志与可观测


调阈值靠感觉会漂。最小集合是每次路由打结构化字段：


```typescript
type RouteLogFields = {
  requestId: string;
  route: "direct" | "retrieve";
  reason: string; // greeting_only | high_sim:... | gray_retrieve:... | llm:... | heuristic_default_direct
  fastPath: boolean;
  precheckSimilarity?: number;
  latencyMs: number;

```


线上调参时看三类分布即可：

1. `reason` 前缀占比（快路径 / high / low / gray / llm / default）
2. `precheckSimilarity` 直方图，对照用户反馈的「该检未检 / 不该检却检」
3. `route=retrieve` 之后 `vector.search.no_docs` 的比例——偏高说明路由偏激进，或检索层阈值过严

没有这些日志，0.68 / 0.42 只能永远停在「经验值」。


## 8. 如何从真实语料标定阈值（哪怕很粗）

1. 抽 N 条真实问题，人工标 `should_retrieve: yes/no`。
2. 对每条只跑预检，记下 Top-1。
3. 画两个条件错误：
    - 标了 yes 却 `< T_direct` → 漏检
    - 标了 no 却 `≥ T_retrieve` → 误检
4. 先固定灰区宽度，再平移两个阈值，使漏检优先被压低（与产品立场一致）。
5. 改 env 灰度，观察 §7 的三类分布，而不是一次性改死在代码里。

Phase 1 没有自动标定流水线；上面是手动能做完的最小闭环。

| `ENABLE_LLM_QUERY_ROUTER=false` 且预检 skip | `heuristic_default_direct`                                   |


## 10. 边界

- 预检本身要付一次 query embedding；用小成本换掉大量无效全量检索，但不是零成本。
- 0.68 / 0.42 是经验起点，换模型必须重标。
- 灰区偏向 retrieve，会提高检索 QPS；这是产品选择，不是精度最优。
- 路由说 retrieve 之后，仍可能 `no-docs`（检索阈值、混库挤占等）——「该检」≠「检得到」。
- 向量库抛错时，预检层未统一降级为 skip（应补日志与降级策略）。
- HyDE / Multi-Query / Rerank 不在本篇决策范围内；打开它们会放大「误 retrieve」的成本。

## 11. 收束


回头看，路由层真正守住的是：

1. **三层是什么**：意图快路径 → embedding 预检 →（仅 skip 时）LLM 兜底。
2. **为什么**：成本/延迟不对称，漏检比误检更伤；用廉价信号先分流。
3. **优势**：相对永远检索更干净更省；相对永远 LLM 更稳更便宜；相对纯规则更能覆盖换说法。
4. **不做会怎样**：闲聊脏账单、或知识库失灵、或每句多一轮模型。
5. **原理**：`decideQueryRoute` 短路求值；聊天入口用 `route === "retrieve"` 门控 `getRelevantContext`。

「要不要检」和「怎么检好」分开，阈值才调得动，日志才读得懂。
