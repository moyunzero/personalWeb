> **Personal GPT Phase 3 · 系列第 1 篇**

## 0. 零基础背景


### RAG（Retrieval-Augmented Generation，检索增强生成）

- **是什么**：让大模型回答前，先去你的知识库里「翻资料」，再根据翻到的段落生成答案——而不是纯靠训练记忆瞎编。
- **像什么**：开卷考试——先允许查书，再写答卷。
- **本项目**：Chat / Agent 查 Astra（或 Milvus）+ 可选 Elasticsearch，再把片段塞进提示词。

### 向量 / Embedding（嵌入）

- **是什么**：用模型把一句话变成一长串数字（本项目 **2048** 维）。意思相近的句子，数字「长相」也更像。
- **像什么**：给每段文字拍一张「语义照片」，找资料时比的是照片像不像，不是逐字相同。
- **本项目**：NVIDIA NIM 生成向量；问句也变成向量后再去库里找邻居。

### 向量库 / Astra DB

- **是什么**：**专门存向量并支持「找最像的几条」** 的数据库。**Astra DB** 是 DataStax 的云端托管版，开通账号就能用，少运维。
- **像什么**：不是 Excel 表格，更像「按长相检索的相册」。
- **本项目**：默认向量后端；可选换成自建 **Milvus**（第 9 篇）。

### ANN（Approximate Nearest Neighbor，近似最近邻）

- **是什么**：在海量向量里快速找「差不多最近」的邻居（允许一点点误差换速度）。
- **像什么**：人不逐个比对全市人口，而是先分区再细比。
- **本项目**：向量检索走 ANN；擅长「意思像」，对「奥德赛计划书」这种专有名词常常不如关键词稳。

### Elasticsearch（简称 ES）

- **是什么**：开源的**全文搜索引擎**（底层基于 Lucene）。你把文档灌进去，它建**倒排索引**（「哪个词出现在哪些文档」），查询时按关键词相关性排序。行业里很多人用它做站内搜索、日志检索。
- **像什么**：你自己网站里的「迷你 Google」——搜的是**你上传的那些字**，不是全网。
- **本项目**：Docker 本地起一个 ES；入库时把每段 chunk 的标题/正文写进去，问答时用它做关键词检索。挂了也没关系（检索侧会降级，见 fail-open）。

### BM25（Best Matching 25）

- **是什么**：ES（以及很多搜索引擎）给「关键词查询」打分的经典公式之一。名字里的 25 是历史版本号，不必纠结。它会考虑：
    - 词在文档里出现得是否够多；
    - 这个词是否太常见（「的」「是」权重大低）；
    - 文档长短是否要公平对待。
- **像什么**：阅卷老师给「题目关键词命中情况」打分——专有名词、标题里的词往往分很高。
- **本项目**：`esBm25Search` 就是「在 ES 里用 BM25 搜」；标题字段加权 `title^2`（标题命中更重要）。
- **和向量的差别**：BM25 认字不认义——「奥德赛」三个字对上就行；向量认义不认字——可能捞到「规划人生」却漏掉标题。

### IK 分词

- **是什么**：给中文切词的 ES 插件。英文靠空格分词；中文「珍珠奶茶」要切成「珍珠」「奶茶」等才能建索引。
- **像什么**：先把连续汉字拆成词典里的词，再交给 BM25。
- **本项目**：建 ES 索引时用 `ik_smart` 分析器；没装 IK 插件会导致建索引失败。

### RRF（Reciprocal Rank Fusion，倒数排名融合）

- **是什么**：把**多路检索结果**合成一路的算法。不看各路原始分数（因为 BM25 分和向量分没法比），只看「排第几」：排得越前贡献越大。常用公式：(1/(k+))，本项目默认 (k=60)。
- **像什么**：两份排行榜合并——两边都进前三的歌，总榜更高；不比「销量绝对值」。
- **本项目**：`reciprocalRankFusion([esHits, vectorHits])`，先 ES 列表再向量列表。

### Rerank（重排）

- **是什么**：在已经召回的一小撮候选里，再用更「懂相关性」的模型重新排序。
- **像什么**：粗筛简历 → 面试官精排；不是再全库海选。
- **本项目**：默认调用 HTTP rerank API（`ENABLE_RERANKER` 未设为 `false` 就开）；可关。

### fail-open / fail-closed

- **fail-open（失败仍放行）**：ES 超时 → 当作「没有关键词结果」，只用向量继续答，HTTP 仍 200。
- **fail-closed（失败就挡住）**：入库写 ES 失败 → 任务标失败，文档不能假装「已就绪」。
- **像什么**：读路线「导航没网还能用离线地图」；写路线「备份没成功不许点完成」。

### 举例对照


| 用户问          | 向量（认意思）      | BM25 via ES（认字） |
| ------------ | ------------ | --------------- |
| 「奥德赛计划书三条路径」 | 可能捞到别的「规划」文档 | 标题含「奥德赛」时很稳     |
| 「什么是幸福」      | 语义段落往往更好     | 关键词稀疏时较弱        |


**混合检索** = 向量 ANN 与 ES BM25 **同时查** → RRF 合并名次 →（可选）rerank。

## 1. 开场矛盾


Phase 1 的 Chat 检索只有 **向量 ANN**。实际语料里经常出现：

1. **专有名词 / 文档标题**：用户问「奥德赛计划书给了什么建议」，BM25 对标题命中极稳，向量 Top-1 却可能是 psychology 种子（相似度 0.4x）。
2. **拼候选再统一 rerank**：把 ES 和向量各取 Top-5 拼成 10 条再送 rerank，BM25 分数与 cosine 量纲不同，模型容易被错误尺度误导——reference 混合检索材料里明确标为反模式（Pitfall 1）。
3. **ES 依赖可选**：本地 demo 常忘起 Elasticsearch；检索路径不能因为 ES 超时就让整次问答 500。

事后整理：共享包 `hybridSearch` 做 **并行双路 → RRF 融合 → 可选 rerank → Corrective**；ES 读路径 **fail-open**，与 ingest 写路径的 fail-closed 对称（第 2 篇）。


## 2. 本篇目标


讲清共享函数 `hybridSearch` 的数据流、RRF 键规则、ES 降级与 `ENABLE_RERANKER` 开关。


**注意（与 Phase 1 不同）**：`hybridSearch` 里 `ENABLE_RERANKER !== "false"` → **默认开启 rerank**；设 `=false` 才关。Phase 1 Chat 旧常量曾是 `=== "true"` 才开——以本篇代码为准。


**不负责**：ingest 如何写 ES（第 2 篇）、Corrective 改写细节（第 3 篇）、意图路由何时调用 hybrid（第 7 篇）。

## 3. hybridSearch


### 3.1 总览


| 层/部件                   | 做什么                        | 代价             | 备注                        |
| ---------------------- | -------------------------- | -------------- | ------------------------- |
| `embedText`            | 2048 维 query 向量            | 1× NIM 调用      | 在 `hybridSearchOnce` 内    |
| `VectorStore.search`   | ANN，按 corpus 选 collection  | 向量库 RTT        | `getVectorStoreForCorpus` |
| `esBm25Search`         | IK 分词 BM25，`title^2`       | ES RTT；失败→`[]` | `.catch` fail-open        |
| `reciprocalRankFusion` | 按排名融合，保留 cosine 作门槛        | CPU 可忽略        | RRF 融合                    |
| `rerankDedicated`      | HTTP rerank 或 LLM fallback | 可选 8s 超时       | 可选重排                      |
| `maybeCorrective`      | top1 低分则改写再搜一次             | +1 LLM（第 3 篇）  | Corrective                |


默认 `corpus` 为 **`user`**（D-27）；查 seed demo 必须显式 `corpus: "seed"`。


### 3.2 为什么要 RRF 而不是分数加权


向量 cosine 与 BM25 `_score` **不可直接加权求和**。RRF 只看各列表中的**名次**：


[
(d) = _{} 
]


默认 `k = 60`（`RRF_K`）。融合后 **仍保留 chunk 上的** **`similarity`****（cosine）** 给下游门槛——Chat embedding 预检、Agent `minSimilarity`、Corrective 都依赖 cosine 尺度，不能把 rerank 分当 cosine 用。


### 3.3 优势


| 对比对象       | 本方案优势                  |
| ---------- | ---------------------- |
| 纯向量        | 标题/编号类 query 召回专名词     |
| 拼表再 rerank | 避免异构分数污染排序             |
| ES 必选      | ES 挂了仍单向量可用（带 warn 日志） |


### 3.4 不做会怎么样


| 若取消…                                     | 会发生什么                         |
| ---------------------------------------- | ----------------------------- |
| **RRF，改加权融合**                            | BM25 大分数压过向量，或反之；专有名词与语义召回不可控 |
| **并行检索**                                 | 延迟相加；体验变慢                     |
| **ES fail-open**                         | ES 抖动导致全站检索 500               |
| **保留 cosine 不替换为 RRF 分**                 | Corrective / Agent 门槛全失效      |
| **candidateLimit = max(limit×2, limit)** | 融合池太浅，RRF 无互补空间               |


### 3.5 原理小结（数据流）


```plain text
hybridSearch(query, workspaceId, corpus?)
  → embed(embedQuery || query)
  → parallel:
       vectorStore(corpus).search(vector, limit×2)
       esBm25Search(query)  // catch → []
  → reciprocalRankFusion([esHits, vectorHits])
  → if ENABLE_RERANKER !== "false": rerankDedicated
  → slice(limit)
  → maybeCorrective (最多 1 次改写重搜)
```


一句话原理：**用名次融合异构检索器，用 cosine 守门，用 ES 降级保可用。**

## 4. 方案取舍


| 方案                  | 优点                    | 缺点 / 为何不选     |
| ------------------- | --------------------- | ------------- |
| 仅调大 `limit` 单向量     | 零依赖                   | 专名词仍 miss     |
| BM25+向量线性加权         | 实现简单                  | 分数不可比，调参地狱    |
| **RRF + 可选 rerank** | 工业界混合检索常用；与 rerank 解耦 | 需维护 ES 索引     |
| 检索侧 ES fail-closed  | 强一致                   | 一次 ES 抖动全站不可用 |

## 6. 关键实现（完整核心）


### 6.1 hybridSearchOnce + 入口


```typescript
const DEFAULT_LIMIT = 5;

function resolveCandidateLimit(limit: number): number {
  return Math.min(Math.max(limit * 2, limit), 50);
}

function isRerankerEnabled(): boolean {
  return process.env.ENABLE_RERANKER !== "false";
}

async function hybridSearchOnce(
  params: HybridSearchParams,
  deps: HybridSearchDeps,
): Promise<RetrievedChunk[]> {
  const corpus = params.corpus ?? "user";
  const limit = params.limit ?? DEFAULT_LIMIT;
  const candidateLimit = resolveCandidateLimit(limit);
  const embed = deps.embed ?? embedText;
  const getStore = deps.getStore ?? getVectorStoreForCorpus;
  const esSearch = deps.esSearch ?? esBm25Search;
  const rerank = deps.rerank ?? rerankDedicated;

  const embedQuery = params.embedQuery?.trim() || params.query;
  const vector = await embed(embedQuery);

  const vectorPromise = getStore(corpus).search({
    workspaceId: params.workspaceId,
    vector,
    limit: candidateLimit,
  });

  const esPromise = esSearch({
    query: params.query,
    workspaceId: params.workspaceId,
    corpus,
    limit: candidateLimit,
  }).catch((err: unknown) => {
    console.warn("[hybridSearch] es unavailable; vector-only", { err });
    return [] as RetrievedChunk[];
  });

  const [vectorHits, esHits] = await Promise.all([vectorPromise, esPromise]);
  let fused = reciprocalRankFusion([esHits, vectorHits]);

  if (isRerankerEnabled() && fused.length > 0) {
    fused = await rerank(params.query, fused, limit);
  }
  return fused.slice(0, limit);
}

export async function hybridSearch(
  params: HybridSearchParams,
  deps: HybridSearchDeps = {},
): Promise<RetrievedChunk[]> {
  if (!params.workspaceId?.trim()) {
    throw new Error("hybridSearch requires workspaceId");
  }
  const fused = await hybridSearchOnce(params, deps);
  if (deps.skipCorrective) return fused;
  return maybeCorrective(params, fused, {
    rewrite: deps.rewriteQuery,
    reSearch: (query) =>
      hybridSearch({ ...params, query, embedQuery: query }, { ...deps, skipCorrective: true }),
  });
}
```


### 6.2 RRF（禁止拼表再 rerank；下列为控制流节选）


```typescript
export function reciprocalRankFusion(
  lists: RetrievedChunk[][],
  k: number = Number(process.env.RRF_K ?? 60),
): RetrievedChunk[] {
  const rankConstant = Number.isFinite(k) && k > 0 ? k : 60;
  const scores = new Map<string, { chunk: RetrievedChunk; score: number; listIdx: number }>();

  for (let listIdx = 0; listIdx < lists.length; listIdx++) {
    const list = lists[listIdx]!;
    list.forEach((chunk, idx) => {
      const id = chunk.documentId
        ? `${chunk.documentId}:${chunk.chunkIndex ?? chunk.text}`
        : chunk.text;
      const add = 1 / (rankConstant + idx + 1);
      const prev = scores.get(id);
      if (!prev) {
        scores.set(id, { chunk, score: add, listIdx });
        return;
      }
      prev.score += add;
      // 较后列表（向量）优先保留 cosine；另有同列表更高 similarity / 补 bm25Score 分支（见源码）
      if (listIdx > prev.listIdx) {
        prev.chunk = { ...chunk, bm25Score: chunk.bm25Score ?? prev.chunk.bm25Score };
        prev.listIdx = listIdx;
      }
    });
  }

  return [...scores.values()].sort((a, b) => b.score - a.score).map(({ chunk }) => chunk);
}
```

## 9. 诚实边界

- **未做**：学习排序（LTR）、查询侧 HyDE 默认仍关（`ENABLE_HYDE`）。
- **ISSUE-001**：user corpus 检索日志仍可能出现低分 psychology（混合 collection 历史债）；奥德赛 query 验收时 Top1 仍为正确文档。
- **seed collection**：验收环境若未建 `ASTRA_DB_COLLECTION_SEED`，`corpus=seed` 向量路径硬失败（ES 亦可能空）。
- **无编造 P95**：未接检索延迟 SLI。

---


## 10. 收束

1. 混合检索的核心是 **RRF 名次融合**，不是异构分数相加。
2. **cosine 保留**给门槛与 Corrective；rerank 只调序，不替代 cosine 语义。
3. **读 ES fail-open、写 ES fail-closed** 是刻意不对称。
4. 默认 **user corpus**，防 seed 污染生产问答。
