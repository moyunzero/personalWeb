> **Personal GPT Phase 2 · 系列第 4 篇**

## 0. 背景


### 什么是 tool calling（工具调用）


大模型默认只会「生成文本」。**工具调用**是另一条能力：模型在回答过程中可以发出结构化请求，例如「请执行名为 `kb_search` 的函数，参数 query=…」。运行时真的去跑这段程序，把返回文本塞回对话，模型再继续写。


没有工具时，模型只能靠训练记忆瞎编文档号；有工具时，它可以**查库、搜网页、做算术**——但仍会偷懒、越权、或把工具结果当指令。所以还要限制：**哪个角色允许挂哪些工具**。


### 为什么要拆成四个角色


一个人兼「查库 + 联网 + 算账 + 写终稿」，常见失败是：

- 写报告时顺手再搜一次网，把配额打爆；
- 查库时编造外链；
- 调度员自己去调工具，专科形同虚设。

Phase 2 的做法：同一个底层聊天模型，挂上**不同的 systemPrompt（工种说明书）+ 不同的 tools 数组**，得到四个专科；再加一个只调度、不绑工具的 Supervisor。


权限有两份「账本」，不要混淆：

- **`AGENT_TOOL_CAPS`**：给人读、给单测对齐的**文档化 allow-list**（改了常量不等于自动改绑定）；
- **`create*Agent({ tools: [...] })`**：真正决定运行时能不能发出 tool call 的白名单。

两者应对齐；真正挡住越权的是工厂里的 `tools`，不是 caps 对象本身。


| 角色         | 人话职责      | 允许的工具        |
| ---------- | --------- | ------------ |
| Retriever  | 只查内部知识库   | `kb_search`  |
| Researcher | 只查公开网页    | `web_search` |
| Analyst    | 只做受限算术    | `calculator` |
| Editor     | 只写面向用户的终稿 | （无）          |
| Supervisor | 只委派，不亲自检索 | （无）          |


联网另有硬上限：`MAX_WEB_SEARCH_CALLS_PER_TASK = 10`（工具侧计数强制）。并行调研主题最多 `MAX_PARALLEL_RESEARCH_TOPICS = 3`——常量与 Supervisor **prompt 双写**，**不是**运行时硬并发锁。


---


## 1. 开场矛盾


多 Agent 演示里，最容易翻车的不是「模型不够聪明」，而是**权限边界糊了**：

1. Retriever 若也能 `web_search`，知识库 miss 时它会偷偷补外网，终稿分不清「库内依据」和「网上摘要」——诚实检索协议立刻被绕开。
2. Editor 若挂上工具，终稿阶段又会发起检索，流式 UI 里「报告」和「中间工具噪声」缠在一起。
3. 只靠 prompt 写「请勿调用某某工具」不够：模型仍可能发出 tool call；真正挡住的是 **`tools: []`** **或只注入允许的那一把**。

事后整理时，我们把「文档化 allow-list」和「工厂绑定」做成双写：`AGENT_TOOL_CAPS` 给人读、给单测；`create*Agent` 里的 `tools` 数组给运行时。


## 2. 本篇目标


讲清四专科 + Supervisor 的**工具权限胶囊**：常量、工厂绑定、systemPrompt 边界规则、联网次数与并行主题上限。


**不负责**：Sequential 边如何排（第 1 篇）、Skill 文件如何加载（第 5 篇）、HIT/NO_HIT 协议细节（第 6 篇）、预检索（第 7 篇）。

## 3. 工具 caps


### 3.1 总览


| 层/部件                                  | 做什么                         | 代价        | 代码入口  |
| ------------------------------------- | --------------------------- | --------- | ----- |
| `AGENT_TOOL_CAPS`                     | 文档化各角色允许的 tool 名            | 需与工厂双写    | §6.1  |
| `create*Agent`                        | 真正绑定 `tools` + systemPrompt | 每角色一次模型图  | §6.2  |
| `MAX_WEB_SEARCH_*` / `MAX_PARALLEL_*` | 成本护栏（与 prompt 双写）           | 超限后降级跳过   | §6.1  |
| `createSpecialistAgents`              | 建图时实例化四专科并注入 Skill          | 读磁盘 Skill | 第 5 篇 |


对外效果：Supervisor / Sequential 图上的每个节点，**只能调用自己那把工具（或没有工具）**。


### 3.2 为什么要这么做


成本不对称：一次 `web_search` 要打外部 API；一次 `kb_search` 要 embedding + 向量查询；Editor 再外呼等于把「润色」变成「又一轮研究」。


职责分离后，诚实协议更好落地——只有 Retriever 产出 `KB_SEARCH_STATUS`，Editor 只消费上游结果写人话。


Prompt 里仍写「允许工具：kb_search」：给模型自我约束；**硬边界仍是 tools 数组**。


### 3.3 优势


| 对比对象               | 本方案优势                                |
| ------------------ | ------------------------------------ |
| 单 Agent 挂齐所有工具     | 越权面小；终稿阶段不会再搜网                       |
| 只靠 systemPrompt 劝说 | 运行时根本没有多余 tool schema                |
| 每个角色独立部署不同模型       | Phase 2 成本可控：同一模型换 prompt/tools 即可演示 |
| 无限联网次数             | 10 次封顶，账单与延迟有上界                      |


### 3.4 不做会怎么样


| 若取消…                    | 会发生什么                      |
| ----------------------- | -------------------------- |
| 取消 Editor 的 `tools: []` | 终稿阶段可能再检索，轨迹与正文搅在一起        |
| Retriever 同时绑 web       | miss 时偷补外网，假「库内引用」难查       |
| Researcher 同时绑 kb       | 联网角色污染 citation 解析来源       |
| Supervisor 绑专科工具        | 调度员亲自干活，专科与轨迹失真            |
| 取消 web 次数上限             | 单任务可能刷爆 Bocha / 触发 TPM 429 |
| caps 常量与工厂不一致           | 文档撒谎；单测会红（这正是双写的价值）        |


### 3.5 原理小结（数据流）


```plain text
用户任务
  → router（闲聊短路 / 进图）
  → Sequential 边 或 Supervisor handoff
  → 某专科节点：仅其 tools 对模型可见
        Retriever → kb_search
        Researcher → web_search（累计 ≤10 / 任务）
        Analyst → calculator
        Editor → 无工具，只写 Markdown
  → 消息汇总进下一节点 / 流式输出
```


一句话原理：**角色 = 同一模型 × 不同工具白名单 × 不同边界 prompt。**

## 4. 方案取舍


| 方案                              | 优点         | 缺点 / 为何不选                    |
| ------------------------------- | ---------- | ---------------------------- |
| 一个 Super-Agent 全工具              | 实现短        | 越权与幻觉难控；演示轨迹糊                |
| 每专科独立模型 / 独立进程                  | 隔离更强       | v2 运维与成本过重；明确不做 Docker agent |
| 运行时动态改 tools                    | 灵活         | 难测、难演示；易与 Skill 混淆           |
| **四专科固定 caps + 空工具 Editor（采用）** | 可测、可讲、边界清晰 | 不是「万能助理」；新工具要改 caps 与工厂      |


也曾想过「Editor 只读 KB、不写」——仍会诱使终稿阶段再检索。最终选择 **Editor 零工具**，材料只来自上游消息。

## 5. 调用链


```plain text
buildSupervisorGraph / createSequentialPipelineWorkflow
  → createSpecialistAgents(model)
       → createRetrieverAgent(model, { skillPrompt })  // tools: [kbSearchTool]
       → createResearcherAgent(...)                     // tools: [webSearchTool]
       → createAnalystAgent(model)                      // tools: [calculatorTool]
       → createEditorAgent(...)                         // tools: []
  → 图节点执行时模型只能发起已绑定 tool 的调用
  → web_search 内部 bump 计数；>10 则返回降级文案（不 throw）
```

## 6. 关键实现


### 6.1 权限胶囊与硬上限


```typescript
/**
 * D-15 硬上限：子 Agent / 工具调用护栏（与 prompt 双写）。
 * 「双写」= 常量写进 prompt 提醒模型，工厂 tools 数组才是硬边界。
 */

/** Researcher 单次任务 web_search 次数上限（工具内部计数，超限降级跳过） */
export const MAX_WEB_SEARCH_CALLS_PER_TASK = 10;

/** Supervisor 并行调研主题 / Researcher 实例上限（主要靠 prompt 约束，非运行时锁） */
export const MAX_PARALLEL_RESEARCH_TOPICS = 3;

/** 文档化 allow-list：各 Agent 允许的 tool 名（供单测与文档对齐，运行时以 create*Agent 的 tools 为准） */
export const AGENT_TOOL_CAPS = {
  retriever: ["kb_search"] as const,   // 只查内部知识库
  researcher: ["web_search"] as const, // 只查公开网页
  analyst: ["calculator"] as const,    // 只做受限算术
  editor: [] as const,                 // 终稿阶段禁止再调工具
  supervisor: [] as const,             // 调度员只委派，不亲自检索
} as const;
```


`web_search` 实现里对超限的处理是**降级跳过**（返回说明字符串），而不是抛异常打断整图——否则报告任务会在半路挂死。


### 6.2 工厂示例：Retriever（完整 create）


其余三角结构相同：换 `name` / `tools` / 边界文案。下面给出 Retriever 全文级控制流。


```typescript
import type { LanguageModelLike } from "@langchain/core/language_models/base";
import { createAgent } from "langchain";

import { KB_CITATION_RULES, TOOL_RESULT_SAFETY } from "../prompts/fragments/kb-citation-rules";
import { kbSearchTool } from "../tools/kb-search.tool";
import { AGENT_TOOL_CAPS } from "./caps";

export type AgentSkillOptions = {
  /** 已格式化的 Skill 文本块；追加到 systemPrompt，非 Agent 名 */
  skillPrompt?: string;
};

// 工厂函数：同一底层 model + 不同 tools/systemPrompt → 专科 Agent
export function createRetrieverAgent(model: LanguageModelLike, options: AgentSkillOptions = {}) {
  // Skill 正文可选；有则拼进 systemPrompt 末尾
  const skill = options.skillPrompt?.trim() ? `\n\n${options.skillPrompt.trim()}` : "";
  return createAgent({
    name: "retriever",
    description: "企业内部知识库检索与引用；回答需可溯源。",
    model, // 与其他专科共用同一聊天模型，省成本
    tools: [kbSearchTool], // 硬边界：模型只能看到这一把 tool schema
    systemPrompt: `你是 Retriever。职责边界：仅处理知识库（KB）检索与引用。

规则：
- 必须先调用 kb_search；禁止编造文档内容。
-${TOOL_RESULT_SAFETY}
- **无命中硬约束**：若工具或【知识库预检索】返回含\`KB_SEARCH_STATUS: NO_RELEVANT_HIT\`：
  - 对上游只回一句中文：「知识库未找到足够相关依据。」并另起一行保留标记\`KB_SEARCH_STATUS: NO_RELEVANT_HIT\`（供 Editor 识别）。
  - 禁止代码块、禁止任务规划、禁止表格、禁止列举假文档 / DOC-*、禁止假装命中。
  - 不要向用户解释工具协议；终稿由 Editor 撰写。
- **有命中**：若上下文已有【知识库预检索】且为\`KB_SEARCH_STATUS: HIT\`，直接复述其中 title / source / documentId / snippet，禁止改口称未命中；否则先调用 kb_search 再复述工具结果。
- 允许工具：${AGENT_TOOL_CAPS.retriever.join(", ")}。
- 混库召回边界（ISSUE-001）仍存在；低相关片段已被工具过滤。

${KB_CITATION_RULES}${skill}`,
  });
}
```


Researcher 侧会把 `MAX_WEB_SEARCH_CALLS_PER_TASK` 与 `MAX_PARALLEL_RESEARCH_TOPICS` 写进 prompt；Analyst 绑 `calculatorTool`；Editor 为 `tools: []`，并强调「无外网工具」「禁止复述 KB_SEARCH_STATUS」。


### 6.3 建图时如何挂上四专科


```typescript
// 建图前一次性实例化四专科；Skill 按名注入对应专科的 systemPrompt
function createSpecialistAgents(model: LanguageModelLike) {
  const skills = loadEnabledSkills(); // 从磁盘读 skills/<name>/SKILL.md
  return {
    retriever: createRetrieverAgent(model, {
      skillPrompt: formatSkillForPrompt(findSkill(skills, "kb-retrieval")),
    }),
    researcher: createResearcherAgent(model, {
      skillPrompt: formatSkillForPrompt(findSkill(skills, "web-research")),
    }),
    analyst: createAnalystAgent(model), // 当前无对应 Skill，边界写在工厂 prompt 里
    editor: createEditorAgent(model, {
      skillPrompt: formatSkillForPrompt(findSkill(skills, "report-writer")),
    }),
  };
}
```


Skill 是**追加进 systemPrompt 的流程指南**，不是第五个可 handoff 的 Agent（下一篇展开）。

## 7. 日志与可观测


Phase 2 没有按「工具越权次数」的正式 metrics 盘。可观测主要靠：


```typescript
// 概念型观测字段：Phase 2 未接正式 metrics，主要靠执行轨迹肉眼验收
type CapsObs = {
  agent: "retriever" | "researcher" | "analyst" | "editor" | "supervisor";
  toolName?: "kb_search" | "web_search" | "calculator";
  webSearchCallCount?: number; // 按 run_id / thread 隔离，防同会话并发串计数
  summary: string;             // 轨迹里的短摘要，便于 grep 是否越权调工具
};
```


执行轨迹里应看到：Retriever 节点出现 `kb_search`，Researcher 出现联网摘要，Editor **不应**再出现新的检索 tool 事件。web 超限时工具原文含「已达单任务上限」。

## 8. 如何验证


| 输入 / 条件              | 期望                                                                                              |
| -------------------- | ----------------------------------------------------------------------------------------------- |
| `AGENT_TOOL_CAPS` 单测 | retriever=`[kb_search]`，researcher=`[web_search]`，analyst=`[calculator]`，editor/supervisor=`[]` |
| 源码扫描工厂               | Retriever 无 `webSearchTool`；Editor 为 `tools: []`                                                |
| 多步「先查库再联网再写报告」       | 轨迹按专科出现对应工具；终稿无假 DOC-*                                                                          |
| Researcher 连续搜 >10 次 | 第 11 次起返回降级跳过文案，图不崩                                                                             |
| Supervisor prompt    | 写明只调度、禁止亲自 kb_search/web_search；含并行主题上限 3                                                       |

## 9. 诚实边界

- Caps 是 **allow-list 文档 + 工厂绑定**，不是 OS 级沙箱；模型仍可能在正文里「假装搜过」。
- Analyst 的 calculator 是受限表达式解析，不是任意代码执行。
- 并行「最多 3 个调研主题」主要靠 Supervisor prompt 约束；Sequential 路径按清单顺序跑，并不自动扇出 3 个 Researcher 进程。
- 未做：按租户的工具 ACL、动态热更新 caps、生产级越权审计指标。

---


## 10. 收束

1. 多 Agent 的第一道护栏是 **tools 数组**，不是口号式 prompt。
2. 四专科把「查 / 搜 / 算 / 写」拆开，诚实检索与成本封顶才站得住。
3. `AGENT_TOOL_CAPS` 与工厂双写，靠单测防止文档漂移。
4. Skill 只是流程说明书——下一篇专门拆「Skills ≠ Agent」。
