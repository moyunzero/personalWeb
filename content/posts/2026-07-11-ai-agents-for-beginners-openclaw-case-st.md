## 一、大型语言模型 (LLM) 基础概念


**GPT 的内涵**：GPT 代表**生成式预训练变换器（Generative Pre-trained Transformer）**。

    - **Transformer**：2017 年由 Google 提出，核心是**注意力机制（Attention）**，使其能同时处理句子中所有单词并理解它们之间的关系。
    - **Pre-trained**：模型在海量数据（如维基百科、书籍、代码）中学习语言**模式**而非事实。
    - **Generative**：模型逐字预测并生成新文本，而非简单的数据库搜索。

**Token（令牌）**：LLM 处理的基本单元。一个令牌约为 4 个英文字符或 0.75 个单词。令牌影响**成本、速度和上下文窗口**。


### 什么是 Token 以及它是如何生成的？

- **分词过程（Tokenization）**：在处理任何输入之前，系统会先将文本拆分为 Token。一个 Token 可以是一个完整的单词、单词的一部分，甚至是一个标点符号或单个字符。
- **拆分逻辑**：
    - **高频词汇**：在训练数据中经常出现的短词（如 "the"、"is"）或常见长词（如 "computer"、"language"）通常各自占据一个 Token。
    - **稀有词汇**：不常见的词会被拆分为更小的“构建块”。例如，"tokenization" 会被拆分为 "token" 和 "isization"；更复杂的词如 "anthropomorphisation" 可能会被拆分为 5 个 Token。
    - **特殊类型**：**代码**通常消耗更多 Token，因为其中的标点和关键字会被频繁拆分。此外，**非英语文本**由于在训练数据中代表性不足，每个单词通常会比英文消耗更多的 Token。

### Token 的换算估算

- **通用比例**：在英文文本中，**1 个 Token 大约相当于 4 个字符**，或者约等于 **0.75 个单词**。
- **实际感知**：一篇 1000 词的英文文章大约会转换成 1300 到 1500 个 Token。

### Token 的三大关键影响


Token 被视为开发 AI 智能体时的“流通货币”，它直接决定了以下三个核心要素：


A. 成本（Cost）

- **计费模式**：OpenAI、Anthropic 和 Google 等提供商均按 Token 数量对输入（Prompt）和输出（Completion）进行计费。
- **输出更贵**：**输出 Token 的成本通常是输入 Token 的 4 倍**。这是因为输入 Token 是并行处理的，而输出 Token 是逐个顺序生成的，每次生成都需要模型进行一次完整的计算，能耗更高。

B. 速度（Speed）

- **生成机制**：LLM 每次只预测并生成一个 Token。
- **延迟表现**：响应中的 Token 越多，等待时间就越长。例如，生成 100 个 Token 的响应速度远快于生成 2000 个 Token。

C. 上下文窗口（Context Window）

- **硬限制**：每个模型都有处理 Token 的最大数量限制（即上下文窗口），这包括了系统指令、对话历史、工具调用结果以及模型即将生成的回答。
- **容量增长**：随着技术发展，上下文窗口已从 GPT-3.5 的 4,000 Token 增长到现代模型（如 Gemini 1.5 Pro）的 1,000,000 Token 以上。
- **溢出后果**：如果输入和输出的总和超过此硬性限制，模型将无法处理请求。这就像一个“白板”，空间填满后，必须擦除（截断或压缩）旧的信息才能写入新内容。

**Temperature（温度）**：控制生成多样性的参数（0-2）。**0 为确定性输出**（适合代码、分类），**更高值则更具创意**（适合写作）。对于 AI 智能体，通常建议使用较低温度以保证可靠性。


在构建 AI 智能体时，**温度（Temperature）是一个至关重要的配置参数，它直接决定了模型生成响应的随机性**和**创造力**。


### 温度的核心定义与数值范围

- **定义**：温度是一个数值，通常设定在 **0 到 2** 之间。
- **控制机制**：它就像一个“调节旋钮”，控制模型如何从概率分布中采样。
    - 当 LLM 生成文本时，它会为每个可能的后续令牌（Token）计算概率。
    - **温度控制的是模型在这些选项中“掷骰子”的风险程度**。

### 不同数值下的表现

- **温度为 0（确定性模式）**：
    - 模型总是选择概率最高的响应，**没有任何随机性**。
    - **相同输入必然产生相同输出**（Same input, same output）。
    - 适合需要高度一致性和准确性的任务。
- **温度为 0.5 到 0.7（平衡模式）**：
    - 模型主要选择高概率选项，但偶尔会产生一些令人惊喜的变化。
    - 输出感觉更加**自然且可靠**。
- **温度超过 1.0（创造性模式）**：
    - 模型会更均匀地在所有选项中“分摊赌注”，从而变得极具创意，但也可能导致**胡言乱语（Nonsensical）**。

### **Temperature**不同场景下的最佳实践建议


| 任务类型               | 建议温度           | 理由                    |
| ------------------ | -------------- | --------------------- |
| **数据提取与分类**        | **0**          | 需要每次都得到相同的准确答案。       |
| **代码生成**           | **0 到 0.2**    | 代码需要的是正确性而非创造力。       |
| **一般对话**           | **0.5 到 0.7**  | 保持语言自然且具备基本的可靠性。      |
| **创意写作**           | **0.8 到 1.2**  | 需要多样性和惊喜感。            |
| **AI 智能体（Agents）** | **较低值（通常为 0）** | 智能体需要的是**可靠的决策**而非创意。 |


### 为什么 AI 智能体通常使用低**Temperature**？

- **可靠性优先**：智能体在运行过程中需要根据观察结果做出判断，如果温度过高，即使输入相同，智能体也可能在多次尝试中采取完全不同的行动路径，这会极大地增加调试难度并降低系统的稳定性。
- **确定性决策**：对于诸如调用天气插件或查询数据库等任务，开发者希望智能体的决策逻辑是**可预测的**。

### **Temperature**工程实现要点

- **API 层面设置**：温度是在每次 **API 调用**时单独设置的参数，由开发者控制而非模型自行决定。
- **代码示例**：在 Python SDK 中，只需在 `client.chat.completions.create` 函数中添加 `temperature=0` 即可将模型转变为确定性输出模式。
- **OpenClaw 的处理**：在 OpenClaw 等生产级系统中，模型后端（如 Hybrid Provider）会封装这些调用逻辑，确保在不同模型供应商（如 Claude, GPT, Gemini）之间切换时，温度设置能够保持一致。

**上下文窗口 (Context Window)**：LLM 的“工作内存”，包含系统指令、对话历史和工具结果。如果超出此限制，模型会遗忘较早的信息。


### **Context Window**核心组成与容量限制

- **构成要素**：上下文窗口不仅包含当前的输入，还包括**系统指令（System Instructions）、工具定义（Tool Definitions）、完整的对话历史**以及模型正在生成的**输出内容**。
- **硬限制特性**：上下文窗口是一个**硬性限制**，而非建议。如果输入和输出的总 Token 数超过了模型的窗口限制，模型将无法处理该请求，或者会导致系统报错。
- **容量演进**：
    - **早期模型**：2022 年的 GPT-3.5 仅有约 4,000 Token 的窗口（约 6 页文本）。
    - **现代模型**：GPT-4o 扩展到了 12.8 万 Token（约 200 页文本），而像 Gemini 1.5 Pro 等模型已支持高达 **100 万甚至 1,000 万 Token** 的超大规模窗口。

### 智能体（Agent）面临的特殊挑战


相比简单的聊天机器人，上下文窗口对 AI 智能体而言是核心的工程难题：

- **消耗极快**：智能体在循环中运行，每一次迭代产生的推理过程、工具调用指令及庞大的工具返回结果都会被塞入窗口。
- **单次开销示例**：在智能体的一次交互中，系统提示词可能占 2,000 Token，10 个工具定义占 3,000 Token，加上历史记录和推理空间，单次调用可能瞬间消耗 **23,000 Token**。
- **注意力衰减（U型曲线）**：研究表明模型对窗口**开头和结尾**的信息关注最强，中间的信息最容易被忽略（Lost in the Middle）。

### **Context Window**溢出处理策略


当对话内容超出窗口上限时，通常有以下几种处理模式：

- **截断（Truncation）**：直接丢弃最早的消息。这会导致智能体“失忆”，遗忘用户最初提到的姓名或偏好设置。
- **总结（Summarization）**：调用 LLM 对旧消息进行浓缩，用简短的摘要替换详细的历史记录，以节省 Token 并保留关键事实。
- **滑动窗口（Sliding Window）**：保持一个固定大小的窗口随着对话向前移动，始终只保留最近的内容。
- **上下文压缩（Compaction）**：这是 OpenClaw 采用的高级策略。它不仅总结旧消息，还会**修剪冗长的工具输出**，在保留核心事实的同时最大限度释放空间。

### **Context Window**经济与性能权衡

- **按量计费**：开发者需要为窗口内的每一个 Token 支付费用。如果窗口内堆积了 10 万 Token，即使你只问了一个简单问题，你也需要为这 10 万输入 Token 支付全额费用。
- **重复支出**：在一个复杂的任务中，如果智能体进行了 10 次 API 调用，且每次都携带 5 万 Token 的历史背景，开发者实际上支付了 **50 万输入 Token** 的费用。
- **速度延迟**：庞大的上下文会增加模型的推理负担，导致响应速度变慢。

### 上下文窗口 vs. 长期内存


**上下文窗口并非长期内存，**它更像是一个随用随擦的白板。要实现跨会话的记忆（如记住用户上周提到的信息），必须依赖**外部存储层**（如 JSON 文件、SQLite 数据库或向量数据库），在需要时将相关片段重新注入到当前的上下文窗口中。


在构建大语言模型（LLM）应用和 AI 智能体（Agent）时，开发者通常使用 API（应用程序编程接口）与模型交互。在这种模式下，对话不再是简单的纯文本，而是由具有特定**角色（Roles）**的消息数组构成的,。


主要的对话角色分为以下三种：


### 系统角色 (System Role)

- **定义**：这是由开发者设置的角色，用于定义模型的**行为规则、个性、身份和任务约束**,。
- **作用**：它相当于在员工上岗前给予的“简报”或“指令”，为模型设定整个对话的基调。
- **特性**：系统消息对最终用户通常是不可见的，但它在后台持续影响模型的每一个回复。例如，可以要求模型扮演“高级 Python 工程师”或“友好的客服专家”,。
- **应用**：开发者通过系统提示词（System Prompt）来设定约束（如“仅使用 JSON 格式回复”、“不要使用列表”）和提供背景知识,。

### 用户角色 (User Role)

- **定义**：代表与 AI 进行交互的**真实人类**。
- **作用**：它包含用户提出的实际问题、请求或指令。
- **地位**：它是对话的输入端，驱动模型根据系统角色的设定做出反应。

### 助手角色 (Assistant Role)

- **定义**：代表 **LLM 模型自身**生成的回复。
- **关键作用（上下文维持）**：由于大模型 API 本身是**无状态的（Stateless）**，这意味着模型不会记得之前的对话内容。
- **实现记忆**：为了实现多轮对话，开发者必须手动将模型之前的回复（作为助手角色）重新添加到消息列表中并发送给 API。这样模型在看到新问题时，能通过历史记录中的助手消息理解上下文（例如，知道用户提到的“那个城市”是指前文讨论过的“巴黎”）。

### 角色协作的意义


这三种角色共同构成了一个**消息数组（Messages Array）**。在执行任务时，系统消息排在首位，随后是交替出现的用户消息和助手消息,。这种结构化的方式让开发者能够精准控制模型的输出，并解决模型原生缺乏长期记忆的问题,。


在构建 AI 智能体时，**工具调用（Tool Calling，也称为函数调用 Function Calling）**是将其从一个纯粹的“文本生成器”转变为能够采取行动的“智能体”的核心机制。

定义两个工具：

- `check_calendar` — 查找指定日期发生的事件
- `send_email` — 向收件人发送电子邮件

代码会向模型发送用户消息，检测模型何时请求工具调用，在本地执行该工具，并将结果发送回去，以便模型可以组成最终答案。


**Tool 工具架构概述**


OpenAI API 要求工具采用特定的 JSON 结构。每个工具都是一个字典，其结构如下：


```plain text
{
    "type": "function",
    "function": {
        "name": "tool_name",
        "description": "What this tool does.",
        "parameters": {
            "type": "object",
            "properties": {
                "param_name": {
                    "type": "string",
                    "description": "What this parameter means."
                }
            },
            "required": ["param_name"]
        }
    }
}
```


要点：

- 模型会读取 `description` 字段，以决定何时调用该工具。
- 参数遵循 JSON Schema 格式
- `required` 列表告诉模型它必须提供哪些参数

```javascript
import os
import json
from openai import OpenAI

# 初始化 OpenAI 客户端，从环境变量中读取 API 密钥和基础 URL
client = OpenAI(
    api_key=os.getenv("OPENAI_API_KEY"),
    base_url=os.getenv("OPENAI_API_BASE"),
)

# 定义模型可以调用的工具列表（函数声明）
tools = [
    {
        "type": "function",
        "function": {
            "name": "check_calendar",
            "description": "查看用户在指定日期的日程安排。",
            "parameters": {
                "type": "object",
                "properties": {
                    "date": {
                        "type": "string",
                        "description": "要查询的日期，格式为 YYYY-MM-DD。"
                    }
                },
                "required": ["date"]
            }
        }
    }
]

# 模拟本地数据库或 API 的日历查询函数
def check_calendar(date):
    return "上午 10 点：团队例会，下午 2 点：看牙医"

# 根据模型生成的函数名和参数，在本地执行相应的工具
def execute_tool(name, args):
    if name == "check_calendar":
        return check_calendar(**args)
    return f"未知工具: {name}"

# 设置系统提示词与初始的用户提问
system_message = "你是一个贴心的个人助理。"

messages = [
    {"role": "system", "content": system_message},
    {"role": "user", "content": "我今天的日程安排是什么？"}
]

# 第一次调用大模型，传入对话历史和可用的工具列表
response = client.chat.completions.create(
    model="openai/gpt-4.1-mini",
    messages=messages,
    tools=tools,
)

# 获取模型停止生成的原因
finish_reason = response.choices[0].finish_reason
print(f"停止原因: {finish_reason}")

# 如果停止原因是 "tool_calls"，说明模型决定调用我们提供的函数
if finish_reason == "tool_calls":
    # 提取模型返回的助理消息（其中包含具体的工具调用指令）
    assistant_message = response.choices[0].message
    # 必须将助理的这条消息存入历史记录中
    messages.append(assistant_message)

    # 遍历模型要求调用的每一个工具（大模型可能一次要求调用多个函数）
    for tool_call in assistant_message.tool_calls:
        name = tool_call.function.name
        # 模型返回的参数是 JSON 字符串，需要解析为 Python 字典
        args = json.loads(tool_call.function.arguments)
        
        # 在本地执行函数，拿到真实数据
        result = execute_tool(name, args)

        # 将工具的执行结果以角色为 "tool" 的消息格式存入历史记录
        # 必须带上对应的 tool_call_id，以便大模型和前面的指令对齐
        messages.append({
            "role": "tool",
            "tool_call_id": tool_call.id,
            "content": result,
        })

    # 第二次调用大模型，此时带上了工具执行后的数据，让模型组织语言回复用户
    final_response = client.chat.completions.create(
        model="openai/gpt-4.1-mini",
        messages=messages,
        tools=tools,
    )
    # 打印最终模型结合日历数据后生成的回答
    print(final_response.choices[0].message.content)
else:
    # 如果模型不需要调用工具，直接打印模型首次的回答
    print(response.choices[0].message.content)
```

### 工具调用的核心定义

- **突破局限**：大语言模型（LLM）本身被困在训练数据中，无法访问实时信息或执行外部操作（如发送邮件、查询数据库）。
- **能力的延伸**：工具给了智能体“双手”。通过工具，模型可以**搜索网页、进行精确计算、调用 API、操作文件以及执行代码**。
- **基本原则**：让 LLM 负责“思考”（判断何时使用什么工具），让代码负责“执行”（确保结果的确定性和准确性）。

### 工具的组成部分


一个标准化的工具定义通常包含三个要素，模型通过阅读这些信息来决定是否调用该工具：

- **名称（Name）**：工具的唯一标识符。
- **描述（Description）**：详细说明工具的功能。模型依赖这段描述来判断该工具是否符合当前任务的需求。
- **参数（Parameters）**：定义工具所需的输入数据及其格式（通常遵循 JSON Schema 格式），例如日期、地点或查询关键词。

### 工具调用的循环过程（Tool Use Loop）


工具调用并非由模型直接运行代码，而是一个**感知—推理—行动（Perceive-Reason-Act）**的循环过程：

1. **用户输入**：用户提出请求（如“我今天的日程是什么？”）。
2. **模型决策**：LLM 意识到需要实时数据，它不会直接回答，而是输出一个**结构化的请求（JSON 格式）**，包含要调用的工具名称和参数。
3. **代码执行**：开发者的应用程序充当“中间人”，拦截该请求，并在本地环境或通过网络**运行对应的 Python 函数**。
4. **结果反馈**：程序将工具运行的结果（如日历上的会议记录）作为“工具消息”添加回对话历史中。
5. **最终响应**：模型阅读了这些新信息，将原始数据转化为自然语言回复用户。

### 常见的工具类型

- **搜索与查询**：网络搜索（Google Search）、数据库查询（SQL）。
- **计算工具**：执行精确的数学运算或单位转换，弥补 LLM 数学能力的不足。
- **API 交互**：发送电子邮件、创建日历事件或通过 REST API 与第三方服务通信。
- **系统与代码操作**：读写本地文件、执行 Python 脚本或 Shell 命令。

### 生产环境中的高级模式


为了确保工具调用的安全性和可靠性，通常会引入以下设计模式：

- **React 模式（Reasoning and Acting）**：强制模型在调用工具前写下“思考（Thought）”，在获得结果后写下“观察（Observation）”，这能显著提高复杂任务的成功率。
- **人工干预（Human-in-the-loop）**：对于涉及高风险的操作（如支付、发送邮件或删除数据），系统会暂停并请求人工确认后再执行。
- **安全沙箱（Sandboxing）**：在隔离的环境中执行代码或 Shell 命令，限制其访问权限，防止智能体误操作或受到攻击。
- **ACI（Agent Computer Interface）**：通过提供极其精确的工具描述和参数约束（如使用枚举值），引导模型更准确地选择和使用工具。

## 二、工作流 (Workflows) vs 智能体 (Agents)


在 AI 系统架构中，**工作流（Workflow）是指通过预定义的代码路径**来编排大语言模型（LLM）和工具的系统。它的核心在于由开发者提前决定处理步骤，而不是让模型自主选择路径。


### 工作流的核心定义

- **预定义性**：在工作流中，开发者在任务开始前就“画好了地图”。每一步的顺序、分支逻辑和执行条件都由程序代码定义。
- **确定性**：由于路径是固定的，系统的运行过程是可预测的，通常会有固定数量的 LLM 调用。
- **模型角色**：LLM 在工作流中主要负责处理每个步骤中的“重活”（如文本理解、生成或分类），但它不负责决定下一步该做什么。

### 常见的工作流设计模式


介绍六种开发者常用的工作流模式：

- **顺序模式（Sequential Steps）**：最简单的模式，将任务拆分为连续步骤。例如，第一步由 LLM 撰写邮件，第二步由另一个 LLM 调用来审查和润色第一步的内容。
- **路由模式（Routing）**：先由一个分类器 LLM 对输入进行识别，然后将其引导至对应的处理程序。这允许开发者针对简单任务使用便宜的模型，针对复杂任务使用昂贵的模型。
- **并行化/分段模式（Parallelization/Sectioning）**：同时运行多个独立的子任务。例如，在生成“每日简报”时，同时检查日历、邮件和天气，最后汇总结果。
- **投票模式（Voting）**：多次运行同一任务并采取共识结果。例如，询问三个模型某内容是否安全，并以多数票为准。
- **编排者模式（Orchestrator）**：中心 LLM 动态决定需要哪些子任务，并将其分配给“工人”LLM 处理。这处于工作流与智能体的交界处，但通常仍具有结构化的组合逻辑。
- **生成器-评估器模式（Generator-Evaluator）**：一个模型生成响应，另一个模型进行评估并提供反馈，生成器根据反馈进行改进，直到质量达标。这常用于翻译或编写生产代码。

### 什么时候该选择工作流？


在增加系统复杂度（转向智能体）之前，应尽可能优先寻找最简单的解决方案。**工作流适合以下情况**：

1. **问题已被充分理解**：即使输入会变，但处理步骤是明确且固定的（如翻译链、数据提取）。
2. **需要高度的可预测性**：你需要确切知道系统会如何运行，且需要方便调试。
3. **成本和延迟敏感**：工作流的调用次数固定，成本更易控制。
4. **不需要模型自主决策**：任务不需要模型在运行过程中根据发现的新情况即兴调整路径。

### 核心差异：谁在控制“流”？


这是区分两者的关键指标：**是开发者通过代码预设路径，还是 LLM 自主决定下一步？**

- **工作流（Workflow）**：控制权在**开发者**手中。开发者在任务开始前就“画好了地图”，通过代码定义了每一步的顺序、分支和逻辑。LLM 只是作为执行每个特定步骤的“工具”或“大脑”。
- **智能体（Agent）**：控制权在 **LLM** 手中。它运行在一个持续的循环中（感知—推理—行动），根据当前观察到的情况和反馈，自主决定调用哪个工具或采取什么行动，直到完成目标为止。

### 特征对比


| 特征        | 工作流 (Workflow)                 | 智能体 (Agent)                    |
| --------- | ------------------------------ | ------------------------------ |
| **路径定义**  | **预定义（Predefined）**，步骤在运行前已确定。 | **动态（Dynamic）**，路径随着任务进展而出现。   |
| **可预测性**  | **高度可预测**，执行路径固定，易于调试。         | **不可预测**，同一个问题可能采取不同的路径或工具调用。  |
| **成本与延迟** | **固定且可控**，LLM 调用次数是已知的。        | **变量且较高**，取决于解决问题所需的迭代次数。      |
| **适应性**   | 较差，遇到未预见的边界情况可能失效。             | **强**，如果工具调用失败或需要更多信息，能自主调整策略。 |


### 应用场景选择


建议遵循“**最简原则”**：优先选择最简单的方案，仅在必要时增加复杂度。

- **适合选择工作流的场景**：
    - 任务路径清晰、可重复，例如**邮件分类、日常简报生成、数据提取或翻译链**。
    - 需要严格控制成本和延迟。
    - 可以通过流程图完整画出所有可能路径的任务。
- **适合选择智能体的场景**：
    - 任务是**开放式的**，路径取决于过程中发现的信息，例如**行程规划、复杂的排程任务、编码协助**。
    - 需要处理无法预定义的异常情况或需要深度研究的任务。
    - 任务具有“如果工具 A 不行，尝试工具 B”的探索性特征。

### 关系与演进


工作流与智能体并非非黑即白，而是一个**连续的光谱**：

1. **左端（纯工作流）**：所有步骤预定义。
2. **中间（路由/编排）**：LLM 决定走哪条预设路径（路由）或动态创建子任务（编排器）。
3. **右端（自主智能体）**：LLM 在循环中拥有完全的控制权。

### 决策清单


在决定使用哪种模式时，可以询问以下四个问题：

1. **能否预先定义所有路径？**（能 $\rightarrow$ 工作流；不能 $\rightarrow$ 智能体）
2. **LLM 是否需要决定下一步做什么？**（不需要 $\rightarrow$ 工作流；需要 $\rightarrow$ 智能体）
3. **这是否是一个定义明确的重复性任务？**（是 $\rightarrow$ 工作流；不是 $\rightarrow$ 智能体）
4. **成本是否需要被严格控制？**（是 $\rightarrow$ 工作流；不是 $\rightarrow$ 智能体）

**总结**：最好的系统通常会将两者结合——使用**工作流来处理可预测的部分**，而将**智能体用于需要灵活性和自主决策的环节**。


## 三、AI 智能体


**AI 智能体（Agent）** 被定义为一个以大语言模型（LLM）为核心、在**循环（Loop）中运行，并利用工具**来完成特定目标的系统。其最本质的特征在于它能够根据观察到的反馈自主决定接下来的行动，而不是仅仅遵循开发者预定义的固定路径。


### 核心运行模式：感知—推理—行动循环


智能体遵循一个被称为**感知—推理—行动（Perceive-Reason-Act）**的闭环过程：

- **感知**：智能体接收来自用户的输入、之前工具调用的结果以及完整的对话历史。
- **推理**：模型对当前状态进行分析，判断任务是否已完成，如果没有，则规划下一步需要采取的行动或需要调用的工具。
- **行动**：模型输出一个结构化的请求（如调用某个函数），由代码执行该操作并将结果反馈回循环中。

### 五大核心组件


一个完整的智能体系统通常由以下五个部分构成：

- **模型（Model）**：智能体的“大脑”，负责所有逻辑推理和决策过程。
- **工具（Tools）**：智能体的“双手”，让它能超越文本生成的限制，去搜索网页、精确计算、发送邮件或执行代码。
- **内存（Memory）**：
    - **短期内存**：即**上下文窗口（Context Window）**，存储当前的对话内容、工具结果和中间推理过程。
    - **长期内存**：通过外部数据库或 JSON 文件持久化存储用户偏好、历史任务事实等信息，使其在不同会话间保持一致。
- **编排循环（Orchestration Loop）**：一段底层代码（通常是 `while` 循环），负责不断驱动模型进行尝试，直到模型返回“停止”信号。

### 推理策略：React 模式


**React 模式**（Reasoning and Acting，推理与行动）是构建 AI 智能体最主流的推理策略，其核心在于让模型在行动（调用工具）之前先进行显式的推理（思考）。


**核心机制：三步循环**


React 模式强制智能体在每个环节都遵循“思考—行动—观察”的闭环过程：

- **思考 (Thought)**：在调用任何工具之前，模型必须先写下一行“Thought:”，解释它**为什么**选择这个工具、它的**计划**是什么以及它希望通过这次行动获得什么信息。
- **行动 (Act)**：基于上述思考，模型输出一个结构化的指令（通常是 JSON 格式）来执行具体的操作，如搜索网页、查询日历或运行代码。
- **观察 (Observation)**：工具执行完毕后，系统将结果以“Observation:”的形式反馈给模型。模型会记录并分析这个结果，判断它是解决了问题还是需要进一步的操作。

这个循环会一直持续，直到模型判断任务已经完成并给出最终回答。


**为什么需要 React 模式？**

- **决策质量更高**：研究表明，当 LLM 在行动前显式地进行步骤分解（即**思维链/Chain of Thought**的应用）时，其决策的准确性会显著提升。
- **可审计与透明化**：在没有 React 的系统中，推理过程隐藏在模型内部，开发者只能看到最终结果；而在 React 模式下，整个思考过程是**可见且可审计的**，方便开发者调试和理解智能体为何做出特定行为。
- **动态适应性**：React 让智能体具备了“边做边学”的能力。它不只是死板地执行预设计划，而是能根据“观察”到的新信息（如搜索结果不理想或工具报错）实时调整策略。

**具体案例演示**


以“预订下周五 300 美元以下去纽约的机票”为例，React 智能体的运行逻辑如下：

1. **Thought**: 我需要找下周五去纽约的机票，且预算在 300 美元以下。我应该先搜索所有可选航班。
2. **Act**: 调用 `search_flights(destination="NYC", date="next Friday")`。
3. **Observation**: 找到 4 个航班，最低价 280 美元，但时间是凌晨 6 点。
4. **Thought**: 280 美元的航班符合预算，但用户通常不喜欢凌晨。我需要检查用户的偏好。
5. **Act**: 调用 `get_user_preferences()`。
6. **Observation**: 用户偏好下午出发的航班。
7. **Thought**: 下午 2:30 有一趟 280 美元的航班。在预订前，我得确认用户那天下午是否有空。
8. **Act**: 调用 `check_calendar(date="next Friday")`。
9. **Observation**: 用户周五上午 11 点后没有任何日程。
10. **Thought**: 机票符合预算和偏好，且日程无冲突。我现在执行预订。

**局限性与风险控制**


尽管 React 模式很强大，但它也存在一些常见的失败模式：

- **陷入死循环**：智能体可能会反复调用同一个工具，却意识不到它已经获得了所需的信息。
- **过度规划**：消耗过多的 Token 进行思考，而没有采取实际行动。
- **拒绝修正**：即便观察结果显示原计划行不通，模型仍坚持原有路径。

**应对方案**：生产级系统（如 OpenClaw）通常会设置**最大迭代次数限制**（如最多 10 次循环）、**Token 预算上限**以及**硬性的错误处理逻辑**来确保系统的稳定性。


### 内存


短期内存：上下文窗口 (Context Window)


短期内存即智能体的“工作内存”，对应于大语言模型（LLM）的**上下文窗口**。

- **定义与构成**：它是模型在给定瞬间能“看到”的所有文本的总和，包括**系统指令、对话历史、工具调用结果以及模型自身的中间推理**。
- **硬限制**：上下文窗口是一个硬限制。位于窗口内的数据模型可以处理，而窗口之外的数据对模型来说则不再存在。
- **白板比喻**：来源将短期内存比作**白板**——当前写在白板上的内容模型都能看见，但当白板写满时，必须擦除旧内容才能写新内容。

内存管理策略（应对溢出）


由于智能体的每一轮迭代（工具调用、思考过程等）都会消耗大量 Token，内存很快就会填满。常见的管理策略包括：

- **截断（Truncation）**：直接丢弃最旧的消息。这种方法简单但容易导致模型丢失早期重要的上下文（如用户的姓名或最初的偏好）。
- **总结（Summarization）**：调用 LLM 对旧消息进行精简总结，用简短的摘要替换详尽的历史记录，以节省 Token 空间。
- **上下文压缩（Context Compression）**：选择性地移除不重要的内容，而不是删除整条消息。这是生产级代理（如 **OpenClaw**）常用的策略。
- **滑动窗口（Sliding Window）**：保持一个固定大小的消息窗口随对话向前移动，通常会锁定并保留第一条“系统提示词”以维持智能体的身份设定。

长期内存：持久化存储 (Persistence)


长期内存允许智能体在不同的对话会话之间记住信息，这在 LLM 原生功能中是不存在的，需要通过工程手段实现。

- **笔记本比喻**：长期内存被比作**笔记本**，智能体可以随时查阅其中的历史记录。
- **实现方式**：
    - **键值存储（Key-Value Store）**：保存特定事实（如“用户住在布鲁克林”）并在每次请求时注入提示词。
    - **JSON/文件存储**：将用户偏好或历史事实写入文件，供智能体后续读取。
    - **向量数据库（Vector Database）**：将过去的对话转换为嵌入（Embeddings）存储，当需要时通过语义搜索检索相关记忆。

内存的工程挑战与成本

- **直接成本**：由于模型是按 Token 计费的，如果为了维持记忆而在每次调用时都填充大量的历史上下文，会导致费用迅速增加。
- **性能权衡**：更大的上下文意味着更好的结果，但也意味着更高的延迟和成本。在生产环境中，管理这种平衡是核心技能之一。
- **质量影响**：如果核心上下文被错误地丢弃，智能体的决策质量会显著下降，甚至表现得“健忘”。

### 多智能体系统（Multi-agent Systems）


当单个智能体因工具过多或提示词过长而难以管理时，可以引入协作模式：

- **编排者 + 专家模式（Orchestrator + Specialists）**：最常见的模式。编排者决定谁来做哪部分工作。例如，用户要求“研究工具并写个追踪脚本”，编排者会同时安排 A 研究、B 写代码、C 存偏好。这种模式支持**并行工作**，效率极高。
- **流水线模式（Pipeline）**：智能体按顺序运行，每个环节精炼上一个环节的输出。通常流程为：**规划智能体**（拆解步骤）→ **执行智能体**（调用工具）→ **评审智能体**（核查结果）。这在需要极高准确性的生产代码编写中非常有用。
- **辩论/对抗模式（Debate/Adversarial）**：让两个具有不同立场的智能体互相讨论。例如，一个智能体倾向于省钱（推荐凌晨航班），另一个倾向于舒适（推荐下午航班）。最后由合成者智能体（Synthesizer）根据用户的真实偏好做出最优决策。

**智能体间的通信机制**


为了让信息在不同专家间流转，通常采用以下三种方式：

- **共享消息历史**：所有智能体都能读取和写入同一个对话列表。
- **移交消息（Handoffs）**：一个智能体完成工作后，将总结好的关键信息直接传递给下一个。
- **共享内存库**：所有智能体通过读写同一个中央数据库（如向量数据库或 JSON 文件）来同步状态。

**多智能体系统会显著增加复杂度和延迟**，因此仅在以下情况使用：

- **工具广度过大**：单个智能体若管理 50 个工具容易产生幻觉或误操作，拆分成每个专家管理 5 个工具更可靠。
- **需要不同模型**：例如，使用快速且便宜的模型进行分类（编排），使用功能最强大的模型进行深度推理或代码编写。
- **任务具有明确的可分性**：子任务之间逻辑独立，适合专门化处理。

## 四、 AI 智能体的六种核心故障模式


### 1. 工具故障 (Tool Failures)

- **现象**：工具调用本身失败，原因包括 API 服务宕机、输入参数无效或请求超时。
- **解决方案**：采用 **“错误回传”** 策略。不要在代码中静默捕获错误，而是使用 `try-except` 块封装工具执行逻辑，将捕获到的异常或错误信息作为“工具结果”返回给智能体（作为 Observation）。这样智能体就能感知到失败，并尝试采取不同的方法或向用户解释问题。

### 2. 错误的工具选择 (Bad Tool Selection)

- **现象**：智能体为当前任务选择了不适用的工具，例如在需要搜索时调用了日历工具。
- **解决方案**：这被视为一个**设计问题**。应通过 **改善 ACI（智能体计算机接口）** 来解决：
    - **优化描述**：提供精确、独特的工具名称和详细的功能描述，告知智能体该工具何时使用、何时不该使用。
    - **增加负面示例**：在提示词中明确指出工具不适用的场景。

### 3. 幻觉工具调用 (Hallucinated Tool Calls)

- **现象**：智能体尝试调用一个根本不存在的工具，或者传递了非法参数。
- **解决方案**：
    - **参数约束**：在工具的 JSON Schema 定义中添加严格的参数约束，例如使用**枚举值（Enums）**来限制可选范围，强制模型从有效列表中选择。
    - **代码层验证**：在工具边界进行参数验证，而不是仅依赖提示词，确保非法参数无法进入执行层。

### 4. 无限循环 (Infinite Loops)

- **现象**：智能体反复执行相同的动作且没有进展，这会迅速耗尽 Token 和预算。
- **解决方案**：
    - **设置最大迭代次数 (Max Iterations)**：将 `while true` 循环替换为带上限的循环（如最多 10 次）。
    - **强制退出逻辑**：当达到迭代上限时，强制触发退出分支，要求智能体根据现有信息给出最佳答案。
    - **监控报警**：实时监测循环次数，在接近限值时（如第 8 次）发出预警。

### 5. 上下文溢出 (Context Overflow)

- **现象**：对话历史和工具结果累积超过了模型的上下文窗口限制。
- **解决方案**：实施 **“上下文压缩 (Context Compression)”** 策略：
    - **总结旧消息**：使用 LLM 总结早期的对话内容，用精简的摘要替换冗长的历史记录。
    - **修剪冗余**：修剪掉过长的工具输出，仅保留核心事实。
    - **滑动窗口**：仅保留最近的几轮对话，但始终锁定并保留首条系统提示词以维持智能体身份。

### 6. 模型错误 (Model Errors)

- **现象**：包括 API 频率限制（Rate Limit）、服务器错误或输出格式错误。
- **解决方案**：
    - **模型降级/回退 (Model Fallback)**：配置多个供应商作为备份。如果主要模型（如 Claude）不可用，系统自动切换到备用模型（如 GPT 或 Gemini）。
    - **指数退避 (Exponential Backoff)**：遇到频率限制错误时，让系统等待一段时间并逐步增加重试间隔。
    - **结构化输出强制**：使用强制 JSON 模式确保模型输出的内容符合程序可读的格式。

### **推理与计划层面的失败**


即使工具和模型都在运行，智能体在逻辑规划上也可能出错：

- **原地打转 (Going in Circles)**：智能体不理解自己已经获得了信息，从而反复进行同样的工具搜索。
- **过度计划 (Overplanning)**：智能体消耗了过多的 Token 进行推理，却迟迟不采取实际行动。
- **错误的假设 (Wrong Assumptions)**：智能体基于对任务的错误理解制定计划，导致路径南辕北辙。
- **拒绝适配 (Not Adapting)**：即使工具返回的结果显示原计划行不通，智能体仍固执地坚持原有方案。

### **LLM 原生局限性故障**


智能体的“大脑”本身也存在一些固有的盲点：

- **幻觉 (Hallucination)**：模型并不是在查找事实，而是在根据模式生成文本。当它不知道答案时，可能会自信地编造看似正确的错误回答。
- **知识断层**：模型的知识截止于其训练日期，无法获知最近发生的事件。
- **数学与计算错误**：由于 LLM 是预测单词而非计算数字，直接让其进行复杂数学运算常会出错。

### 生产环境中的安全与鲁棒性


构建生产级智能体（如 **OpenClaw**）时，必须考虑以下挑战：

- **安全沙箱**：在隔离环境中执行代码和 Shell 命令，防止智能体误操作或受到恶意指令攻击。
- **人工干预（Human-in-the-loop）**：对于支付或删除数据等高风险操作，设置暂停环节请求人工确认。
- **上下文管理**：当对话过长超出窗口限制时，采用**压缩（Compaction）**或总结技术来腾出空间，同时保留核心信息。
- **错误恢复**：当 API 调用失败或模型陷入无限循环时，具备自动重试、降级到备用模型以及强制退出循环的能力。

## **五、框架（Framework）**


在构建 AI 智能体（Agent）时，**框架（Framework）** 是预先封装了多种模式和组件的库，旨在简化开发流程。


### 框架的核心定义与功能


框架是将开发者手动构建的各个智能体组件（如循环、工具注册、内存等）进行标准化封装的库。它的主要作用包括：

- **组件预置**：将复杂的“智能体循环”转变为内置的“运行循环（Run Loop）”；将“工具注册”简化为装饰器或 Schema。
- **内存管理**：自动处理会话历史和向量存储的集成。
- **协作原语**：提供多智能体协调的原始操作、重试逻辑和失败回退链。
- **权衡**：框架的核心权衡是**速度与控制权**。框架能让开发更快，但它也会在架构、命名和抽象方式上替开发者做决定，有时可能导致开发者需要“对抗框架”来满足特殊需求。

### 主流智能体框架概览


五个在行业中具有代表性的框架：

- **LangChain & LangGraph**：目前最广泛使用的框架。LangChain 最初用于链接 LLM 调用；**LangGraph** 则专门为智能体设计，将行为建模为图形（节点为步骤，边为转换），是 Python 生态系统的首选。
- **Anthropic SDK**：虽然不是完整的框架，但它是调用 Claude 的官方客户端，内置了对工具调用、流式传输和多轮对话的支持，适合构建轻量级应用。
- **OpenAI Agents SDK**：官方框架，核心概念是**“移交（Handoffs）”**，即一个智能体决定需要帮助时直接将对话移交给另一个智能体，非常适合“编排者-专家”模型。
- **Google Agent Development Kit (ADK)**：基于 Gemini 模型，同样采用图形化建模，并与 Google Cloud（如 Vertex AI, BigQuery）深度集成。
- **Mastra**：一个 **TypeScript 优先**的框架，将 Python 生态中的智能体模式带到了 JavaScript/TypeScript 生态中。

###  “从零构建” vs. “使用框架”


通过 **OpenClaw** 的案例讨论了选择路径的考量。OpenClaw 没有使用上述主流框架，而是基于专用的轻量级包（如 `PI agent core`）构建。


**建议选择框架的场景：**

- 需要快速交付产品。
- 团队已经熟悉该框架。
- 需要利用现成的集成生态和社区示例。
- 处于原型开发阶段。

**建议从零构建（或使用低级库）的场景：**

- 有非常特定的、不寻常的需求。
- 需要对智能体循环的每个部分进行精细控制。
- 框架的抽象层开始阻碍开发或性能。
- 构建需要大规模运行或在受限环境（如树莓派）运行的系统，以减少依赖包的大小和开销。

### 框架中的关键技术概念

- **接地（Grounding）**：Google 框架强调的概念，指将智能体响应连接到可验证的数据源（如搜索结果或数据库），以解决幻觉问题。
- **显式编排层（Orchestration Layer）**：将决策、执行工具和管理内存的逻辑显式化，作为连接模型、工具和内存的“胶水”。
- **执行通道（Execution Lanes）**：在生产级框架中用于处理并发请求，防止多个会话的数据互相污染。

## **六、OpenClaw**


**OpenClaw** 是一个生产级、开源且可自托管的 AI 智能体平台。它被设计为一个运行在用户自有设备上的个人助理，能够处理复杂的任务并通过多种即时通讯渠道进行交互。


### 1. 核心定义与定位

- **全能个人助理**：OpenClaw 实现了“感知—推理—行动”（Perceive-Reason-Act）循环，使其能像人类助理一样思考、执行工具并根据反馈调整策略。
- **多渠道集成**：它支持通过 **WhatsApp、Telegram、Slack、Discord、iMessage** 和 **Signal** 等多种渠道与用户通信。
- **硬件兼容性**：它可以在 macOS、iOS、Android、Linux、Windows 甚至 **Raspberry Pi（树莓派）**上运行。

该平台包含以下 **8 个主要系统**：

1. **智能体执行系统 (Agent Execution)**：负责运行核心循环并处理执行过程中的错误。
2. **网关 (Gateway)**：作为一个 WebSocket 服务器，负责协调系统内的所有事务。
3. **渠道 (Channels)**：用于集成各种即时通讯平台（如 WhatsApp、Telegram、Slack 等）。
4. **工具 (Tools)**：提供具体的功能支持，包括 Bash 命令执行、网页搜索和浏览器控制等。
5. **内存 (Memory)**：负责存储会话历史记录以及用于语义搜索的向量嵌入（Embeddings）。
6. **路由 (Routing)**：负责将接收到的消息分配给相应的智能体进行处理。
7. **插件 (Plugins)**：用于扩展系统的各项能力。
8. **配置 (Config)**：通过经过验证的 JSON 5 文件来管理整个系统的所有设置。

这些系统共同协作，使 OpenClaw 能够实现从接收消息、推理决策到执行工具并最终通过相应渠道回复用户的完整流程。


### 2. 底层架构与核心包


OpenClaw 并非基于 LangChain 等通用框架构建，而是使用了由 Mario Zechner 开发的四个专门化的底层包，以实现更轻量级和更精准的控制：

- **Pi AI**：处理底层的 HTTP API 调用，支持从不同供应商流式传输 Token。
- **Pi Agent Core**：定义了所有组件（如 50 多个工具接口和事件系统）通用的标准语言和类型。
- **Pi Coding Agent**：管理智能体回话的核心对象，负责维护对话历史、运行工具循环以及将历史持久化到磁盘。
- **P-tui**：提供终端用户界面，支持 Markdown 渲染、自动补全以及复杂的 UI 布局。

### 3. 六大核心系统组件


在代码实现上，OpenClaw 被拆分为六个关键区域：

1. 智能体循环 (Agent Loop)
- **核心位置**：位于 `src/agents` 文件夹中。
- **关键文件**：`pi_embedded_runner.ts` 是最重要的文件，它负责驱动整个“感知—推理—行动”（Perceive-Reason-Act）循环。
- **功能详述**：该组件作为系统的“指挥部”，接收来自各渠道（如 Slack 或命令行）的消息，将其发送给大语言模型（LLM），检查模型是否需要调用工具，并根据结果重复循环直到任务完成。在生产环境层面，它还额外处理了**身份验证、流式传输、多供应商回退（fallback）和错误恢复**。

2. 内存系统 (Memory)

- **核心位置**：位于 `src/memory` 文件夹。
- **关键组件**：
    - `manager.ts`：负责读取、写入和搜索记忆。
    - `search_manager.ts`：通过**向量搜索（Vector Search）**让智能体根据含义（而非精确关键词）寻找相关记忆。
    - `storage.ts`：底层的存储后端。
- **技术实现**：OpenClaw 使用 **SQLite** 进行持久化存储，并利用向量嵌入（embeddings）实现跨会话的长期记忆。

3. 工具集 (Tools)

- **核心位置**：注册中心位于 `src/agents/(tools)/agent_tools.ts`，具体实现分布在如 `bash_tools.ts` 等文件中。
- **功能详述**：系统中注册了 **50 多个工具**，每个工具都配有 LLM 可读取的描述和定义参数的 Schema。
- **应用实例**：涵盖了从基础的信息检索到复杂的代码执行（如通过 `bash_tools.ts` 运行 Shell 命令），且所有高风险操作（如代码执行）都包含**手动审批校验**。

4. 渠道引擎 (Channels)

- **核心位置**：每个平台在 `src/channels` 下都有独立的文件夹（如 Slack、Telegram、Discord、iMessage、WhatsApp）。
- **功能详述**：该组件负责**消息标准化**。它接收平台特定的原始消息，将其规范化后交给智能体循环处理，最后再将智能体的回复转化为对应平台支持的格式。对于智能体本身而言，它无需感知消息是来自哪个具体的社交软件。

5. 供应商管理 (Providers)

- **核心位置**：位于 `src/providers` 文件夹。
- **关键文件**：`hybrid.ts`。
- **功能详述**：负责管理 AI 模型后端（包括 Claude、GPT、Gemini 和本地模型）。该组件实现了**顺序故障切换**机制：如果首选供应商（如 Claude）不可用，系统会自动尝试 Gemini 或本地模型，确保用户始终能收到响应而不会报错。

6. 安全沙箱 (Security/Sandbox)

- **核心位置**：位于 `src/agents/sandbox` 文件夹。
- **功能详述**：这是生产环境中的关键护栏，负责在每一个工具调用执行前进行**强制检查**。
- **防御机制**：它严格控制哪些二进制文件可以运行、哪些文件路径可以访问、哪些操作必须屏蔽。这种安全性是通过**代码硬编码**而非提示词实现的，这意味着智能体无法通过“话术”绕过这些物理限制。

### 4. 智能体运行的五个阶段


OpenClaw 每次处理消息时都会严格遵循五个工程化阶段：

- **阶段 1：设置 (Setup)**：加载会话历史，确定模型供应商，并根据策略动态组装系统提示词和可用工具。
- **阶段 2：验证 (Validation)**：检查上下文窗口大小。如果对话过长，会自动触发**上下文压缩（Compaction）**，总结旧消息以释放空间。
- **阶段 3：尝试循环 (Attempt Loop)**：执行真正的推理循环，直到模型给出最终回答。
- **阶段 4：错误处理 (Error Handling)**：处理 API 频率限制、重试逻辑、指数退避以及格式错误恢复。
- **阶段 5：持久化 (Persistence)**：使用**会话锁定（Session Locking）**机制安全地将更新后的对话和状态写入磁盘，防止并发请求导致数据损坏。

### 5. 高级提示词工程 (Prompt Engineering)


OpenClaw 的系统提示词不是简单的文本，而是一个由 **19 个段落**组成的动态生成系统：

- **分段注入**：根据当前运行的智能体、频道和加载的技能，动态包含身份、工具定义、安全规则和用户偏好等模块。
- **结构化推理**：强制智能体使用特定的 `<think>` 标签先进行思考，然后再给出最终答案，以提高决策的鲁棒性。
- **示例驱动**：在提示词中嵌入“正确 vs 错误”的 Few-shot 示例，确保输出格式能被下游系统完美解析。

### 6. 安全与生产特性

- **人机协作 (Human-in-the-loop)**：对于发送消息、修改数据库或执行删除操作等高风险行为，OpenClaw 会暂停并请求用户手动确认。
- **执行巷道 (Execution Lanes)**：通过并发控制确保多个用户同时发送消息时，各自的会话状态不会交叉污染。
- **零信任原则**：不信任任何来自工具或外部输入的指令（如防止提示词注入），在工具边界而非提示词层面实施硬性验证。
